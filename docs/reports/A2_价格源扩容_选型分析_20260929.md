## 一、结论先行（TL;DR）

> **★ 最终结论：A2 暂缓不做。** 前提是"**用户无创业板/科创板购买资格**" ⇒ 不该放开双创
> ⇒ 战法池排除双创是正确设计 ⇒ **没有标的需要补 K 线**。下面的量化是"万一要放开"时的
> 决策依据，**当前不需要执行**。触发条件见文首状态框与 §8。

1. **需求池只有 ×1.39，不是 ×6.4。** 战法池 2026 → 2901 只（注：2026 为已修正前缀后的口径），
   因为 `filter_stock_pool` 默认 `min_market_cap=50亿` 已是一道强过滤，双创多数够不着。
2. **"空扫"的性质不是"功能不可用"，而是"验证盲区"。** 它**不在扫描侧**
   （战法走腾讯按需 K 线，能覆盖全池）；无 K 线的信号**仍会被推送**（白名单是**战法级**
   判据），只是它在**回测/统计里被跳过** ⇒ ①该信号没有历史背书；
   ②**战法胜率样本系统性偏向主板** ⇒ 用主板样本给双创放行 = **外推风险**。
   （系统已有 `check_signal_coverage` 覆盖率**告警**兜底，非硬拦截。）
3. **建议不采用"全市场 K 线铺开"，也**不**采用事件驱动 —— 改做「回填池扩容」。**
   即把回填池从"**触达过的**"扩到"**战法池里没有 K 线的**"（复用现成优先队列）。
   依据：现有机制是"先被选中 → 次日回填 → 之后可验证"，**首次选中必然是盲区**；
   扩容后双创**在被选中之前**就有 K 线 ⇒ **无盲区、无延迟**（详见 §7）。
   而全量铺开的代价是 **≈634MB 存储 + ≈395 万行回填**（受数据源限流，需数周~数月）。
4. **决策 1（前缀修正）已执行**：`filter_stock_pool` 原先只判 `300`/`688`、漏 `301/302/689`
   ⇒ 301 段 240 只一直待在池内空转。已改为引用 `backtest.engine` 的**唯一前缀来源**，
   **池子 2266 → 2026 只**。剩余决策见 §8。

## 四、★★ 关键发现：「空扫」不在扫描侧，而在白名单/回测侧

### 4.1 扫描侧：能覆盖全池 ✓

所有战法统一调用：

```
strategies/*.py::_check_stock  →  strategies/base.py::get_kline_with_indicators
                               →  app.tencent.get_kline
                                  ├─ 内存缓存 KLINE_CACHE（盘中 TTL 90s）
                                  ├─ 未命中 ⇒ 真实请求腾讯（对 300/688/301 均可用，A1 已实测）
                                  └─ WAF 冷却期 ⇒ 查 DB kline_cache 兜底，否则返回 []
```

⇒ **战法扫描不依赖 `backtest_prices`**，因此"扫不到双创"不成立。

### 4.2 白名单侧：读 `backtest_prices` ✗

```
strategies/recommendation.py::_recompute_whitelist()
   → from app.backtest.strategies import _load_prices_map
   → prices_map = _load_prices_map(codes, start=...)      # ← 读 backtest_prices
```

⇒ 没有 K 线的标的**在重放里撮合不到** ⇒ **不产生胜率样本**。

**★ 但「不产生样本」≠「信号被丢弃」**（本文 v1 在此判断过强，已修正）：
- `get_push_whitelist()` 返回的是**战法英文名列表** —— 白名单是**战法级**判据，
  **个股级不查价格** ⇒ 无 K 线的个股信号**仍会被推送**（只要其所属战法在白名单）；
- `check_signal_coverage`（`flash/scheduler.py:880-891`）是**告警**（无价格/滞后 >20% 时
  推 `_notify_failure`），**不是硬拦截**；其自身注释写的也是"信号会在**回测中**被静默跳过"。

⇒ 真实后果是两条，都属"验证盲区"而非"功能不可用"：
1. **该信号没有历史背书**（回测里没有它的胜负）；
2. **战法胜率样本系统性偏向主板** ⇒ 拿主板样本去给双创信号放行 = **外推风险**。

**同一机制还影响**：`coach.audit.backfill_outcome`（5 日结果回填）、模拟盘撮合、
日报/周报的绩效归因。

### 4.3 修正后的表述

> 不是"战法扫不到双创"，**也不是"信号被静默丢弃"**，而是：
> **"无 K 线的标的在回测/统计里没有样本 ⇒ 它被推送时没有历史背书，
> 且战法胜率的分母偏向主板 ⇒ 外推风险。"**
> 性质是**验证盲区**，不是功能缺失 —— **A2 的紧迫性据此下调**。

### 4.4 顺带发现的口径 BUG —— ✅ 已修正（2026-09-29）

`exclude_chinext` 只判 `300` ⇒ **`301` 段（创业板注册制新股）从未被排除，一直待在战法池里**
（240 只，仅 8 只有 K 线 = 纯空转）。`exclude_star` 同款问题（只判 `688`，漏 `689`）。

**修法（避免第二份口径）**：把前缀集合抽到 `backtest/engine.py`（那里本就有权威定义）
作为**全项目唯一来源**，两处都引用：

```python
STAR_PREFIXES    = ("688", "689")             # 科创板（689 = CDR）
CHINEXT_PREFIXES = ("300", "301", "302")      # 创业板（301/302 = 注册制新股段）
BROAD_PREFIXES   = STAR_PREFIXES + CHINEXT_PREFIXES   # 双创 = 20cm
```

`filter_stock_pool` 改为 `code.startswith(STAR_PREFIXES / CHINEXT_PREFIXES)`；
`engine._limit_pct` 的 20cm 判定改用 `BROAD_PREFIXES`（行为不变）。

**实测验证**：`_limit_pct` 对 300/301/302/688/689 仍返 0.20、对 600/000 仍 0.10 ✓；
战法池 **2266 → 2026**（移除 240 只全为 301 段，**无预期外移除**）✓。

## 五、量级测算（若选"全量铺开"）

以现库均值为基准：**753 行/只、0.121 MB/只**。

| 方案 | 目标只数 | 预计行数 | 预计体积 | 需补只数 |
|---|---|---|---|---|
| 现状 | 870 | 65.5 万 | 105 MB | — |
| 补齐现行池 | 2026 | ≈153 万 | ≈245 MB | 1309 |
| **放开双创（推荐上限）** | **2901** | **≈218 万** | **≈351 MB** | **2173** |
| 全市场铺开 | 5251 | ≈395 万 | ≈634 MB | 4412 |

> 目标只数为**前缀修正后**口径。

**额外的三条约束**

1. **回填吞吐（最大约束）**：`backfill_history.backfill_daily(quota=...)` 是**每晚限量**的，
   原因写在 docstring 里 —— **数据源（东财/腾讯）对连续请求限流**（实测教训：
   "400 只池子里 334 只长期 0 数据"）。**现机制是为 870 只设计的**，扩到数千只需重算配额与周期。
2. **存储**：≈634 MB（全市场，含索引更多）⇒ Supabase 档位需评估。
3. **读取 egress**：`backtest/strategies.py` 已有字节级兜底
   （`_PRICES_CACHE_MAX=200` / `_PRICES_BAR_MAX=900` / `_PRICES_BARS_MAX=50000` ≈ **65 MB**），
   **内存可控**；但池子变大 ⇒ 缓存命中率下降 ⇒ 库查询上升 ⇒ **egress 才是要担心的**
   （项目目标 < 167 MB/天）。
   > ⚠️ 注：早前"必须改整表常驻内存模式"的说法**不成立** —— 该缓存本就是按需 + 上限。

## 六、候选路径对比

| 路径 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A** 全量铺开到 Postgres | 回填 3141/5251 只进 `backtest_prices` | 改动最小、一条链路、口径统一 | ≈379~634 MB + egress 线性涨 + 回填周期长（限流） |
| **B** 纯按需拉取 | 不留历史，用时现拉 | 库里不涨 | 扫描/重放时外部请求暴涨（限流）、**历史不可复现**（回测命门） |

## 七、将来**若启动**时的推荐方案：E（**回填池扩容**）

### 7.0 先看现状机制（这一节是 v2 新增，也是推荐变更的原因）

现有回填池由 `backfill_history._collect_strategy_codes()` 决定：

```python
# 1. strategy_results 中全部战法选股；
# 2. 近 days 天 ranking_history 中出现过的评分股票。
```

⇒ 即"**先被选中 → 当日/次日回填 → 之后可验证**"。
实测佐证：池子规模 870 只 ≈ `strategy_results` 440 + `ranking_history` 473 − 重叠
≈ `backtest_prices` 的 870 只 —— **三者自洽，说明这不是"缺失"，而是"按需"的必然结果**。

**⇒ 因此唯一的 Blind Spot 是：「第一次被选中」那一刻还没有 K 线。**
而 v1 推荐的"事件驱动按需回填"（信号来了才补）会**保留**这个盲区（且延迟一天）。

### 7.1 理由（全部来自本次实测）

> ⚠️ **本节的前提是"决定放开双创"。** 若**不放开**（用户无购买资格 ⇒ 见 §8 决策 2），
> 则本方案**无标的可做** —— 这正是 A2 被判"暂缓"的原因。

0. **★ 增量收益本身就偏小（关键澄清）**：本方案消除的只是"某标的**首次**被选中那一天
   少一条回测样本"，而**次日即被现有机制回填**（§7.0）⇒ 属"**机制自愈**"。
   而"外推风险"（主板样本给双创放行）**只在放开双创后才存在**。
1. **池子只 ×1.39**（2026 → 2901），不是 ×6.4 —— 全量铺开的动机被削弱。
2. **触达率很低**：301 段 240 只曾在池内，实际只选出 **10 只**（≈4%）。
   ⇒ 即使放开双创（+875 只），按同比例推算增量触达约几十只/周期。
3. **真实缺口实测 = 27 只**：评分触达的双创 29 只中，仅 2 只有 K 线。
   ⇒ 量级在**几十只**，而不是几千只。
4. 回填通道**限量**（数据源限流），预算应花在"真正会被用到"的标的上 ——
   而"战法池里没 K 线的"正是可用的排序依据。

### 7.2 形态

```python
# backfill_history._collect_strategy_codes() 的池来源增加一项：
#   3. 战法池（复刻 filter_stock_pool）中「尚无 K 线」的标的
#      —— 按流动性（成交额/市值）排序，排在队尾或按配额混合推进
```

- **复用现成优先队列**（"无数据排最前、滞后越久越前"）与单只增量 `backfill()`（含复权
  基准检测、限速、失败切源），**不新建回填通道**。
- **池子来源**：日批在 GitHub Actions 上**没有内存行情**，但可用 `market_snapshot`
  （最新收盘快照，含 `market_cap`/`amount`，**单位为万元**）**复刻 `filter_stock_pool`**
  的过滤条件 ⇒ 不依赖实时缓存。
  ⚠️ 复刻时**必须复用 §4.4 的共享前缀常量**，否则口径又会分叉。

### 7.3 收益与代价

| | v1（事件驱动） | **v2（回填池扩容）** |
|---|---|---|
| 盲区 | 仍有（信号来了才补） | **无**（被选中前已有 K 线） |
| 延迟 | 1 天 | **无** |
| 工程量 | 需在信号链路插环节 | 改池来源 + 配额，**小时级** |
| 口径风险 | — | 复刻池子须与 `filter_stock_pool` 同源 |

⇒ 把 A2 从"**≈634 MB 存储 + ≈395 万行回填 + 回填通道重构**"降级为
"**改一个池来源 + 几百行增量**" —— **差两个数量级**。

| 3 | A2-E（回填池扩容）是否立项 | **⏸ 暂缓** | 决策 2 = 不放开 ⇒ **无标的可做**；且其增量收益本就偏小、机制自愈（§7.1 第 0 条） |
| 4 | 统一重扫口径 | **⏸ 随 A2 一同暂缓** | 它是 A2 的验收项，不与 A2 独立 |

**⇒ A2 整体：暂缓。触发条件 = 开通双创购买资格，或出现与"可交易范围"无关的新用途。**

### 8.1 ★ 为什么「前缀修正」反而是本轮的实质收益（与能否买双创无关）

| | 修正前 | 修正后 |
|---|---|---|
| 战法池 | 2266 只（含 **301 段 240 只创业板**） | **2026 只（沪 / 深主板）** |
| 与用户可交易范围 | **不一致** —— 可能选出**买不了**的票 | **一致** ✓ |
| 连带问题 | 那些票还被算进**战法胜率统计** ⇒ **判据被不可交易标的污染** | 已消除 ✓ |

> 举例：某战法靠一批买不了的创业板票把胜率撑到 60%，而用户实际能做的那批票可能只有 45%
> —— 修正后**统计口径与可执行性对齐**。

### 8.2 ★ 分清 A1 与 A2（避免误读为"整个全市场化改造都该停"）

| | **A1（已做，继续）** | **A2（暂缓）** |
|---|---|---|
| 解决的问题 | **市场统计口径**：涨跌家数 / 两市成交额 / 涨停家数 | **战法能选什么** |
| 双创的权重 | 成交额约 **40%**、且是涨停主力 | — |
| 是否依赖购买资格 | **不依赖** ✓ | **依赖** ✗ |
| 判断 | **该做** —— 漏双创 ⇒ 市场温度失真 ⇒ `coach._breadth()` ⇒ `gate_add` 判据失真 | **不做** |
