# 全项目审查：多轮迭代后的逻辑冲突排查与优化建议（2026-09-13）

> 审查方式：纯静态代码审查（5 个专项探查 + 人工复核），**全程未连接 Supabase，零 egress 消耗**。
> 审查范围：backend/app（约 3.9 万行）+ scripts + frontend 评分引擎 + 配置开关面。
> 置信度标注：✅=已人工读码复核；其余为深度探查结论（高/中置信），标「待复核」处建议改动前再确认。
> 行号基于 2026-09-13 main 分支（HEAD=0b61c9f）。

## 1. P0 — 必须尽快修

### P0-1 ✅ regime 双写者使 neutral_bearish「两日确认」退化为单日
- **位置**：`backend/app/flash/scheduler.py:1648`（`regime_cache_loop` 在常驻任务列表）+ `scripts/daily_batch.py:109-121`（`task_market_regime` 日批再跑一次）+ `backend/app/backtest/market_regime.py:437-448`（prev 读法）与 `:600-633`（按日期覆盖 upsert）。
- **机制**：`_apply_bearish_refine` 的 prev 读法是 `ORDER BY date DESC LIMIT 1`（无日期下限）。Render 15:40 写入当日行后，日批 19:30 重算时「昨日」读到的是**当日 15:40 的行** → 进入条件 `raw_nb and prev_raw is True` 当日即成立，退出同理提前一天。Actions re-run / `--force` 重跑同样触发。
- **影响**：①nb 进/出全部提前一天，两日确认形同虚设（这正是为修"9 天横跳 5 次"而设计的机制）；②同一天 15:40 与 19:30 可能写出不同 state，daily_report/trader_brief（读表）与 live_ranking/评分权重（读内存）口径分叉；③`daily_batch.py` 顶部 docstring 写「只读模式下被关」，与 scheduler 实际把 `regime_cache_loop` 放常驻列表矛盾——两位作者认知不一致。
- **修法**（两处都做，5 行改动）：
  1. prev 查询加 `WHERE date < :today`（并校验是上一交易日，见 P1-2）；
  2. `refresh_regime_cache` 开头判断「history 已有当日行且非 force → 跳过重算」，保证同日幂等。
- 另：把 `regime_cache_loop` 从 Render 常驻列表移除**或**保留并在日批跳过，二选一，并把决策写回两边注释。

### P0-2 ✅ 模拟盘盘后兜底把未满持有期的仓位提前平掉，实盘口径系统性偏离回测 v2
- **位置**：`backend/app/strategies/paper_trading.py:746-751`（兜底分支两个 `reason` 都走 `_close_position`）+ `:653-660`（`_hold_days` 用**自然日**）。
- **机制**：盘后兜底窗口 15:40 起，而 `backtest_prices` 当日回填 16:10 才开始 → 兜底时永远看不到当日 K 线。周一成交的仓位：周三兜底时 `_hold_days(周一,周三)=2 < 3`，但代码走 `else` 分支以**周二收盘价**平仓（`timeout_no_trigger`）。「持有 3 交易日」实际退化为约 2 日；周五成交的仓位周一就被平（自然日口径）。未做跌停可卖性检查（engine 侧有 `_sellable`）。
- **影响**：模拟盘实测胜率/持有天数与白名单重放（v2 口径，3 个交易日）**系统性分叉**——而「模拟盘实测 vs 回测胜率对比」正是 PLAN §2.6 排定的关键校验点，这个偏差会让校验结论失真。
- **修法**：兜底分支改为「未满持有期且未触发止损 → `continue` 顺延」；`_hold_days` 改交易日口径（或直接复用回测撮合的 K 线根数逻辑）；持有期/止损常量引用 `backtest/strategies.py` 的 `WARFARE_HOLD_DAYS_V2/WARFARE_STOP_PCT_V2`（见 P1-8）。

### P0-3 ✅ 榜单每次重算全量拉 mainforce_state（无缓存），egress 治理后最大的新漏洞
- **位置**：`backend/app/routers/scoring.py:1090-1091`（每次重算 `_mf_load([s["code"] for s in valid])`，在 ranking_live 早退判断**之前**）+ `backend/app/mainforce/state.py:196`（`load_latest` 直接 `SELECT DISTINCT ON ... chip_json`，零缓存）。
- **量级**：前端榜单页交易时段每 60s 刷新 → 重算每 3min 一次 → 每交易日约 80 次 × ~2000 只 × chip_json ≈ **40-55MB/天**（有人开榜单页时）；叠加 ranking_live 500 行含 payload ≈ **再 +20MB/天**（`scoring.py:1072` + `live_ranking.py:226`，行宽 840B）。
- **对照**：egress 治理目标 <167MB/天（投影 70-95MB），这一个点就可能吃掉一半预算，且是 09-13 之后新出现的行为。
- **修法**：① `load_latest` 结果按 code 集合做 30-60min 进程缓存（mainforce_state 本来就是日批日更表）；② ranking_live 读取列裁剪（不要 payload）；③ 中期把 mainforce_state / ranking_live 接入 `sync_meta` 版本门控（机制已有，见 §5 建议 4）。

## 2. P1 — 本周内排期修

### 2.1 regime 链路

**P1-1 ✅ nb 保持分支可覆盖当日 defensive 判定**（`backtest/market_regime.py:458-466`）
昨日为 nb 且昨日 raw=True 时，今日即使已判成 defensive（恐慌大跌），`raw_nb` 因 `state != neutral` 恒 False、`prev_raw` 为 True → 落入最后的「保持 nb」分支，返回 neutral_bearish。**defensive（独立权重/trade_gate 禁加仓）被降级为 nb（权重同 neutral/trade_gate 允许 20% 轻仓）整整一天**——恰在最需要防御的切换日犯错。修法：保持分支加前置 `state == NEUTRAL` 校验，当日非 neutral 一律返回当日判定。

**P1-2 ✅ prev 行未校验日期，历史断档时跨缺口误判**（`backtest/market_regime.py:438-440`）
prev 不要求是上一交易日。若 history 停更 N 天（09-08 事故重演），今日 raw=True + N 天前 raw=True 即"确认"进入 nb。修法：`WHERE date < :today` + 交易日校验，断档时按"无 prev"处理并打日志。

**P1-3 ✅ 阴跌战法闸门用当日 raw ma_trend，绕过两日确认**（`strategies/market_regime.py:507,536-538`）
`STRATEGY_GRIND_GATE` 判 `ma_trend == down` 用当日原始值：模拟盘入池层 D+0 就全禁，而评分/仓位侧 nb 要两日确认才生效。同一"阴跌"信号在两层生效日不同——与该闸门注释里"避免横跳噪音"的设计初衷相反。修法：闸门改读细化后的 regime（或对 ma_trend 也做同等确认），并写明两层的生效日差是有意还是无意。

**P1-4 ✅ `detect_market_regime` 永不返回 neutral_bearish**（`strategies/market_regime.py:91-96`）
该函数读 `load_regime_history()` 的原始 state（未经 `_apply_bearish_refine`），是战法推荐、`router.py:422`、recommendation 等的 regime 来源 → nb 档对它们完全不可见（恒显示 neutral）。`regime_review.py:64` 的复盘统计同样不含 nb 档。修法：读 history 后套用细化逻辑（或直接读 `market_regime_history.state` 落库的细化态），并让回放与生产一致。

**P1-5 mainforce_state 的 regime 读取无 restore 兜底，None 静默**（`scheduler.py:661-666`、`daily_batch.py:134-139`）
`except: pass` 后 regime=None = 出货乘数闸门不生效、无告警。同文件 trade_gate/confluence/tracker 都有 restore 回退，唯独这里没有。修法：补 restore；regime 为 None 时在日报输出告警行。

**P1-6 restore 无新鲜度校验；同日状态变化不重切权重**（`backtest/market_regime.py:649-676`、`routers/scoring.py:46-55`）
restore 把任意旧行当"当前状态"喂给七个消费方（stale 不告警）；`_engine_weights_applied` 只按 date 去重，P0-1 修复后同日 15:40/19:30 state 变化不会重新 set_weights。修法：restore 加「日期 == 最近交易日」断言 + state 变化时允许同日重应用。

**P1-7（待复核）SQLite 后端下 `prev_raw is True` 身份比较失败**（`backtest/market_regime.py:448,461`）
SQLite 返回 int 1/0 与 NULL，`is True`/`is False` 恒不成立 → 本地 SQLite 模式 nb 永远无法经确认进入/退出。生产 Supabase(psycopg2) 返回真 bool 不受影响。修法：改真值判断 `bool(prev_raw)` / `prev_raw is not None and not prev_raw`。

### 2.2 战法管线（回测/模拟盘/白名单口径）

**P1-8 ✅ 「退出策略 v2」存在四套口径**——白名单重放✅、lowvol 回测脚本✅，但：
- 模拟盘：提前平仓+自然日+常量写死 `3`/`0.93`（P0-2 + `paper_trading.py:57-59,322-325`）；
- 前端「战法回测」接口仍是 v1 旧逻辑（10日上限/0.95止损/目标价止盈，`app/strategies/backtest.py:37,177,232-247`）→ 同一页面与白名单重放口径打架，用户按页面回测验证会得出相反结论；
- `backtest_warfare_by_regime`（周报 regime 切片 + 准入矩阵数据源）不套 exit v2 也不套主力闸门（`app/backtest/strategies.py:365-371`）→ 高波白名单的后续调优依据是旧口径。
- 修法：见 §5 建议 2（常量单源）+ 前端回测接口接 `apply_exit_policy`。

**P1-9 ✅ 开盘确认推送绕过盘后推送的全部过滤**（`scheduler.py:919-950`）
盘后推送做了：白名单∩主力闸门∩置信度∩限量去重∩风险钩子拦截；次日 9:35 的 open_confirmation 只取「最近一次扫描」的结果直接推——不查信号日期（防御市/阴跌期旧信号反复推）、不查主力闸门（盘后被拦的高位票次日照样给买点指引）、不查风险钩子（趋势类暂停推送被绕过）、跨战法不去重。修法：补 scan_date==昨日 校验 + 复用盘后同一条过滤链（抽公共函数）。

**P1-10 白名单重放的主力闸门以 `exit_policy()=="v2"` 为前提**（`recommendation.py:130-136`）
运行时闸门只看 `STRATEGY_MAINFORCE_GATE`/`_mode()`，与退出策略无关。一旦回退 v1，重放样本集 ≠ 实际推送样本集，白名单统计静默失真（lowvol 脚本已把该耦合照抄固化）。修法：重放闸门改跟运行时同一开关。

**P1-11 ✅ 防御市在扫描层仍全禁且无记账**（`strategies/market_regime.py:521-524` + `scheduler.py:808-810`）
09-13 的「扫描/入场分档」只放开了阴跌闸门与高波白名单，base 类型不匹配（含防御市）在扫描层照样 `return []` 不落库。防御时段 strategy_results 永久断档，白名单重放永远评估不了"防御段该不该推"——与阴跌分档前的问题同构，且战法层没有 rejectedSignals 这样的记账结构。修法：分档原则补齐（防御市扫描层也放行落库），或明确接受断档并写入设计文档。

### 2.3 评分引擎（前后端/多出口一致性）

**P1-12 ✅ distribution ×0.85 惩罚实际只有 1/4 个面生效，且注释互相矛盾**
- `score_top`（实时榜）：只在**排序**上乘 mult（`routers/scoring.py:1174-1177`），返回的 `total_score` 仍是原始分；
- 详情页 `/score/{code}`：只挂 mainforce 标签，不动分（`scoring.py:953-966`）；
- 前端本地计算：**完全不消费 mult**（`frontend/src/composables/useFrontendScoring.js:598` 注释自认「后端保持 raw total 口径」——但 score_top 实际在排序上用了，注释与实现矛盾）；
- pack：`generate_backend_pack.py:193` 传 `regime=None` → pack 里 mult **恒 1.0**（overlay.py:117 `active` 判定不成立）。
- 结论：×0.85 出货惩罚目前只影响服务端实时榜的排序，用户在详情页/本地榜/精算榜看到的分数与顺序都不含它。这本身未必是 bug（可解读为「标签优先、调分保守」），但四处行为+两处注释需要对齐成一种明确语义。

**P1-13 ✅ 前端本地引擎没有 nb 换手钳制**（`frontend/src/utils/scoringEngine.js` 全文无对应逻辑）
nb 市高换手股：服务端资金面封顶 40，前端不封 → 同一只股服务端榜与本地计算分差可超 1 分，正好打在「榜单单一事实源差异 ≤1 分」的目标上。修法：前端补同款钳制（需要把当前 regime 传给前端，pack 里已有 regime 字段则直接用），或在本地计算 UI 明示「不含市况钳制」。

**P1-14 ✅ pack 生成与部分路径 regime=None**（`scripts/generate_backend_pack.py:193`；另 `ranking_history.auto_record_ranking` 裸 `ScoreEngine()`）
这些路径产出的分数用静态默认权重、无 nb 钳制。若 pack 携带预计算分，与线上榜口径漂移。修法：pack 生成时读当日 regime（日批里 `task_market_regime` 已先跑，顺序上可行）。

### 2.4 Coach（W1 刚上线，问题集中在口径）

**P1-15 ✅ 情绪熔断的「当日浮亏」用的是账户终身累计 realized_pnl**（`coach/rules.py:283-287`）
`(终身 realized + 当前浮亏) / 初始本金`——熔断跨日不重置、混入真实持仓浮盈亏。累计亏损 ≤-2% 后每天必触发（落库污染），真"当日暴跌 2%"反而可能因历史盈利不触发。修法：改当日已实现盈亏（当日平仓记录）+ 当日浮亏，按北京日重置。

**P1-16 ✅ 「持有满 3 日」用 `hd >= n` 且真实持仓以 created_at 近似买入日**（`rules.py:313-315,230-237`）
user_portfolio 存量真实持仓上线首日即满足条件 → **此后每天推一条**，几天内就会造成"警报免疫"，违背第一周降密度的上线纪律（dedupe 只按日去重，管不了跨日）。修法：改 `== n` 只推一次；真实持仓买入日缺失时跳过该规则。

**P1-17 ✅ 「放弃须填理由」只有后端接口，前端无任何 coach UI**（`routers/coach.py:44-45`；frontend 全目录无 coach 引用）
执行一致性 KPI（教练的核心度量）恒为空，W1 闭环断在最后一米。修法：W1 先降级——企微文案附"回复 1=执行 / 2=放弃+理由"走企微回调或简单表单；或明确本期只落库不闭环，写进周报口径。

### 2.5 Egress（第二梯队，P0-3 之外）

**P1-18 模块导入期执行 DDL → 每次进程启动触发 PostgREST schema 重载**（`scoring/kline_cache.py:67`、`indicator_cache.py:61`、`database.py:143-147` 的 `_DDL_DONE` 只是进程内去重；`mainline.py:129`、`ranking_history.py:92` 还有 ALTER TABLE）
egress_probe 的 diag0912 窗口里 timezone_names/类型内省三连 ×145 次即此指纹。预估 15-25MB/天，与数据访问无关。修法：DDL 集中到 lifespan 启动段执行一次（幂等表放 `_ensure_*` 且只在首次 API 调用时跑）。

**P1-19 进程启动无条件预热 system/performance，db 模式拉全历史 20-40MB/次**（`main.py:109-117` 不判 READ_ONLY；`performance.py:186` 与 `regime_review.py:130`、`backtest/strategies.py:236`、`backtest/run.py:411` 的 `_load_prices_map` 均无 start——commit 2ae2ad8 只修了 recommendation 一处）
Render 免费档每天至少重启 1 次 → 每天白付。修法：预热包 READ_ONLY 判断；其余调用点补 start 下推（同 2ae2ad8 手法）。

**P1-20 READ_ONLY 保留的 open_confirmation/daily_report 路径经 `get_push_whitelist` 触发 strategy_results 整表重读**（`scheduler.py:907,1644-1656`；`recommendation.py:242` 6h TTL 但首拉整表）
db 模式最高 50MB/天；pack 模式下 strategy_results 整表（6564B/行）仍走 Supabase。修法：白名单重算落库缓存（算完写一行 JSON，读端直读），或接 sync_meta。

**P1-21 包陈旧即整链回退 DB，kline 批量兜底单次 ~18MB**（`pack_source.py:354-381`、`kline_cache.py:251` IN ~1567 只 × 11493B/行；`scoring.py:433`、`scheduler.py:963`）
`_PACK_READY_HHMM=(22,0)` 已根治周一误判，残余风险在 DATA_SOURCE=db 实例或包下载失败（`_warn_once` 后**静默**用 DB）。修法：回退 DB 时在日报/企微输出显著告警（现只有一次性 print）。

## 5. 系统性优化建议（按优先级）

1. **regime 单一写者 + 细化态单源**（对应 P0-1、P1-1~6）：market_regime_history 当日只允许写一次（幂等）；对外只暴露细化后状态，`detect_market_regime` 废弃原始口径；闸门/评分/复盘/coach 全部走同一份。这是当前投入产出比最高的一组修复。
2. **口径常量单源化**（对应 P0-2、P1-8）：建 `backend/app/constants.py`（或复用 backtest/strategies.py 的常量）收拢 WARFARE_HOLD_DAYS/STOP_PCT/判据阈值，paper_trading、前端回测接口、regime 切片回测、剧本 review_date 全部引用；`_hold_days` 改交易日。否则"先回测再上线"的铁律会持续被口径漂移架空。
3. **×0.85 语义裁决 + 榜单单一事实源落地**（对应 P1-12/13）：三选一——A) 只做标签（回退 score_top 排序乘法，与前端注释一致）；B) 全面调分（详情页/live_ranking/前端/pack 全套 mult）；C) 维持现状但把四处行为写进文档。同时前端补 nb 钳制或 UI 明示差异。建议 A：改动最小、与「只挂标签不动分」的既有注释一致。
4. **egress 第二批治理**（对应 P0-3、P1-18~21）：优先级 = mainforce_state 缓存/列裁剪 → ranking_live 去 payload → DDL 收口到启动期 → 启动预热加 READ_ONLY 判断 → sync_meta 扩覆盖（mainforce_state/ranking_live/market_snapshot/strategy_results，机制已验证，只差接入）→ 白名单重算结果落库缓存。全部是读端小改动，预期把常态流量压回 50MB/天以下。
5. **部署意图自检**：把 §4 矩阵里 ⚠️ 两项（+ Render 应配 env 清单）做成启动自检——`/api/health` 或 daily_report 输出关键开关的**生效值**，与期望值不符即在企微告警。代码默认值兜底 ≠ 部署意图，这类漂移目前无任何可见性。
6. **测试基线补两类回归**：① 口径一致性（engine vs paper_trading 常量、后端 vs 前端锚点表、pack vs db 分数 parity——现有 `score_regression_check.py`/`verify_pack_score_parity.mjs` 纳入 nb 钳制与 mult）；② 时序类单测（同日双写、跨周末持有日、断档后 refine），这次 P0 两单都属于"单测全绿但集成时序错"。
