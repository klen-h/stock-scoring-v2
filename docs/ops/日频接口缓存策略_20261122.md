# 工作台日频接口缓存策略

> 用途：记录**哪些接口是日频的（当天不会变）、已被前端缓存**，以及**未来改成实时时必须同步改哪里**。
> 数据截至 **2026-11-22**。配套文档：`docs/ops/轮询清单_20261026.md`（有哪些轮询）、`EGRESS.md`（流量总账）。

---

## 0. 一句话结论

工作台切阶段（盘前/竞价/盘中/午盘/盘后/复盘）会跑 `loadPhaseData()`，
轮询又有 8 条定时器 —— 如果**不区分数据时效**，同一个日批接口一天会被打十几遍。
本项目历史上就是被这种"重复请求"把 Supabase egress 打爆过（5GB 配额跑到 16GB）。

**⇒ 日频接口一律走 `dayCache`，盘中会变的才允许重复请求。**

---

## 1. 机制

`frontend/src/utils/dayCache.js`：

```js
const _dayCache = {}                                  // { key: 'YYYY-MM-DD' }
const _dayCached = (key, day) => _dayCache[key] === day
const _dayMark = (key, day) => { _dayCache[key] = day }
```

三条纪律（沿用项目既有约定）：

| # | 纪律 | 原因 |
|---|---|---|
| ① | **键带日期** | 换日/回放自动失效，不需要手动清理 |
| ② | **只在有数据时标记** | 空结果若也标记，当天再也拉不到（日报 19:30 才生成，最典型） |
| ③ | **失败不标记** | 网络抖动只是这一次失败，不该锁死一整天 |

⚠️ `_dayCache` 是**内存对象** ⇒ 刷新页面即失效，这是刻意的
（宁可多拉一次，也不要让用户"刷新后看到旧数据还以为是新的"）。

## 2. 已缓存清单（★ 改实时时逐条对照）

| # | 缓存键 | 接口 | 调用点 | 为什么是日频 |
|---|---|---|---|---|
| 1 | `brief` | 盘前简报 | `useWorkbenchBrief.js` | 盘前一次性生成 |
| 2 | `report` | `getDailyReport` | `loadReport()` | 日报 19:30 生成；**空不缓存** |
| 3 | `amreview` | `getAmReview` | `loadAmReview()` | 11:32 落库；**无结论不缓存**（留给轻轮询补齐） |
| 4 | `reviewSummary` | `getCoachReviewSummary` | `loadReviewSummary()` | 三段复盘对账，盘后才更新 |
| 5 | `emotionReview` | `getEmotionReview` | `loadEmotionReview()` | 盘后对账；**有 items 才缓存** |
| 6 | `consistency` | `getCoachConsistency` | `loadConsistency()` | 历史命中率，按日聚合 |
| 7 | `calendar` | 财经日历 | `loadCalendar()` | 日历按日更新 |
| 8 | `cal_ahead` | `getCalendarAhead(3)` | `loadCalendarAhead()` | 未来 3 天静态事件 |
| 9 | `macroLocked` | 宏观早盘锁定快照 | `loadMacro()` | **早盘锁定**的定义就是"当天不再变" |
| 10 | `defboard_snapshot` | `getShadowDefensive(10)` | `loadDefTop()`（`useDefensiveBoard`） | 日批快照，15:40 后定稿 |
| 11 | `gate_watch` | `getGateWatch(80)` | `loadGateWatch()` | 读 `stock_facts_wide` 日批产物 |
| 12 | `riskwatch_daily` | `getCrowdingWatch` + `getAiBasketWatch` + `getJin10Tidy` | `loadRiskWatch()` | 见下方 §2.1 |

### 2.1 `riskwatch_daily` 是合并键（容易改错）

`loadRiskWatch()` 一次加载**五个块**，但时效不同：

| 块 | 时效 | 轮询时 |
|---|---|---|
| `crowd` 拥挤度 | **日频**（作者主动拒绝实时） | ❌ 不刷 |
| `aiBasket` AI 篮子 | 日批 | ❌ 不刷 |
| `jin10` 金十汇总 | 日批（当天 28 个外呼抓一次定稿） | ❌ 不刷 |
| `keyLv` 关键位 | **实时**（后端 2026-11-05 已轻量实时化） | ✅ 照刷 |
| `xmk`/`tell`/`copper` | 实时（宏观面板缓存） | ✅ 照刷（在 `loadRiskWatch` 之外单独判） |

⇒ 轮询走快路径：**只请求 `getKeyLevelWatch`**，其余三个当天只拉一次。

> `crowding_watch.py` 头注释的原话：盘中用未定稿的当日 bar 算出来的拥挤度
> 会随分钟跳动，**比"显示昨日"更容易误导**。
> 这不是"忘了实时"，是作者主动拒绝 —— 谁要改成实时，先推翻这条结论。

### 2.2 只缓存"骨架"、不缓存"价格"

有两条是**部分缓存**，改动时极易踩：

| 缓存键 | 缓存了什么 | **没缓存**什么 |
|---|---|---|
| `gate_watch` | 闸门候选名单 + 总览（日批） | `loadGwPrices()` 的**实时涨跌幅**（命中缓存时仍会刷） |
| `defboard_snapshot` | 防御影子榜快照（日批） | `loadDefLive()` 的**实时重排 + 涨跌幅**（本机精算，零后端 egress） |

⇒ 卡内"实时"语义不变，只是不再重复拉**当天固定的骨架**。

## 3. 刻意**不**缓存清单（盘中会变）

改这些为缓存 = **把实时数据冻住**，属于 bug：

| 接口 / 函数 | 为什么必须实时 |
|---|---|
| `loadPulse()` → `/market/pulse` | 5 块行情，60s 快组核心 |
| `loadIntradayLite()` | 实时涨停/炸板 + 成交额环比 |
| `loadOverview()` | 指数现价 |
| `loadTemperature()` / `loadEmotion()` | 市场温度、情绪快照随盘面走 |
| `loadSectorTop()` | 东财实时板块（后端 60s TTL） |
| `loadEvents()` | 事件涨家数占比随行情变 |
| `loadTop()` | 评分榜（盘中强制重算） |
| `loadTailReview()` | 尾盘承接 14:30 后每分钟都可能变 |
| `loadAmountShare()` / `loadAmountRt()` | 板块资金流动、成交额环比 |
| `loadGlobals()` | 外盘四件套（美股夜盘在走） |
| `loadCoach()` / `loadRadar()` | 新告警 / 持仓雷达含实时价 |
| `loadPush()` | 推送日志会新增 |
| `loadLimitReview()` | 涨停梯队盘中变化 |
| `loadRealtimeUplimit()` | 实时炸板 |
| `keyLv` | 见 §2.1，后端已实时化 |
| `xmk` / `tell` / `copper` / `evt` | 宏观面板缓存 + 实时行情维度 |

⚠️ 上面若有人加 `_dayCached`，**必须在本文档登记理由**，否则下次审查会被当成遗漏又改回去。

## 4. ★★ 把某个接口改成实时时的检查清单

> 用户的担心原话："如果未来改为实时可能会遗漏。"
> 下面五步**缺一步就会出问题**，改完请把本文档的对应行同步更新。

### 步骤 1｜删掉缓存判定，但**保留** `_dayMark` 的调用点注释

```js
// 改前
if (_dayCached('gate_watch', todayStr)) return
// 改后：直接删掉这一行；`_dayMark` 也一并删
```

⚠️ 只删 `_dayCached` 而留着 `_dayMark` 无害（没人读），但会误导后来者以为还有缓存 ⇒ **两个一起删**。

### 步骤 2｜确认它是否在 `loadPhaseData()` 里

```js
async function loadPhaseData(phase) { ... }
```

- 若在：改成实时后**必须加进合适的轮询组**，否则"只在切阶段时刷新"
  —— 这正是 2026-09-28 评分榜的坑（卡上写"实时"，实际停在进入阶段那一刻）。
- 若不在：确认有没有别的入口会周期性调它（否则永远不刷新）。

### 步骤 3｜选对轮询组，别乱放

| 组 | 间隔 | 放什么 |
|---|---|---|
| `FAST_SEC` 快组 | 60s | 读**后端内存缓存**的行情（零上游） |
| `POLL_SEC` 慢组 | 120s | 打**外部源**的（东财/外盘），或计算密集 |
| 观察器组 | 300s | 观察器里"盘中真会变"的块 |

⚠️ 把外部源接口塞进 60s 快组 = **外部请求翻倍**（红线）。

### 步骤 4｜检查后端是否有 TTL 缓存

前端去掉了缓存，后端若每次回源，外部请求会立刻翻几倍。
参考 `eastmoney._get_cached`（60s TTL）的做法。

### 步骤 5｜更新本文档 + 轮询清单

- 本文档 §2 删掉那一行
- 本文档 §3 加一行（写"为什么必须实时"）
- `docs/ops/轮询清单_20261026.md` 若新增了定时器，同步更新

## 6. 怎么验证缓存真的生效

```js
// 浏览器控制台（页面加载后）
// ① 看标记
Object.keys(window).length   // dayCache 是模块内变量，不挂 window
```

实操更简单 —— **看 Network 面板**：

1. 打开工作台 → 切到「盘中」→ 记下 `gate/watch`、`crowding-watch` 的请求次数
2. 切到「午盘」再切回「盘中」
3. **这两个接口的计数不应增加**（`key-level-watch` 会增加，它是实时的）

轮询场景：等 5 分钟，观察 `ai-basket` / `jin10/tidy` 不应新增请求。
