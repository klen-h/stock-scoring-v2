# 轮询清单（前端 19 个定时器 + 后端 16 个循环）

> 统计口径：**定时器周期性重复执行**才算轮询；一次性的 `setTimeout`、点击触发的请求不算。
> 时间一律 **北京时间（UTC+8）**；「盘中」= 周一至周五 9:30–11:30、13:00–15:00（前端另有竞价段 9:15–9:25）。
> 数据截至 **2026-10-26**，对应代码：`frontend/src/**`、`backend/app/**`。
> 术语说明：本文用「轮询」，代码注释里偶见的「轮训」为同义笔误（例：`Workbench.vue` 李大霄卡并入教练卡轮询）。

---

## 0. 结论先看

| 侧 | 数量 | 说明 |
|---|---|---|
| 前端定时器 | **17 个** | 16 个会发 HTTP；1 个纯本地倒计时（零请求）（2026-10-26：G3 19→18，G5 18→17） |
| 后端常驻循环 | **16 个** | 8 个可能打外部源，其余只读库/内存 |
| 最快 | **12 秒** | 关键标的快速报价（腾讯）、榜单退出提醒 |
| 最慢 | **6 小时** | 数据包（kline/pack）元数据巡检 |

**三条已落地的纪律**（新增轮询必须遵守，详见第 6 节）：

1. 交易时段 / 盘中阶段门控，休市一分钟都不发；
2. 页面在后台（`document.hidden`）不发；
3. 后端接口必须读**缓存或库**（60 秒级 TTL），不得每次回源。

## 4. 成本参考（实测，详见 `docs/EGRESS.md`）

| 项目 | 数值 |
|---|---|
| 20 只报价（`cached=1`） | 约 **1.6 KB**（gzip 0.57 KB） |
| 选股台盘中 60s 刷新（4 小时 / 天） | 约 **0.4 MB / 天**，腾讯外部请求 **0** |
| 整张宽表重拉（20 行 15 列） | 约 15.9 KB / 次（gzip 2.45 KB） |

⇒ 结论：**流量不是瓶颈**，真正要控制的是「外部请求次数」与「60s 级接口是否能承受页面开一整天」。

## 5. 页面一整天开着会发多少请求（估算）

| 页面 | 定时器 | 4 小时盘中估算 |
|---|---|---|
| 工作台 | 120s 主组 + 60s×3 + 300s + 120s + 30s(竞价) | 主组约 120 轮 × 约 12 接口 ≈ **1400 次**；另加 60s 组约 240×3 |
| 选股台 | 60s × 1 | **240 次**（每次 1.6KB） |
| 持仓 / 自选 | 12s + 30s | 12s ≈ **1200 次**，30s ≈ 480 次 |
| 评分榜 | 60s + 12s | 240 + **1200 次**（退出提醒） |
| 全局通知 | 60s | 240 次（仅在开启通知时） |

> 这些都是**同源轻接口**（1~2KB 级），不用太担心；但 12s 级（退出提醒 / 快报价）是真正的大头，
> 多标签页同时开会成倍增加 —— 若要优化，优先做「跨标签去重」。

## 6. 新增轮询前必须过的 5 条硬规矩

1. **时段门控**：必须有 `isTradingTime()` / `isLivePhase()` / `computePhase() === 'auction'` 之类判断，
   休市、午休、周末一律不发（`PROJECT_GUARDRAILS` 第 33 条的延伸）。
2. **后台不请求**：`document.hidden` 时直接 return。
3. **失败保留旧值**：不显示 `—`、不把缺失当 0（本项目踩过「涨0/跌0」误导）。
4. **后端不许回源**：60s 级接口必须读库/内存，必要时加进程内 TTL（参考 `/score/batch-prices?cached=1`）。
5. **统一入口**：工作台新增刷新项**必须加进 `POLL_SEC=120` 那一组**，否则盘中静默不更新（代码里已有同款注释）。
