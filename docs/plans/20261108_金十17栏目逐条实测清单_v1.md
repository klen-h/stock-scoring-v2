## 0. 四个与设计文档不一致的发现（**先看这个**）

### ① `50021`「俄乌冲突最新24小时局势跟踪」是**陈旧数据**

```

其余 16 栏          = 2026-11-06T00:00:00.000Z

**⇒ 这一栏在容器里基本不更新（停留在 10-18 的旧快照）。**

### ② `50032` 与 `50016` **标题相同但不是同源重复**

```
50016  data_id=60168  2026-11-06  意大利燃气电厂 / 俄炼厂遇袭 / 印度储能…
50032  data_id=60114  2026-11-03  西方石油CEO / 特朗普油价 / 阿联酋能源…

设计文档写「两者标题完全相同，按 title 去重」——

## 2. 实现层必须加的三道闸（本次实测得出的硬约束）

设计文档没写这三条，不加会出事故：

### 闸 1 · `display_time` 新鲜度校验（**P0，必须**）

```python
# 逐栏判定，不是整包判定
if (基准日 - parse(display_time)).days > 1:
    skip(该栏)          # 记日志，不报错
```

**理由**：`50021` 停在 10-18、`50032` 停在 11-03，而整包仍然 HTTP 200。
**只看状态码永远发现不了**，只能看每栏自己的 `display_time`。

### 闸 2 · **不要按 title 去重**，按 `display_time` 取最新

`50016` / `50032` 标题完全相同但期次不同（11-06 vs 11-03）。
按 title 去重等于掷硬币，可能留下旧的。

### 闸 3 · 相对时间词与陈旧数据互斥

凡出现「下周」「昨日」「今天」等词，**必须**确认 `display_time` 新鲜，
否则会写出「3 周前的下周将举行会谈」这类错误晨报。

import json, urllib.request

    x = c["data"]

## 5. 结论

1. **设计文档的 17 栏清单是栏目层的**（ID + 标题），本文补齐了**内容层**。
2. **不能直接照设计文档的白名单实现** —— 2 栏陈旧、1 栏命名误导、1 栏重复标题、
   2 栏价值被低估。
3. **最关键的一条**：整包 HTTP 200 ≠ 每栏新鲜。**必须逐栏校验 `display_time`**，
   否则会把 3 周前的"下周"写进今天的晨报。
4. 这批数据是**单日单次快照**，栏目更新频率尚不清楚。
   `50021`/`50032` 停了 19 天/3 天可能只是"该栏目低频"，
   建议**连续观察 3 个工作日**再最终冻结白名单（本清单 v1.0 的先验判定已足够开工）。

## 6. 变更记录

### v1.1 · 2026-11-08（扩栏落地，`46f1d221`）

**决策**：采用**方案 A** —— 扩 `jin10_tidy._TARGETS`，不新建预览接口链路。

#### 6.1 落地方式的根本改变（**本文最重要的修正**）

初版（v1.0）与设计文档都默认「要补这些栏目 ⇒ 必须接**行业动态预览**接口」。
**实测推翻了这个前提**：`jin10_tidy` 用的 tidy-news 接口**支持任意 `category_id`**。

```
GET /api/tidy-news/details?category_id=50022&date=2026-11-06
  → 昨日今晨  contents=19  items=17
GET /api/tidy-news/details?category_id=50023&date=2026-11-06
  → 欧美汇总  contents=16  items=14
相对：预览接口同栏目只有 6 条头条
```

**⇒ 两条链路的能力对比（这才是选型依据）**：

| 维度 | 预览接口（`/home/item`） | tidy 接口（`/tidy-news/details`） |
|---|---|---|
| 内容量 | 每栏 **6 条头条** | 每栏 **8~17 条全文** |
| 请求数 | 1 次拿 17 栏 | 每次 1 栏 1 天 |
| token | **免 token** | 需 `x-token`（会过期） |
| 历史回补 | **不能**（只有最新一期） | 能（`date=` 任意日） |
| 陈旧数据风险 | **有**（50021 停 10-18 却照常返回） | **无**（请求哪天返回哪天，没有就是 null） |

**⇒ 补政策缺口这件事，tidy 全面优于预览**（内容更全、可回补、无陈旧问题），
唯一劣势是需要 token。而 token 本来就是既有依赖，**不新增风险面**。

预览接口剩下的唯一价值：**token 失效时的免 token 备用通道**（暂不接，见 §6.4）。

#### 6.3 请求数控制：按日期分档

不能 7 天 × 6 栏全抓（42 请求/天，比原 28 涨 50%）。

| 日期范围 | 抓取栏目 | 请求数 |
|---|---|---|
| 最近 `_HOT_DAYS`(2) 天 | 全部 6 栏 | 2 × 6 = 12 |
| 更早的 5 天 | 仅 `_CORE_TARGETS` 4 栏 | 5 × 4 = 20 |
| **合计（日常 `days=7`）** | | **32**（原 28，仅 +4） |
| 显式传 `day=`（人工补历史） | 该范围内每天全 6 栏 | `days × 6` |

**理由**：7 天窗口是为防假期漏抓（见模块头 2026-11-04 记录），
但**政策定调只需要最近一两天的**；更早的日期求"不漏"不求"全"。

#### 6.5 ⚠️ 走 tidy 路径后，§2 的「三道闸」**不再适用**

这是很容易留下矛盾的地方，特此说明：

| 闸 | 针对的问题 | 走 tidy 后 |
|---|---|---|
| 闸 1 · `display_time` 新鲜度校验 | 预览接口把 10-18 的旧栏混在 11-06 的包里返回 | **不适用** —— tidy 按 `category_id + date` 取，没有该日数据返回 `null`，天然不会给陈旧内容 |
| 闸 2 · 不按 title 去重 | 预览接口里 50016/50032 同名不同期 | **不适用** —— tidy 按栏目 ID 取，不存在同名冲突 |
| 闸 3 · 相对时间词互斥 | 陈旧数据里的"下周" | **不适用** —— 前提（数据陈旧）已不存在 |

**⇒ §2 保留作历史记录**，它是「如果将来改用预览接口」时的必读约束
（比如 §6.1 说的"token 失效备用通道"真要接的话，这三条必须一起做）。
**当前实现的 tidy 路径不需要它们。**
