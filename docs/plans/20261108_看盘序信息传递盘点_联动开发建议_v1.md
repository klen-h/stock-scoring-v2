# 看盘序信息传递盘点与联动开发建议（2026-11-08）v1.0

> **缘起**：用户要求"整合盘前、竞价等 tab 之间的信息传递，看看是否存在信息传递功能可开发"。
> **方法**：7 阶段 × 产出/消费矩阵 → 已有机制盘点 → 断点分析 → 可开发项分档。
> **红线预览**：本文全部建议均为**观察/展示层**；任何"竞价/盘中数据反过来影响决策"的
> 路径一律划入"明确不做/需预登记"（R2：这些数据没有任何检验结论）。
> **一句话结论**：链路的**骨架已成型**（预判→对账、计划→执行、基线→收盘都落了库），
> 但阶段间的**读取大多是断的**——上游产出都在库里，下游不读。断点 7 处，其中
> **A2 / A3 / A4 三处是低成本纯展示接线**（数据现成）；
> **A1 例外**：`tomorrow_watch` 未结构化落库，须先补落库（详见 **§0.1**），
> 且其上游产出在 11-02~11-06 曾中断（**§0.2**，已修，待 11-10 确认）。

## 0. 事实核验与前置条件（2026-11-08 复核，**实现前先读这节**）

> 本节是对原始盘点的**订正**。撰写时有几处基于静态阅读的推断，
> 经库表与代码实测后需要修正。**凡本节与下文正文冲突，以本节为准。**

### 0.1 `daily_reports` 没有结构化字段（直接影响 A1）

实测表结构**只有三列**：

```
daily_reports(date TEXT, markdown TEXT, created_at TEXT)
```

`tomorrow_watch` 是 `daily_report.py:1109` 调 `llm._call_json()` 得到的 **JSON 字段**，
但代码只把它**渲染进 markdown 正文**（`daily_report.py:1065-1069`），
**从未单独落库**。

⇒ **A1 不能"读现成字段"**。必须先补落库，二选一：

- **（推荐）** 在 `_llm_interpret()` 里把 `data` upsert 到一张新表
  （如 `daily_report_json(date, payload_json, created_at)`），
  落库点就在日报生成路径上，一行 `db.upsert`；
  下游可直接读结构化字段，`holdings.key_level` 之类也能复用。
- （不推荐）从 `markdown` 正则提取 —— 格式一改就断，且嵌套结构难还原。

### 0.2 `tomorrow_watch` 在 2026-11-02~11-06 **压根没产出**（D1 之前还有一层断点）

近 15 条日报实测：含"明日预案与持仓观察"段的仅 **8/15**，
且 **2026-11-02 起连续 5 个交易日全无**：

| 日期 | markdown 长度 | 含明日段 |
|---|---|---|
| 2026-11-06 | 4217 | ✗ |
| 2026-11-05 | 3852 | ✗ |
| 2026-11-04 | 4311 | ✗ |
| 2026-11-03 | 4113 | ✗ |
| 2026-11-02 | 4154 | ✗ |
| 2026-10-30 | 4178 | ✗ |
| **2026-10-29** | **5507** | **✓ 最后一次** |

**机制**：`_call_json` 解析失败 ⇒ `data={}` ⇒ 降级到 `_llm_interpret_markdown()`
纯 Markdown 兜底，**该分支根本没有 `tomorrow_watch`**。
（对照：11-06 那条连"明日预案与持仓观察"标题都不存在，10-29 存在
⇒ 一个走兜底、一个走结构化。）

**根因**：11 月起使用 GLM 5.2（thinking 模型），`max_tokens=8192` 被推理 token 吃掉
⇒ JSON 尾部截断 ⇒ 解析失败。**已于 2026-11-07 修复**
（`flash/llm.py` 改为 `thinking:{"type":"disabled"}` + `reasoning_effort:"none"`）。

**验证状态（2026-11-08）**：手动复现 `_call_json`（以 11-06 的 markdown 作输入）
⇒ **14.3 秒返回完整 6 字段 JSON，`tomorrow_watch` 5 条** ✓
⇒ 但**真实日批尚未验证，须等 2026-11-10（周一）**。

## 2. 已存在的信息传递机制盘点（12 条）

| # | 机制 | 方向 | 载体 | 自动化程度 | 证据 |
|---|---|---|---|---|---|
| 1 | 盘前决策卡（做不做/做什么/做多少/错了怎么办） | 昨夜数据 → 盘前计划 | `GET /system/workbench-decision-card`，规则聚合 | 全自动 | `trader_brief.py:1025` |
| 2 | **"回看盘前决策卡"链接** | 竞价 → 盘前 | 页内跳转 | 手动点击 | `Workbench.vue` 竞价卡脚注 |
| 3 | **竞价面板"昨日日报联动"**（11-08 新增） | 昨日日报 → 竞价 | 关键位/预期区间 vs 开盘 + 板块联动 + LLM | 全自动（进 phase 即拉） | `auction_panel.py` |
| 4 | **情绪对账**：盘前预判 → 盘后实际 | 盘前 → 复盘 | `emotion-review` 30 天表 | 全自动 | `market.py:1301/1336` |
| 5 | 早盘定稿 `am_*` → 早盘复盘页 | 早盘 → 午休 | 11:30-11:40 一次性落库（幂等） | 全自动 | `market.py:1004` |
| 6 | 尾盘承接：14:30 基线 → 收盘 | 盘中 → 复盘 | `tail-review` | 全自动 | `market.py:1546` |
| 7 | 三段复盘（盘前/午休/盘后 LLM）+ 企微推送 | 各段 → 人（跨天阅读） | `run_review` + 推送 | 定时自动 | `flash/scheduler` |
| 8 | 事件 T-N 提示（FOMC/选举等） | 日历 → 竞价/观察器 | `EVENTS` + `event_alert` 文字提示 | 全自动（只提示） | `scenario_watch.py` |
| 9 | 财经日历 T-N → 盘前 | 日历 → 盘前 | `calendar_ahead` | 全自动 | `flash/calendar_ahead.py` |
| 10 | 矛盾验证闭环 T+1 | 当日观点 → 次日验证 | `contradictions validator` | 日批自动 | `contradictions/validator.py` |
| 11 | 日报"明日预案与持仓观察" | 盘后 → 次日 | LLM 段落 + `tomorrow_watch` 结构化 | **产出自动、消费无** | `daily_report.py:1066/1102` |
| 12 | 输出消费标记（👍/👎） | 各卡 → 周复盘 | `output_feedback` | 手动二选一 | `InsightBody`（C2） |

## 3. 断点分析（7 处，按疼痛程度排序）

| # | 断点 | 后果 | 接线成本 |
|---|---|---|---|
| **D1** | 日报 `tomorrow_watch`（3-5 条明日观察指标）**产出后无人消费**；且 2026-11-02~11-06 **产出本身也断了**（原因见 §0.2） | 昨天收盘后系统最值钱的一段前瞻输出，第二天早上不见了 | **低**：须先让 `data` 结构化落库（当前只有 markdown），再读出来展示 |
| **D2** | 竞价定稿（verdict/量比/板块强弱）**不进早盘页** | 9:25 定稿的判断在 9:30 最需要它的时刻消失；早盘页看不到"开局是强是弱" | **低**：面板数据现成，早盘 phase 加一张只读摘要卡 |
| **D3** | 盘前决策卡的候选 Top3/关注池 **不与竞价实际对照** | 计划做完了，开盘后"我关注的票竞价如何"要自己肉眼对 | **低**：决策卡候选 codes × 竞价 gaps 一次 join |
| **D4** | 盘前计划（档位/候选）**不进早盘复盘对照** | 午休复盘"上午做得如何"缺"上午计划是什么"那一列 | 低 |
| **D5** | `auction_*` 历史**只落库不回测**（09-25 评估缺口①） | "竞价强度 → 当日走势"永远停在经验阈值 | 数据在积累，回测须预登记 |
| **D6** | 推演区间位置（强于/弱于预期，11-08 新增）**不进对账体系** | "预期区间"只有当天看的价值，没有对账价值 | 按日落库一行即可攒样本 |
| **D7** | 提示通道分散（浏览器通知/企微/各卡内提示） | 跨阶段信息靠人记得去看 | 收件箱属于大工程，暂缓 |

## 5. 建议排序

```
【前置】2026-11-10 日批后确认日报重新出现"明日预案与持仓观察"段（§0.4）
→ A1a  tomorrow_watch 结构化落库（新表 + upsert，见 §0.1）   ← 新增，A1 的前提
→ A1b  决策卡 / 竞价面板读取展示（原 A1 的展示部分）
→ A2（竞价定稿进早盘，补最粗断点 D2）
→ A3（计划偏离对照，盘前↔竞价成环）
→ A4（早盘复盘两列，计划↔执行成环）
→ B2 顺手落库攒样本
→ B1 等样本 ≥20 交易日后预登记
```

⚠️ **A1 与原文的差别**：拆成 a（落库）/ b（展示）两步。
a 要改日报写入路径、需回归测试；b 才是原文描述的"纯展示接线"。
**省掉 a 直接做 b ⇒ UI 做好了但数据永远为空**（本项目刚踩过同类坑：
竞价面板的空响应被前端本地缓存永久钉住，看起来"做完了"其实没通）。

> **设计原则**（贯穿 A 档）：传递的是**事实与对照**，不是**结论与指令**——
> 每一处接线都保持"上游产出什么就显示什么 + 口径日期如实标注"，
> 不做二次解读（解读已有专门装置：规则判读 / LLM 解读 / 对账账本）。

4. **不得为了接线去改前端本地缓存策略**（`frontend/.env.development` 的 `VITE_LOCAL_CACHE=1`）：
   那是用户为省流量/省后端重算有意开启的。遇到"空值被缓存住"，
   正确处理是控制台 `clearApiCache()`，**不是**禁用缓存。
5. **B 档一律先预登记判据再跑数**，判据未冻结不得出结论、不得据此改任何决策链。
6. **新增的读取一律走既有库表**，不得为此新增外部行情请求（本地开发对流量敏感）。
