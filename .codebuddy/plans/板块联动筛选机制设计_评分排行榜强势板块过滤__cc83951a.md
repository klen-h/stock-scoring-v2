## 产品概述
为评分排行榜新增「板块联动筛选」机制：系统每日先评估各行业板块走势、识别强势板块，排行榜仅允许强势板块内的个股参与排名，非强势板块个股被排除（由强势板块内次高分递补，保持 Top50 满员）。目标是改善评分榜胜率回查（现状：预登记检验 FAIL，Top50 T+5 跑输可取价池 −1.43pt）。

## 核心功能
- **板块走势评估**：按 `stock_industry.main_industry`（新浪 49 行业，唯一可与个股关联的 taxonomy）用个股收盘价等权聚合出自建行业指数，5 日累计涨幅做相对分位判定强势板块（前 30% 且为正）。
- **板块-个股关联**：`industry_map.get_industry_map()` 精确匹配；映射缺失个股如实披露数量，不静默。
- **排除逻辑**：排序后、落库/返回前加「排名资格过滤层」，不动评分本身、不动详情页。
- **边界处理**：无强势板块/数据缺失/序列不足 ⇒ 过滤失效放行并打标（fail-open，缺失≠满足）；普涨日（行业选择无增量，E2 结论）过滤降级。
- **影响控制**：`ranking_history` 原版记录**一字不动**（mainline/观察池等下游零影响），过滤版平行落库供 A/B 回查；`SECTOR_LINKAGE_MODE=off|shadow|on` 三态开关，默认影子模式。
- **预登记纪律**（项目红线）：判据先冻结 → 历史回放 → 影子并行 → 前瞻样本复判，全程禁止用回查结果反推板块强度参数；已有反面证据（行业动量无预测力、板块动量因子 INSUFFICIENT）如实披露，机制必须允许被证伪。


## 技术方案

### 一、板块走势评估：自建行业指数（方案 A，推荐）
**不采用** zzshare `plate_daily_zz` 板块指数直连（104 粗分与新浪 49 行业仅 4 个同名，taxonomy 断裂，强行匹配会产出误导性结果）；也**不采用**人工维护映射表（维护成本+错配风险）。

- **行业维度**：`stock_industry.main_industry`（49 类），个股关联走 `app/industry_map.py::get_industry_map()`（2026-10-19 刚收拢的共享 1h 缓存，零新增 egress）。
- **指数构造**：行业等权日收益 = 行业内成分股日涨跌幅均值（当日无价个股剔出分母，**缺失≠0**），复利累计 5 日得 `ret5`。
- **价源**：生产用 `backtest_prices`（989 只池、日批更新，与回查价源同源、口径自洽，诚实标注池偏差）；长历史回放用本机 `data/zzshare_daily.db`（6123 只 / 2005 起 / 零 egress）+ `_code_industry` 映射，**可回测 21 年**——这是自建指数的决定性优势（zzshare plate 序列只有 2026-08-21 起约 40 个交易日）。
- **强势判定（v1.0 草案，冻结后不可改）**：
  - `ret5 > 0` 且 分位进入前 30%（约 Top 15/49）⇒ 强势板块；
  - 噪声板块：成分股 < 5 只的行业不参评；
  - 普涨日守卫：连续 3 日全市场上涨家数占比 ≥ 70% ⇒ 当日过滤降级为放行（E2 期实证“普涨非轮动、行业选择无增量”）；
  - 无强势板块日（普跌/判据不满足）⇒ 放行 + 打标 `filter_inactive`，**不产出空榜**（下游 trader_brief/观察池依赖 Top50，断粮代价大于过滤收益）。

### 二、预计算与存储（egress 纪律）
- 新模块 `backend/app/sector_strength.py`：日批任务 `task_sector_strength` 每晚预计算，落表 `sector_strength_daily`，盘中/榜单路径**只读不重算**（板块序列一天只变一次，参照 `sector_momentum._load` 的 5 分钟缓存模式）。
- 批量取价用 `load_bars_bulk()`（`ROW_NUMBER() OVER (PARTITION BY code)` 一次窗口取全池最近 N 根，2026-10-18 已验证 178s→6.4s 的既有范式），**禁止 989 次逐只往返**。
- 表结构（双库兼容，数值列 TEXT，参照 `sector_amount_daily` 幂等建表范式）：
```sql
CREATE TABLE IF NOT EXISTS sector_strength_daily (
    date TEXT, industry TEXT,
    ret5 TEXT, ret10 TEXT, rank_pos INTEGER,
    is_strong INTEGER, member_n INTEGER,
    market_up_ratio TEXT, filter_active INTEGER,   -- 普涨守卫/空强势 ⇒ 0
    reason TEXT, created_at TEXT,
    PRIMARY KEY (date, industry)
)
```

### 三、排行榜接入：排名资格过滤层（影子优先）
- 位置：`routers/scoring.py` 三路（`/score/batch/top` 精算、`task_score_snapshot` 快照、调度器兜底）在**排序完成后**应用过滤：从全量排序中按序取强势板块内前 50 递补满员，返回结构附 `sector_filter: {active, strong_n, excluded_n, backfilled_n, unavailable_reason}`。
- **不动**：`score_single` 详情页、评分引擎、`_pool_quality_filter`（质量过滤语义不混入板块语义）。
- 落库：`ranking_history` **原版照旧**（mainline 行业扎堆、观察池、既有回查零影响）；新增平行表 `ranking_history_sector`（同结构）同步写过滤版，供回查双版本对照。
- 开关：`SECTOR_LINKAGE_MODE=off|shadow|on`，登记进 `app/env_check.py` 期望值表（防“代码默认≠部署意图”静默分叉）；shadow = 只算+平行落库+前端只读对照，前端榜单仍展示原版。
- 前端对齐：`useFrontendScoring.js` 本地榜在 on 模式下同步过滤（复用 `/api/score/sector-strength` 下发的强势板块清单，避免两套口径漂移——项目纪律“同一数据两处渲染=必然漂移”）；`ScoreRank.vue` / 工作台加一行定位说明 + 被排除数量披露。

### 四、验证链路（预登记，顺序不可颠倒）
1. **冻结判据** → `PLAN_SECTOR_LINKAGE.md` v1.0（参数、边界、降级规则、GO/KILL 线一次性写死；**冻结前只看数据可用性、绝不看回查结果**）。
2. **历史回放 A**（判据本身的预测力）：zzshare_daily 21 年自建行业指数，“当期强势板块未来 5/10 日等权超额 vs 全市场”，配对聚类 bootstrap + 分年分解（策略上线三重检验铁律）。
3. **历史回放 B**（快照 A/B 对照）：31 个既有快照日模拟过滤版 Top50 vs 原版 Top50，T+5/T+10 vs 可取价池，复用 `score_edge_check` 引擎口径；样本仅 31 日 ⇒ 标注检验力有限，结论以前瞻影子样本（≥20 快照日）为准。
4. GO/KILL 预冻结：过滤版超额 − 原版超额，T+5 配对 95%CI 下界 > 0 且 ≥ +1.0pt ⇒ GO；CI 上界 < 0 ⇒ KILL（判据双条件，参照 `flow_consec` 教训）。
5. 注册 `app/edge_verify.SCRIPTS` 月度复检（脚本支持 `--json`）；GO 且用户拍板才切 `on`。
- 诚实披露：已有反面证据（E2 期“行业动量无预测力”、`sector_momentum_edge_check` INSUFFICIENT）写进 PLAN 文档，机制可能被证伪，KILL 则 `SECTOR_LINKAGE_MODE` 定案 off。
