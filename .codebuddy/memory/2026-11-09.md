## ★★ 生产启动崩溃事故（`d343cf54` → 修复 `ffcfa323` / main 上 `d019867a`）

### 现象

```
[deploy] 重启服务 stock-scoring
[deploy] ❌ 健康检查 40 秒未通过：http://127.0.0.1:8000/api/health
   Active: active (running) ... 2s ago     ← systemd 显示 running，其实在反复重启
   ⚠ 没有进程监听 8000
   curl: (7) Failed to connect ... Connection refused
Nov 08 23:53:22 uvicorn[127915]: NameError: name 'etf_quote_loop' is not defined
Nov 08 23:53:22 uvicorn[127915]: ERROR: Application startup failed. Exiting.
```

### 根因

`d343cf54 feat(monitor): ETF实时热度榜上线（方案B）` 在
`backend/app/flash/scheduler.py` 的 `start()` 里写了：

```python
asyncio.create_task(etf_quote_loop()),
```

但**从没导入** `etf_quote_loop`（定义在 `app/etf_board.py`）。
`scheduler.start()` 由 `app/main.py` 的 **lifespan** 调用 ⇒ startup 抛 NameError
⇒ uvicorn 退出 ⇒ 8000 无监听 ⇒ 健康检查 40s 超时 ⇒ 部署失败。

**为什么之前没炸**：那个提交之后一直没成功部署过（CI 也在挂）。

### 为什么原有 CI 三道检查全部漏掉

| 检查 | 漏掉的原因 |
|---|---|
| `compileall` | 只查**语法**。NameError 语法完全合法 |
| `import app.main` | 只执行**模块级**代码；`scheduler.start()` 在 lifespan 里，import 时根本不跑 |
| `python scripts/code_hygiene_check.py` | 查的是代码卫生口径，不查名字解析 |

**⇒ 教训：`import app.main` 不等于"应用能启动"。**
lifespan/startup 是一整块独立的执行面，必须单独覆盖。

### 修复（2 处代码）

1. `scheduler.py` `start()` 内补延迟导入（与同处 `coach_loop` 同款）：
   `from app.etf_board import etf_quote_loop`
2. **pyflakes 顺带查出第二个同类问题**：`scheduler.py:296` 的 `health_loop`
   用了 `time.strftime` / `time.gmtime`，但**模块级没 `import time`**。
   那条分支只在腾讯快照缺 `data_date` 时才走（有就短路），所以一直没炸，
   但一旦触发会 `NameError`，且被 `try/except Exception` 吞掉
   ⇒ **行情陈旧巡检静默失效**。已补 `import time`。

### CI 三道新闸（`.github/workflows/ci.yml` + `requirements-dev.txt`）

1. **pyflakes `undefined name`**（只拦这一类，避免存量噪音）
   —— 抓「根本没 import」（本次 `etf_quote_loop`、`time` 的形态）。
2. **`scripts/smoke_scheduler_imports.py`**（新）
   静态收集 `scheduler.py` 里全部 `from app... import X`（**128 个名字 / 56 模块**），
   逐个真 `import_module` + `hasattr` 验证，抓「模块路径写错 / 模块里没这个名字」。
   - 坑：`from app.flash import service` 是**导入子模块**，子模块未加载时
     `hasattr` 为 False ⇒ 需再试探 `import_module("app.flash.service")`，否则 13 个误报。
   - 不跑 lifespan、不连库、不外呼 ⇒ CI 秒级、无副作用。
3. 保留原 `import app.main`（抓 ImportError / 循环导入）。

**三者合起来**覆盖 startup 期的 `NameError` + `ImportError`。

## ★★ 坑：并行会话切了分支，`git push origin main` 静默"成功"却什么都没推

修完提交后 `git push origin main` 返回 **"Everything up-to-date"**，
但 `git rev-list --count origin/main..HEAD` 显示 `AHEAD=3`。

**根因**：另一个会话在期间执行了 `git checkout -b fix/audit-20261109`，
**同一个工作目录** ⇒ 我后续所有 git 操作都落在新分支上。
`git push origin main` 推的是**本地 main 分支**（仍停在 `5164e342`），所以 up-to-date；
而我的提交 `ffcfa323` 在 `fix/audit-20261109` 上，**根本没到 main**。

**查法**（`push` 的返回不可信时）：
```bash
git branch --show-current          # ← 必查
git -c core.sshCommand="..." ls-remote origin refs/heads/main   # 远程真实 HEAD
git rev-parse HEAD ; git rev-parse main
```

**修法**（不打断并行会话的工作区）：用独立 worktree 只 cherry-pick 我那一个 commit
```bash
git worktree add D:/stock-scoring/_wt_main main
cd .../_wt_main
git cherry-pick ffcfa323          # 只取该 commit 的 4 文件 diff
git push origin main              # 5164e342..d019867a
git worktree remove ... --force
```
⇒ 远程 main = `d019867a`，只含我的 4 个文件，未把并行会话的其它提交带上线。

**★ 纪律**：多会话共享同一工作区时，**每次 push 前先看 `git branch --show-current`**；
`AHEAD>0` 且 push 说 up-to-date ⇒ 九成是推错分支/推错 refspec，别当成"已经好了"。
