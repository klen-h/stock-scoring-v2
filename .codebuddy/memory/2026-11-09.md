## ★★★ 生产启动崩溃的**真根因**（`6a86aae2`）—— 前面只修了 import，没修函数本身

### 上一轮修复不完整

上轮只补了 `from app.etf_board import etf_quote_loop`（解决 NameError），
但**没发现 `etf_quote_loop` 根本不是 async 函数**。

### 真根因

```python
# etf_board.py（d343cf54 引入时就是 sync）
def etf_quote_loop():
    while True:
        ...
        time.sleep(60)

# scheduler.py
asyncio.create_task(etf_quote_loop())   # ← 灾难
```

`asyncio.create_task(X())` **先同步求值参数** `X()` ⇒ `etf_quote_loop()` 直接进入
`while True` 死循环（`time.sleep(60)` 同步阻塞）⇒ **永不返回** ⇒
`scheduler.start()` 卡死在构造 tasks 列表（第 2686 行）。

**生产表现**（两种，取决于时序）：
- 卡住 → systemd `TimeoutStopSec` 90s 后 SIGKILL（`code=killed, status=9/KILL`）
- uvicorn 判 startup 失败 → `sys.exit(3)`（`code=exited, status=3/NOTIMPLEMENTED`）

**定位锚点**：`[scheduler] 重启恢复市场状态` 之后**永远看不到 `[scheduler] 已启动:` 这行**。
那行是 `start()` 里 tasks 构造完成后的摘要打印，看不到 = 卡在 tasks 构造。

### 为什么三轮检查全漏

| 检查 | 抓不到的原因 |
|---|---|
| `import app.main` | 不执行 lifespan |
| pyflakes | `etf_quote_loop` 已 import，无 undefined name |
| `smoke_scheduler_imports`（旧版） | 只查 `from X import Y` 可解析，**不查 Y 是不是 async** |

### 修复

1. `etf_quote_loop` 改 `async def`：`time.sleep(60)` → `await asyncio.sleep(60)`，
   同步的 `refresh_once()` → `await asyncio.to_thread(refresh_once)`。
2. `smoke_scheduler_imports.py` **新增第三条检查**：收集 scheduler.py 里所有
   `asyncio.create_task(NAME(...))` 与 `*_heavy(NAME)` 的 NAME，逐一
   `asyncio.iscoroutinefunction` 验证。

**实现坑**：`etf_quote_loop` / `coach_loop` 是 `start()` 里的**局部延迟导入名**，
`getattr(scheduler, name)` 找不到 ⇒ 要回到 `from X import Y` 的 `X.Y` 去 getattr；
`loop_fn` 是 `_heavy` 形参要跳过。

### 验证

```
asyncio.iscoroutinefunction(etf_quote_loop) = True
scheduler.start() 完整跑通：SCHEDULER_START_OK tasks=30（打印出 [scheduler] 已启动）
冒烟：延迟导入 128/56 ✓ + create_task/_heavy 全部 async ✓
卫生门 ✓  pyflakes ✓  pytest 134 passed ✓
推送 8a0dcdc0..6a86aae2 main -> main
```

**★ 教训（本轮最大）**：**"名字能 import" ≠ "能放进 create_task"**。
同步函数（尤其 `while True: time.sleep` 循环）放进 `asyncio.create_task` 会
**同步死循环卡死事件循环**，且**没有任何异常**（死循环不返回，不抛 TypeError）。
这类 bug 只有 `iscoroutinefunction` 或真实启动能抓。

## ★★ 李大霄视角「有更新却没更新」根因（`992e6db1`）—— 一条脏数据毁掉整张卡

### 现象（用户报）

```

```
但卡内 tab 明明列着 `11-07 20:54` / `11-07 17:35`…

### 根因：**一行脏数据 + 字符串排序**

库里 536 条中有 **1 条**：
```
date = '未知'      ← 不是日期
bvid = 'unknown'
title = '小书为什么不涨价'
```

`ORDER BY date DESC` 是**字符串排序**，而 **`'未知'` 的 Unicode 码位远大于 `'2026-…'`**
⇒ 这行被排到**第一位** ⇒ `latest = rows[0]` 就是它 ⇒

1. `_lag_days('未知')` → `strptime` 抛 ValueError → 返回 **None** → 前端显示 `· —天前`
2. `date` 渲染成 `'未知'` → 显示"日期为—"；`bvid='unknown'` → 拼出
   `bilibili.com/video/unknown` 死链 + 显示"unknown"
3. **`items[0]` 也是它** ⇒ `lidxSel=0` 默认选中它 ⇒
   **真正最新的 `11-07 20:54` 被挤到第二位，用户以为"没更新"**

**⇒ 与"字符串排序把 10 月排到 9 月前面"是同型问题（本项目已踩多次）。**

### 三层修复

1. **入库**（`_slim`）：date 必须匹配 `^\d{4}-\d{2}-\d{2}`（原来只判"非空"，`'未知'` 能过）；
   `bvid` 经 `_clean_bvid()` 过滤 `unknown/未知/none/null/-/—` 等占位词 → None。
2. **读取**（`load` / `_latest_meta` / `_latest_date`）：统一加 `_DATE_OK` 过滤，
   历史脏行即使还在库里也不许参与排序。
3. **补 `import re`**（我新写的正则用了 `re`，但文件没导入 —— **pyflakes 会抓，但我是先写完才跑**）。

### ★ 双库兼容坑（把我坑了，单测直接 4 红）

`_DATE_OK` 不能这么写：

| 写法 | 结果 |
|---|---|
| `LIKE '2%'` | ✗ `%` 被 psycopg2 当占位符 → `IndexError: tuple index out of range` |

| `SUBSTR(date,1,1)='2'` | ✓ SQLite 与 PG **都内置**，且首字符能区分 `'未知'`（中文） |

**⇒ 项目同时跑 PG 与 SQLite，SQL 函数一定要挑两边都有的。**
（`pytest` 用 `DATABASE_URL=sqlite:///:memory:`，所以**本地单测就是双库兼容的最后一道闸**。）

**`isLivePhase()` 口径**：只有 `auction` / `intraday` / `midday` 三个阶段为真
⇒ **盘前、盘后、复盘、夜间全为 false** ⇒ 温度在非盘中一律不刷。

**为什么这个砍法是对的**：`/market/temperature` 的 docstring 明写
「**同步端点（含网络抓取）**」⇒ 不是纯内存缓存，夜间每 120s 刷会产生真实外部请求。
BK-55 的原意（注释原文）："夜间 A股变量不会变 ⇒ 停轮询（旧实现十余个加载器整夜每 2 分钟空转，
'页面开一天' 的 egress 白付）"。

**⇒ 所以"之前实时"是真的，但只差 `temperature` 一行，且 2026-10-24 就改了，不是最近的事。**
用户现在感觉"完全不实时"，主因仍是**服务崩溃 + backend-pack 停更在 11-06**（见上一条）。

**若要把温度夜间也刷**：把 `loadTemperature()` 挪到 `if (!isLivePhase()) return` 之前即可；
**代价是夜间每 120s 一次带网络抓取的请求** ⇒ 需用户明确同意（属 egress 决策，不宜擅自改）。
