## 045 全市场 4000 只的必要性与 CPU/内存归因（只分析，未改代码）

- **为什么需要全市场**：不是"每只都精算"，而是口径/横截面需要全量：
  涨跌家数·涨跌停·成交额（少一只就错，`tencent.py:33-36` 实测缺 36%/40%）、
  行业聚合（`industry_amount_share` 全池遍历 `sector_industry.py:658`）、
  横截面分位/排名（温度/Regime/评分排序）、涨停精确口径（rt_k 5569 只）。
- **池子规模**：`_build_stock_pool()` 生成 ~11999 个候选（深 5999 + 沪 6000，`tencent.py:74-104`），
  全量扫描 11999/80 ≈ 150 批；增量 = 有效 ~3236/80 ≈ 41 批（`BATCH_SIZE=80`，60s 冷却）；
  快照恢复 5257 只；前端 kline-pack 3000 只 × 60 日；rt_k 全市场 5569。
- **CPU 归因**：
  · 后端每 120s 全市场增量刷新（41 批 + 3236 只解析 → dict），GIL 单进程与请求争用；
  · `/market/overview` 每次请求对全池做 **3~4 次遍历**（up/down/changes/amount，`market.py:340-370`），
    60s 轮询 = 每天 ~1440 次全池遍历；
  · `industry_amount_share` 每次全池遍历 + 每行业建 chg 列表（60s 轮询）；
  · `live_ranking.compute_full_ranking` 全量精算 ~1550 只（尖峰）；
  · 前端 `computeRanking`：全市场报价 **60+ 批 × 50 只**（`tencent.js:37,51`，每批 sleep 100ms）、
    财报 3 批、6 份数组副本 + 粗排/精算。
- **内存归因**（实测）：JSON→dict 放大 3~4 倍（45MB → 150~200MB，见 Agent 手册 452 行）；
  多份全市场副本（`_cache["stocks"]` / 快照 payload / `_SPEED_CACHE` / `_valid_codes` /
  `_CODE_TO_PREFIX` / `KLINE_CACHE`）；按需大缓存常驻（`_load_signal_map` 整 JSON、
  `_FLOW_MAP_CACHE`、`_latest_cache`、`_PRICES_CACHE`）；
  `cache_release.md` 实测 RSS 159→384（10min）→409（81.8% 告警）→420→被杀→半小时又 367
  ⇒ **512MB 实例 + 单进程，锯齿状 OOM**。
- **前端**：`computeRanking` 里 merged/withQuote/valid/stocksWithQuotes/stocksWithFin/scored
  6 次 `.map({...s})` ⇒ 3000 只瞬间 18000 个对象；IndexedDB 3000 只 K 线 + 500 天指标序列。
- **结论**：4000 只是"口径需要"，不是"计算需要"；爆的是"全量快照多副本 + 每 tick 重复遍历 +
  按需大缓存不释放"，不是股票数量本身。
- **优化优先级**：P0 合并 overview 遍历（4→1）、amount_share 复用同一趟、前端 6 份副本改单趟；
  P1 行情缓存列式/紧凑结构、按需只读候选 150 只；P2 pack/SQLite 化、Render 升 1GB。
- **实测入口**：`GET /api/system/memory?types=1&top=15&history=48`、`memory_probe` 表、前端 `performance.memory`。

## 046 三类行情数据的接口形态（澄清"是否必须全量"）

- **涨跌家数**：无现成全市场聚合接口。腾讯 qt 是逐只；东财 clist 的 `f104/f105/f106` 是**板块级**
  （`eastmoney.py:285`）⇒ 只能自己遍历全池统计，**这一项必须全量**。
- **涨停/跌停**：`rt_k(fields='all')` **3 批 5569 行 / 14s**（`realtime_uplimit.py:17,94-106`），
  是**全市场快照**，成本 O(1) 次请求；`limit_stats.counts_best` 已 rt_k 优先、
  内存按板幅近似只作 fallback（`market.py:2020-2022`）⇒ **不需要本地全量池**。
- **成交额**：`market_amount.estimate()` 用腾讯分时 `sh000001 + sz399001`，**2 次请求/60s，
  与股票数无关**（`market_amount.py:45,97`）；而 `overview.stats.total_amount` 仍是
  池内 `sum(amount)`（`market.py:369`）⇒ **重复且口径偏小（池内不含北交所/ST，实测缺 40%）**。
- **接口成本模型**：逐只接口成本 ∝ N（腾讯 80/批 → 5000 只 ≈ 63 次）；全市场快照成本 O(1) 请求
  但 payload O(N)；指数聚合 2 次；板块聚合按板块数。⇒「请求外部接口」≠「必须自建 4000 只池」。
- **收敛结论**：真需要全量的只剩 ①涨跌家数/宽度 ②行业聚合 ③横截面分位/排名；
  成交额与涨停都应改为读聚合接口，`overview` 的池内求和属于应删除的重复。

## 048 澄清「全市场增量刷新」的真实含义与副作用

- **增量 = 代码池剪枝，不是数据增量**：`do_full_scan = force or not _valid_codes`；
  全量 = `_ALL_CODES` ≈ 12000 个候选（150 批，2~4 分钟）；增量 = `_valid_codes` ≈ 3236 只（41 批，30~60s）。
  每次仍 `_cache["stocks"] = stocks` **整体替换**（`tencent.py:458-493`）⇒ 流量/解析不省，只省空号。
- **目的**：① 让 120s 周期能跑完（全量跑不完）；② 不请求 8000 个空号（WAF 风险）；
  ③ 快照持久化 `_valid_codes`（方案 C）⇒ 重启后也走增量而非全量（`tencent.py:575-640`）。
- **服务对象**：overview / temperature / emotion / amount-share / coach / radar / limit_stats /
  trader_brief / scan / event 等一批「零外部请求」接口，全靠这份内存快照。
- **间隔**：`STOCK_CACHE_INTERVAL_SEC` 默认 120s（`scheduler.py:227`），但 docstring 写「每 3 分钟」
  ⇒ **注释与实现不一致**（历史遗留）。
- **副作用**：① 新 dict 构造完才替换 ⇒ 瞬时双份内存（3236 项）；
  ② **新股盲区**：`_valid_codes` 只在全量扫描时重建，而收盘快照不 force、不重建
  （`scheduler.py:1937-1939`）⇒ 新上市代码不会进池，快照恢复后仍走旧 `_valid_codes`。
- **若要降负载**：改「分层刷新」（快层 60s 只刷持仓/观察池/主线成分 ~200 只；慢层 300s 全市场），
  并在统计接口标注 `data_ts/age`；不要靠改名，因为增量并不减少请求。
