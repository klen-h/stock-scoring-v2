## 002｜**AI 解读整篇是编的**——`missing` 没进 prompt（`fb6e3563`）

### 现象
用户贴回一段输出，读起来极其专业、逻辑自洽：

> 白酒板块 -2.8% 与隔夜纳指 -1.9% 同向…
> 半日成交 9842 亿、按曲线推全天约 1.55 万亿，环比缩量 12%…
> PMI 49.8 跌破荣枯线…

**逐条核对：一条都不在数据里。**

| 输出里的数字 | 系统实际 |
|---|---|
| 白酒 -2.8% | `amount_share available=False`，无板块涨跌 |
| 隔夜纳指 -1.9% | **纳指根本不在数据源**（代码注释：标普/纳指不在日频表内） |
| 上涨 2814 家 | `market_emotion_daily` 当天**整行不存在** |
| 半日成交 9842 亿 / 全天 1.55 万亿 | `market_amount.peek()` 全为 None |
| PMI 49.8 | 当日 `actual=None`（未公布），consensus 51.6 / prev 52.1 |
| 水泥/钢铁跌幅小于指数 | 无板块、无指数 |
| 消息面两条 | `flash_block news=0 条` |

当天实际喂给模型的**只有 4 行**：市场状态、主力资金结构、情景推演、数据口径。
（当时是 **00:27**，周一凌晨，本来就没有早盘数据。）

### 根因（三层，都不是"模型不听话"）
1. **`missing` 从来没进 prompt** —— 模型不知道自己缺什么，只看到 4 行，却要满足"4~6 条"的要求。
2. **system 里"不得编造"是软约束** —— 没有"数据不足就直接拒答"的硬门，也没有"未提供的板块名/指数名禁止出现"。
3. **端点无数据门槛** —— 无论 payload 有没有料，都直接调 LLM。

### 修法
- `_digest_user_text`：顶部插入「可用数据：盘面 N / 宏观 N / 消息 N」，末尾追加
  「⚠️ 数据缺失（你没有这些，**禁止推测、禁止补数字**）」逐条列出原因。
- `_DIGEST_SYS`：加四条绝对红线（未出现的板块名/指数名/数据值不得出现；
  缺失段列出的类别不得给结论；可用<4 项只输出一行"数据不足"；禁止引入外部数字）。
  条数改为"由数据量决定"，明确「宁可 1 条有出处，不要 5 条编一半」。
- `am_review_digest_run`：**硬门**——盘面为空直接拒绝（`blocked=True`）且不烧 LLM，
  同时 `pop` 掉可能已缓存的"编造版"；前端把 `hint` 一起显示。

### 验证
- 今日（00:27）：`ok=False blocked=True`，返回具体缺什么 + 该怎么做。
- 历史 10-30（盘面 4 项 / 宏观 16 项）：正常生成 **453 字**，全部可追溯：

```
815/4137、涨停49/跌停93、连板1、主力2853只(下跌1981/吸筹237/出货22+洗盘14=36 自己算的加法)、
布伦特111.85、法国GDP -0.1% vs 前值0.50%、情景基准磨底 多2/空3 锚点3574
```
  **没有再出现成交额、指数点位、板块涨跌、个股名。** 唯一提到的"银行/保险/煤炭"是引用消息面原文。

### 教训（写进 MEMORY 级别）
**展示型 AI 输出必须显式告知"你缺什么"，而不是只说"你不能编"。**
LLM 在信息真空下不会留白，它会用最合理的常识填空 —— 而"合理"恰恰最难被察觉。
**输入越贫乏，输出越流畅，就越危险。**

## 006｜**修正 005 的结论**：元凶是 per-thread glibc arena，不是开盘、不是缓存（`95b4ce90`）

用户贴出 Render 事件日志，今天实际**失败 8 次**（全部 "used over 512MB"）：
09:36 / 09:38 / 09:40 / 09:42 / 09:46 / 11:44 / 11:47 / 14:28。
09:36~09:46 是同一个实例 `8w7kp` 的**连续崩溃循环**（每次约 2 分钟）。

### 决定性证据：线程数 ↔ RSS 一比一
`memory_probe` 全天（含 `threads` 列）：
| 时刻 | 线程 | RSS | 容器% | 具名缓存 | 未归类 |
|---|---|---|---|---|---|
| 常态（12 次采样） | 8~17 | 205~230 | 41~47% | 38~40 | 165~190 |
| **11:44:29** | **23（全天最高）** | **446.8** | **95.3%** | **45.7** | **401.1** |

⇒ 具名缓存只从 40 涨到 46MB，**RSS 却涨了 220MB**。涨的**不是数据**，
是"每多一个并发线程就多一块不归还 OS 的堆"（glibc arena）。

### 这在本项目已诊断过一次，但只修了一半
`main.py:64-73`（2026-10-25）写得很准："每线程一个独立 arena、碎片不归还 OS"，
对策是 `anyio` limiter=8。**但 `anyio` 只覆盖 FastAPI 同步端点**；
**调度器里上百处 `asyncio.to_thread(...)` 走的是 loop 默认执行器**
（`ThreadPoolExecutor(max_workers=min(32,cpu+4))`，**完全没封顶**）⇒ 25 个循环一开机同时开跑。
这解释了两件事：① 崩溃循环总是在**启动后 2 分钟内**；② 11:44 线程冲到 23。

### 本次修法
1. `asyncio.get_running_loop().set_default_executor(ThreadPoolExecutor(max_workers=6))`
   （`ASYNCIO_POOL_WORKERS` 可调）⇒ 调度器并发也上了同一个闸。
   代价：启动预热串行化、首批页面稍慢；但 CPU 只有 0.1~0.5 核，并行本就是假的。
2. 启动时**打印 `MALLOC_ARENA_MAX` 实际生效值**，并在 `/api/system/memory` 的
   `process` 里暴露 `malloc_arena_max`。
   【为什么必须能看见】这个开关**只能在进程启动前由环境变量注入，代码里设无效**；
   `render.yaml` 自述"本文件只是变量清单文档，不生效" ⇒ 到底配没配只能靠猜。

### 仍需用户确认（我做不了）
**Render 控制台里 `MALLOC_ARENA_MAX` 到底有没有配成 2？**
看启动日志或 `curl /api/system/memory | grep malloc`。没配的话，arena 数按 CPU 开，
线程一多碎片必涨 —— 那才是 512MB 的真上限。

## 007｜再次修正：`MALLOC_ARENA_MAX=2` **确实生效** ⇒ 元凶是闸门并发构建（`591bfd03`）

用户明确回复："MALLOC_ARENA_MAX 确确实实设置了 2"。

⇒ **006 里"每线程一块 arena"的说法作废**：arena 最多 2 块，不可能随线程数线性增长。
线程数在这里只是**"同时有几个重活在跑"的计数器**。

### 真正的机制（代码级）
`mainforce/gate.py::gate_states_for_signals()` 一次要给 **1018 只 × 750 根**日线建 map：
- `research_cache.ohlc_for()` 每次返回**全新** `{code: [ {date,open,...} ]}`
  ⇒ 76 万根 bar × ~280B ≈ **210MB**，且**没有任何进程缓存**（每次重建）
- 紧接着原代码又 **整份复制一遍**（`[dict(b, date=...) for b in bars]`）⇒ **峰值 420MB**
- 这些是**函数局部变量**，不在模块级缓存里 ⇒ `memory_probe` 显示"具名缓存 45MB、未归类 401MB"
- 调度器里 `workbench_scan_loop` / `portfolio_radar_warm_loop` / `score_snapshot_loop`
  **会并发调它** ⇒ 23 线程 = 好几份 210MB 同时存在 ⇒ 512MB 一击即穿

这条链路自己也有前科：`gate.py:360` 注释写着 2026-10-21 曾因 76 次全历史 IN 查询造成 **1.4GB**。

### 本次修法（两刀）
1. **去掉整份复制**：`ohlc_for()` 每次返回新对象 ⇒ 原地归一化 `date` 即可，省下 210MB。
2. **单飞锁**：`_GATE_BUILD_LOCK` + 双检缓存，并发调用退化为"排队 + 命中缓存"，峰值只剩一份。
   实测：5 个线程并发调，**只构建 1 次**、总耗时 0.40s（不锁会是 2.0s）。

### 现在的三层防线
| 层 | 位置 | 作用 |
|---|---|---|
| 并发闸 | `main.py` `set_default_executor(6)` | 调度器 `asyncio.to_thread` 不再无限开线程 |
| 单飞 | `gate.py` `_GATE_BUILD_LOCK` | 同一份重活不并发构建 |
| 少拷贝 | `gate.py` 原地归一化 | 不再 210MB × 2 |
| 环境 | `MALLOC_ARENA_MAX=2`（已确认） | 堆碎片不按线程膨胀 |

## 008｜**CPU 与内存同步抽顶**的真因：闸门整批重建（`78df228c`）

用户给了 Render 的 CPU/内存双图：两图像**同步**尖峰到 100%，尖峰点约
09:40 / 12:20 / 15:10，其余时间平稳在 40%。"同步"是决定性的——
说明不是泄漏，而是**一次性重算**（既烧 CPU 又吃内存）。

### 机制
`_gate_cache_key()` 是**整批 (code,date) 的 md5 指纹**：

```python
raw = "|".join(sorted("%s,%s" % (s.get("code"), s.get("date")) for s in signals))
```

⇒ **盘中只要多一个新信号，指纹就变，整批缓存全部失效**，
于是把 1018 只 × 750 根日线**全部重读 + 全部重算 chip_series/phase_series**：
CPU 打满（几百只的筹码/阶段计算）、内存 +210MB，两者同时到位。
`flash_loop` 每 5 分钟带来新信号 ⇒ 每 5 分钟一次尖峰。

### 修法：整批 → 逐条增量
新增 `_GATE_ENTRY_CACHE = {(code,date): (ts, gate)}`（TTL 30 分钟、上限 2 万条 ≈ 4MB）：
- 命中直接返回，**连 flow/股本都不读**
- 只对没见过的 (code,date) 走 `_load_gate_bars` + chip/phase
- 新增 1 个信号 = 只算 1 只股票

### 教训
**"CPU 和内存同时打到 100%"这个形态本身就排除了"泄漏/碎片"类解释。**
泄漏是单向爬升、碎片是阶梯不回落，而"同步尖峰 + 迅速回落"只有一个含义：
**有一批活被反复整体重算**。以后先看这个形态，再谈缓存。
