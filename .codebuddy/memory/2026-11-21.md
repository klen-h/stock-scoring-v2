## Supabase 迁移续跑：三个坑（重复进程 / duplicate / DNS）

昨天停在 65.8% / 120.7MB，今天继续。过程中踩了三个坑。

### ① ★ 重复启动进程 ⇒ pooler 连接打满（`EMAXCONNSESSION`）

用户手动 `Start-Process` 了一次，我又启了一次，加上前一个没退干净的，
**同时有 3 个迁移进程**，每个 5~7 workers × 2 连接 ⇒ 源库 pooler 报
`FATAL: (EMAXCONNSESSION) max client connections reached` ⇒ 大量分片失败。

**教训**：迁移这类长任务**必须保证全局只有一个进程**。
排查/清理用：

```powershell
Get-CimInstance Win32_Process -Filter "Name='python.exe'" |
  Where-Object { $_.CommandLine -like '*_tmp_mig*' } |
  ForEach-Object { Stop-Process -Id $_.ProcessId -Force }
```

**并发定为 5**（10 连接）：7 路虽然快（实测 198KB/s）但会打满 pooler，
5 路稳定（实测 48KB/s）且零错误。**稳定性优先于速度**。

### ② ★ duplicate key：COPY 已提交但客户端认为失败

现象：`shadow_rank_daily` 源 7200 行，目标只进 6836 行，日志全是
`duplicate key value violates unique constraint`。

诊断：`TRUNCATE` 本身有效（实测 6836→0）。真正原因是
**COPY FROM 在服务端已提交，客户端读响应时连接被掐** ⇒ psycopg2 抛异常
⇒ `_task` 重试 ⇒ **同一片数据插第二遍**。

**修法**：写连接改 `autocommit=False`，COPY 后显式 `commit()`；
异常时 `rollback()` 再重连。连接断开时服务端事务自动回滚，重试安全。

**另修**：分片页数用 `pg_relation_size(oid)/8192`（精确），
不用 `relpages`（统计估计值偏小 ⇒ 最后一片覆盖不到 ⇒ 少行，
`sector_daily` 曾少 2571 行）。

### ③ ★ 本机 DNS 解析不了 pooler 域名

```
nslookup aws-0-ap-southeast-1.pooler.supabase.com
  → public1.alidns.com (223.5.5.5) : Server failed
nslookup ... 8.8.8.8  → 正常返回 3 个 ELB IP
```

**阿里 DNS 解析不了 Supabase 的 pooler 域名**（并发建连时更会
`getaddrinfo failed` / `Temporary failure in name resolution`）。

**修法**：连接用 **`host`（域名，供 SNI/租户路由）+ `hostaddr`（IP，跳过解析）**
双参数，并对多 IP 依次尝试。

```python
_IPS = {
  "aws-0-ap-southeast-1.pooler.supabase.com":
      ["52.74.252.201", "54.255.219.82", "52.77.146.31"],
  "aws-0-ap-northeast-1.pooler.supabase.com":
      ["54.64.190.72", "35.79.125.133", "52.68.3.1"],
}
psycopg2.connect(host=域名, hostaddr=IP, ...)
```

**⚠️ 不能只给 IP**：Supabase pooler 靠 SNI 识别租户，
只给 IP 会报 `no tenant identifier provided (external_id or sni_hostname required)`。

### 断点续传机制（可反复中断/续跑）

`_tmp_mig4.py` 逐表比对源/目标 `count(*)`，一致就跳过，不一致就
`TRUNCATE` 后重迁。所以任何中断后**直接重跑同一条命令**即可，
已完成的表不会重来。`--check` 只体检不写库。

```powershell
python _tmp_mig4.py --check                    # 看还差多少
Start-Process python -ArgumentList '_tmp_mig4.py' ...   # 续跑
```

### ★★ 端口选择：东京 5432 比 6543 快 3.5 倍

| 配置 | SELECT 1 往返中位 |
|---|---|
| **东京 5432（session）** | **165ms**（163~170，极稳） |
| 东京 6543（transaction） | **571ms**（167~762，抖动严重） |
| 新加坡 6543（旧，现用） | 228ms |

**⇒ 新库 `DATABASE_URL` 用 5432，不要照抄旧库的 6543。**

旧库新加坡 6543=228ms 是正常的；**东京 6543 异常慢**，疑与 Supavisor
在该 region 的实例拓扑有关。6543 只适合极端连接数场景。

### 应用层单查询 ~519ms 是既有架构，不是迁移问题

`database.fetch()` 每次 = **execute + fetch + commit 三次往返**：
`170ms × 3 ≈ 510ms` 与实测吻合。
旧库 `228ms × 3 ≈ 684ms`（与历史记录的 647ms 一致）。
⇒ **新库反而快约 20%，没有退化。**

## 用户想"先用旧库验证流量再切新库"——三个认知纠正

用户（11-21 周六）："我想着先用旧的数据库验证今天的流量消耗，没问题再切新的数据库。"

### ① 生产本来就在旧库，不需要"切回去"

我只改了**本地** `backend/.env`（为跑迁移脚本）。
服务器 `.env` 和 GitHub Secrets 都没动 ⇒ 日批、scheduler、页面全连旧库。
**用户的验证目标其实已经在发生。**

### ② ★ 流量是代码行为决定的，不是数据库决定的

同样的优化后代码，连旧库或新库，传输的行数/查询次数**一样**。
"切库"不会改变流量。要验证的是**优化代码是否生效**，
跟用哪个库无关 ⇒ 在旧库验证并不能更安全。

### ③ 今天（周六）验证不了，且旧库 egress 数据停在 11-20

```

```

**日增量趋势**（按 queryid 差分）：
11-16 638万 → 11-17 263万 → 11-18 163万 → 11-19 140万 → **11-20 139万行**

⚠️ 但 11-20 的 top1 **仍是 596,774 行的 `backtest_prices` 老查询**
（`_load_bars_batch` 没 LIMIT 那条）——优化后应降到 ~12 万行。
**⇒ 优化代码很可能还没部署到服务器**（commit 于 11-20，需 git pull + 重启）。
不确认部署就等几天，验证的仍是旧代码。

### ④ 旧库曾 egress 16GB 打爆 5GB 被 402 限制

若仍处于受限状态，日批写库失败 ⇒ 测到的是"失败态低流量"，
不是"优化后的真实流量" ⇒ **验证结果不可信**。
