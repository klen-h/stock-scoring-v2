## 🔧 修复：ranking_live 全量精算榜 0 行落库（2026-09-14 手动日批发现）
- **现象**：daily_batch [14/19] 精算榜单报 `[live_ranking] 批量写入失败（逐行兜底）: there is no unique or exclusion constraint matching the ON CONFLICT specification` → 0 行落库（榜首云铝股份 68.2 已算出但写不进去）。
- **根因**：`ranking_live` 表 09-11 首建时**缺 `UNIQUE(rank_date, code)` 约束**（实际库里 pg_indexes 查不到任何索引），而 `save()` 用 `db.upsert_many(..., ["rank_date","code"])` 的 ON CONFLICT 依赖该约束。`init_table()` 里 `CREATE TABLE IF NOT EXISTS` 的 UNIQUE 子句对**已存在的旧表无效**（IF NOT EXISTS 跳过）→ 约束一直缺失。
- **修复**：`live_ranking.init_table()` 在 CREATE TABLE 后补 `CREATE UNIQUE INDEX IF NOT EXISTS idx_ranking_live_date_code ON ranking_live(rank_date, code)`（PG 支持 IF NOT EXISTS，唯一索引可作为 ON CONFLICT 仲裁目标）。
- **验证**：补索引成功（pg_indexes 见 idx）；upsert 端到端冒烟通过（插入返回 1、冲突 DO UPDATE 生效、测试数据已清理）；lint 干净。表当前仅 300 行全 09-11、无重复 → 建索引安全。

## ⚠️ 日批「假成功」修复：rank_live 落库 0 行但任务显示 ✅（2026-09-14）
- **实测**：09-14 日批汇总 `成功 19 / 失败 0`，但查库确认 `ranking_live` **只有 09-11 的 300 行、09-14 完全没落库**——[14/19] 精算榜单是**假成功**。
- **双重根因**：① 表缺 UNIQUE 约束（见上，已修补唯一索引）；② **`compute_and_store` 拿到 `saved` 却不检查**——`save()` 内部 `try/except` 吞掉 upsert 异常返回 0，外层照样返回"X 行落库"成功摘要 → 任务进 ok_list。
- **修复**：`live_ranking.compute_and_store` 加 `if saved <= 0: raise RuntimeError(...)`——落库 0 行即让任务失败（进 fail_list + 企微告警），"算出但没写进库"不再静默。lint + py_compile 干净。
- **需重跑落库**：`python scripts/daily_batch.py --tasks rank_live`（Actions dispatch 或本地，索引已建好，save 会先 DELETE 当日再全量插）。当前 09-14 榜单仅存在于内存/日志（榜首云铝股份 68.2），库里没有。→ **2026-09-14 Actions dispatch `tasks=rank_live` 已验证 ✓**：`300 行落库（date=2026-09-14, 池=1542, 榜首 000807 云铝股份 68.2）`，耗 14s（对比假成功那次 838s——时间全耗在失败写入的重试上）。同批日志 `[env_check]` **9/9 全 OK**，三处配置（本地/Render/Actions）全对齐。
- **教训**：`try/except` 吞异常 + 不校验副作用结果 = 「任务成功」≠「数据落库」。凡"算完要写库"的任务，都应对写入结果做校验（同类风险点值得排查）。
