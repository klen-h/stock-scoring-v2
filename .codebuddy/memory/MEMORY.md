# 长期记忆（跨会话关键事实）

## 项目性能基线（2026-11-01 实测）
- **Supabase 实例在 `ap-southeast-1`（新加坡），本机到它每次 SQL 往返固定 ~570ms**
  （连续 12 次 `SELECT 1`：566~576ms，极稳；首连 +2.8s TLS）。**不是限速，是物理距离**。
- 端口 6543 = Supabase pooler（PgBouncer 事务模式）。
- ⚠️ 因此本项目所有性能问题的第一定律：**优化方向永远是"减少往返次数"，不是"优化计算"**。
  多次点查的端点必然慢；读多写少的数据应进进程缓存/本地包。
- GitHub Actions（美国/欧洲 runner）到新加坡同样 100-300ms/往返 ⇒ "生成的接口"也慢，同因。

## 数据包（pack）已知缺陷
- 增量更新（`update_backend_pack_incremental.py`）的 `_merge_exdiv` 用**一次** zzshare
  factor 比例缩放旧历史来近似复权 ⇒ factor 缺失/多次分红累积 ⇒ **复权断层**。
  实测 000807：历史与实时差 32~36%，10-30 断层 +37.8%。
- 已加读侧防线：`kline_cache._impossible_jump`（末尾 5 根、>31% 跳变 ⇒ 判不可信走实时）。
- **包不会自愈**（`--backfill` 只补缺失日线不重算复权）；根治需全量重建或改 `_merge_exdiv`
  （先验证 zzshare 与包的复权口径一致，否则会把全市场改错）。

## 项目约定 / 用户偏好
- 中文交流；回答要直接、有实测数据支撑，先诊断后动手；重要取舍要问用户。
- 授权模式：用户逐项点头（"可以"“直接做 A"），不擅自扩大改动面；
  改产包脚本这类影响全市场的操作必须先验证口径并征求同意。
- 脚本/日志打印**不得含非 ASCII**（铁律⑥）；时间是北京时间（`rules.beijing_now()`）。
- 临时脚本用完即删；诊断脚本以 `_tmp_*.py` 命名。
- Vue 模板引用未定义变量 **build 不报错**：改模板+script 配对操作后必须 grep 同名变量。
- `*_WINDOW` 常量必须 `0<=start<end<=1440`（曾两次笔误 1555/1800）；`scheduler.start()` 有自检。
