## 决策：浏览器通知**不值得**为此迁 GitHub Pages

用户："我想浏览器通知功能，所以部署到 github 上值得吗？"

### 结论：不值得。真门槛是 **HTTPS**，不是 GitHub。

### 事实（查证）

1. **浏览器通知模块早就写好了**：`frontend/src/composables/useNotifications.js`
   （权限管理 / 状态 diff 去重 / 急涨急跌 / 持仓警报 / 自选买点 / 计划状态，功能完整）
2. **11-10 就已诊断过根因**（文件里有注释）：
   `Notification` 只在 **secure context**（https / localhost）可用；
   `http://101.201.222.167` 下 `'Notification' in window` 仍是 true ⇒ 按钮正常显示，
   但 `requestPermission()` 静默返回 `'default'` 不弹框 ⇒ **"点击无反应"**。
   **本地 localhost 属于 secure context，所以本地一切正常。**

### 迁 GitHub Pages 的三个硬障碍

**① 混合内容（致命）**
`https://xxx.github.io` 页面调 `http://101.201.222.167/api` ⇒ **被浏览器直接阻止**。
⇒ **后端也必须上 HTTPS**。那既然后端都要 HTTPS，`为什么不干脆前端也放同一域名`？

**② 现有 gh-pages 产物连不上后端**
`frontend/src/api/http.js`：
```js
baseURL: import.meta.env.VITE_API_BASE_URL || '/api'
```
`deploy-preview.yml` 构建时**没设** `VITE_API_BASE_URL` ⇒ 产物里是 `/api`
⇒ 在 `xxx.github.io` 上会请求 `https://xxx.github.io/api/...` → **404**。
**所以现有 gh-pages 版本是"离线版"**（靠 `klineDB.js` 下载 K 线包 + IndexedDB 做前端评分）。

**③ 国内访问 GitHub Pages 不稳定**（用户在国内，前端会变慢/时通时不通）

### 正确做法

**给现有服务器配域名 + Let's Encrypt（免费）**，前端后端同一域名：
- 一次配置同时解决 Notification / clipboard / Service Worker / 混合内容
- 保持国内访问速度
- **前提：需要一个域名**（Let's Encrypt 不给纯 IP 签证书）

### ⚠️ 更要紧的认知：浏览器通知 ≠ 后台推送

`useNotifications.js` 用的是 `new Notification(...)` —— **只在页面打开时能弹**
（后台标签页也行）。**标签页一关就没了。**

要"关掉浏览器也收到" ⇒ 需要 **Service Worker + Push API + VAPID 服务端**，工作量很大。

而项目**已经有企微推送**（`app/wechat.py`），已经覆盖"离开电脑也能收到"。
⇒ **浏览器通知的定位是"页面开着时的即时弹窗"，是企微的补充，不是替代。**

**⇒ 如果真实需求是"盘中异动能通知到我"，现在的企微已经满足；先确认这个需求边界再动手。**

## 情绪跃迁观察卡（`3f7158fd`）—— ★ 一次差点被骗的统计

### ★★ 最关键的一步：发现"6/6 全放大"是时间累积偏差

| 组 | n | 下午放大率 | 平均变化 |
|---|---|---|---|

| **差** | | **56pp** | |

**全部是 `long_t`（正T = 先买后卖）** ⇒ **T+1 下当天买的不能卖，一笔都不可能成交**。

**⇒ `+182 元` / 胜率 `50%` 全部失真。**

### 根因

`_t_trade_tick`（`scheduler.py:1864`）：

```python
force = t_min >= _T_TRADE_CLOSE_MIN      # 尾盘强制平
if not sig and not force: continue
r = TX.close_trade(tr["id"], price, ...)  # 当天买 → 当天平
```

**"尾盘强制平"把当天买的直接平掉**，而 `close_trade()` **没有任何日期校验**。

⚠️ 讽刺的是：项目**早就有** `today_bought()`，注释明写「**T+1 不可卖**」，
但它只被用来扣减**反T 的卖出量**，没用在**正T 的平仓**上。

### 修了 3 处，**必须联动**（少一个就出别的问题）

**① `close_trade` 加拦截**

```python
if direction == "long_t" and open_time[:10] == today:
    print(...); return None     # 返回 None 而非异常：调用方 `if not r: continue`
```

**② `open_trades` 改跨日**（否则正T 变孤儿）

```sql
-- 原来：WHERE trade_date=day AND status='open'   （只当天）
-- 现在：当天全部 + 往期仍 open 的正T
WHERE status='open' AND (trade_date=%s OR (direction='long_t' AND trade_date<%s))
```

**反T 不加入跨日**：它卖的是昨仓，当天就该买回；不买回等于减仓，那是另一件事。

**③ `has_traded` 改判据**（否则重复开仓）

```sql
-- 原来：WHERE code=? AND trade_date=today
-- 现在：WHERE code=? AND (status='open' OR trade_date=today)
```

**如果不改 ②③**：正T 当天被拒后永远 open（② 的锅），
或者同一只票次日被再开一笔（③ 的锅），**两笔同时 open**。

### ★ 更深的问题（要跟用户确认，我没擅自改）

**`long_t`（正T）在 A 股 T+1 下本质上不是"做T"，是"隔日波段"。**

真正的做T 只有**反T**（先卖昨仓 → 当天买回）。
所以现在的"正T"要么：

1. **改成隔日持仓逻辑**（今天买、明天按止盈止损卖）—— 那就是波段，盈亏口径要重算
2. **取消正T，只做反T** —— 更贴近"做T"本义，但需要有底仓
3. 保持现状（今天买、明天才能卖）—— 代码已按这个修好

**这个选择涉及策略定义，不是 bug 修复，等用户定。**

```python
# t_trade_exec.py:781
```

`min_base_shares(ratio)` = `max(100, round(100/ratio / 100) * 100)`

**注意 `max(300, ...)` 是硬下限**：`ratio=1/2` 只需 200 股，但仍会建议 300 股。

### ② 成本模型（`t_trade.py`）

```python
T_COMMISSION_RATE = 0.00025    # 佣金 万2.5（双边）

def calc_fee(buy_amount, sell_amount) -> dict   # 返回明细 + total
```

**金额必须按方向传**：

```
正T：买 = open_price×shares，卖 = close_price×shares

```

**不含滑点** —— 本项目按真实成交价记账，滑点已经在价格里，再加就是重复扣。
