## 决策：浏览器通知**不值得**为此迁 GitHub Pages

用户："我想浏览器通知功能，所以部署到 github 上值得吗？"

### 结论：不值得。真门槛是 **HTTPS**，不是 GitHub。

### 事实（查证）

1. **浏览器通知模块早就写好了**：`frontend/src/composables/useNotifications.js`
   （权限管理 / 状态 diff 去重 / 急涨急跌 / 持仓警报 / 自选买点 / 计划状态，功能完整）
2. **11-10 就已诊断过根因**（文件里有注释）：
   `Notification` 只在 **secure context**（https / localhost）可用；
   `http://101.201.222.167` 下 `'Notification' in window` 仍是 true ⇒ 按钮正常显示，
   但 `requestPermission()` 静默返回 `'default'` 不弹框 ⇒ **"点击无反应"**。
   **本地 localhost 属于 secure context，所以本地一切正常。**

### 迁 GitHub Pages 的三个硬障碍

**① 混合内容（致命）**
`https://xxx.github.io` 页面调 `http://101.201.222.167/api` ⇒ **被浏览器直接阻止**。
⇒ **后端也必须上 HTTPS**。那既然后端都要 HTTPS，`为什么不干脆前端也放同一域名`？

**② 现有 gh-pages 产物连不上后端**
`frontend/src/api/http.js`：
```js
baseURL: import.meta.env.VITE_API_BASE_URL || '/api'
```
`deploy-preview.yml` 构建时**没设** `VITE_API_BASE_URL` ⇒ 产物里是 `/api`
⇒ 在 `xxx.github.io` 上会请求 `https://xxx.github.io/api/...` → **404**。
**所以现有 gh-pages 版本是"离线版"**（靠 `klineDB.js` 下载 K 线包 + IndexedDB 做前端评分）。

**③ 国内访问 GitHub Pages 不稳定**（用户在国内，前端会变慢/时通时不通）

### 正确做法

**给现有服务器配域名 + Let's Encrypt（免费）**，前端后端同一域名：
- 一次配置同时解决 Notification / clipboard / Service Worker / 混合内容
- 保持国内访问速度
- **前提：需要一个域名**（Let's Encrypt 不给纯 IP 签证书）

### ⚠️ 更要紧的认知：浏览器通知 ≠ 后台推送

`useNotifications.js` 用的是 `new Notification(...)` —— **只在页面打开时能弹**
（后台标签页也行）。**标签页一关就没了。**

要"关掉浏览器也收到" ⇒ 需要 **Service Worker + Push API + VAPID 服务端**，工作量很大。

而项目**已经有企微推送**（`app/wechat.py`），已经覆盖"离开电脑也能收到"。
⇒ **浏览器通知的定位是"页面开着时的即时弹窗"，是企微的补充，不是替代。**

**⇒ 如果真实需求是"盘中异动能通知到我"，现在的企微已经满足；先确认这个需求边界再动手。**

`status===0 && !e.response` = **连 HTTP 响应都没拿到** ⇒ 请求根本没到达后端。

**⇒ 不是代码 bug，重试即可。**

### ★ 但存在一个真隐患（今天没触发）

| 参数 | 值 |
|---|---|
| `refresh_from_upstream` 单镜像读超时 | **60s** |
| 总预算 `budget` | **90s** |
| nginx 默认 `proxy_read_timeout` | **60s** |

**后端愿意等 90s，但网关 60s 就断** ⇒ 若 8 个镜像（4 lite + 4 full）全挂：

- 后端还在逐个试（累计可能 >60s）

```nginx

    proxy_read_timeout   180s;
    proxy_send_timeout   180s;
    proxy_connect_timeout 30s;
}
```

```
② 或把后端 budget 降到 50s（< nginx 60s），保证错误能被前端看到；
   代价：full 版（6.4MB，国内实测 59s）几乎永远拉不完，只能靠 lite 镜像。
```

**⇒ 建议 ①**：让预算真正生效，错误文案才准确。

## 情绪跃迁观察卡（`3f7158fd`）—— ★ 一次差点被骗的统计

用户："按你建议来"（即做那个「上午涨停跃迁」观察卡）。

### 实现

`market.py::_emotion_leap(limit_up_now, p_day, d_prev)` → 挂进 `/api/market/emotion` 的 `leap` 字段。

```
ratio = 今日涨停 / 上一交易日全天涨停
level: leap(≥1.7x 且 ≥50) / fade(≤0.6x) / normal
hist: 上午 11:30 涨停 ≥50 的历史样本 + **对照组**
```

前端 `Workbench.vue` 情绪行加一枚标记，**只在 leap/fade 时显示**（normal 不占位，避免天天报警），
并把样本量 `n` 和对照组比例**直接印在行内**。

### ★★ 最关键的一步：发现"6/6 全放大"是时间累积偏差

第一版只统计「上午 ≥50」的样本：

```
89→125 · 61→86 · 51→58 · 53→95 · 50→84 · 62→146   ⇒  6/6 全部放大（100%）
```

**看起来完美 —— 但这是陷阱**：上午 11:30 只走了 2 小时，下午还有 2 小时，
**涨停数本来就倾向继续增加**，这不是预测力。

**补对照组后（上午 <50 的 9 个样本）**：

```
33→126 ↑ · 27→31 ↑ · 46→37 ↓ · 42→38 ↓ · 33→33 =
42→38 ↓ · 33→40 ↑ · 24→29 ↑ · 31→30 ↓
⇒ 放大 4/9 = 44%
```

| 组 | n | 下午放大率 | 平均变化 |
|---|---|---|---|
| 上午 ≥50 | 6 | **100%** | +63.0% |
| 上午 <50 | 9 | **44%** | +33.0% |
| **差** | | **56pp** | |

**⇒ 才说明 ≥50 有特异性，而不是时间累积。**

**这个对照已经写进代码**（`hist.baseline` + `hist.edge_pp`），
否则"6/6"会被当成确认信号 —— **正是「缩量企稳」被误用的同一种错**。

### 防御性设计（都要保留）

1. **只在 leap/fade 时显示**，normal 不占位 ⇒ 避免天天报警
2. **`n` 必须印在界面上**（不写样本量 = 会被当信号）
3. `note` 里写全：「观察项，**不是信号**：≥50 组放大率 X%（n=6）vs 对照组 Y%（n=9），差 Zpp」
4. **明确不进决策链**，也不改 `no_chase_rally` 的判定

### 边界

```

am_limit_up 是 TEXT      → Python 里转 int（SQL cast 空串会报错）
```
