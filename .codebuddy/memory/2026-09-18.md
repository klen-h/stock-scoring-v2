## 💾 market_snapshot 跨进程缓存（2026-09-18，已修，实测已验证）
- **用户要求**：把 `market_snapshot` 也做成跨进程缓存。
- **★ 病根：两个读取点读同一行、各有一套进程内缓存**
  | 读取点 | SQL | 次数(6天) | 缓存 |
  |---|---|---|---|
  | `flow.get_float_shares_from_snapshot()` | `ORDER BY saved_at DESC LIMIT 1` | 70 | 30min 进程内 |
  | `store.load_market_snapshot()` | `WHERE key='latest'` | 85 | **5min** 进程内 |
  - 都读**整行**（≈1.1MB 文本 / **约 336KB 过网**）⇒ ① **每重启一个新进程必整份读一次**；
    ② **常驻进程里 300s TTL 反复重读**（最坏 ≈288 次/天 ≈ **97MB/天**）。
  - 而快照**每天只在 15:10 落库一次** ⇒ 短 TTL 纯属浪费。
- **★ 修法（`app/flash/store.py` + `app/mainforce/flow.py`）**：统一到 `store.load_market_snapshot()`，
  三层 —— 进程内存（300s）→ **本机 SQLite**（`backend/data/market-snapshot-cache.db`，
  **key = `saved_at`**，12h 兜底 TTL）→ 才回源。
  - **版本探测只取 `saved_at` 一列**（单行几十字节），不做整行读 ⇒ 版本没变就用本机，**零大流量**。
  - **为什么用 `saved_at` 而不是 `sync_meta` 版本号**：写入方可能在**别的机器**（Actions/自建服务器），
    靠数据自身的 `saved_at` 对比**无需写入方配合**即可跨进程失效。（`flow` 那个读取点原来还多走了一次
    `ORDER BY saved_at DESC LIMIT 1`，现在直接 `from app.flash import store` 复用，去掉了重复缓存。）
  - `flow.get_float_shares_from_snapshot()` 保留自己的 `_FS_CACHE` 作最外层内存缓存（行为不变），
    只把"回源那一跳"换成走 store。
- **验证（决定性，两个新进程）**：
  ```
  第一次: 整行读 85→86（回源并落盘 1.15MB） | 版本探测 0→1
  第二次: 整行读 86→86 【+0】              | 版本探测 1→2（几十字节）
  ```
  ⇒ **新进程整行读完全止住** ✓。lint 0。

## ❓ 「凌晨 00:03 会不会触发走线上流量」——逐窗口核对（结论：不会）
- **核对全部 loop 窗口（北京时间分钟）**：K线缓存 `h>=15 and m>=30`；指标缓存 `h>=16`；
  宏观快照/复盘/盘前简报/开盘确认/午间雷达 均 09:10–13:00 段；矛盾扫描/战法扫描 15:35+；
  回测回填 16:10+；资金流 17:00+；主力状态 17:30+；龙虎榜 17:45+；日报 19:30+；
  **最早的 `ZZ_FINANCE_SYNC_WINDOW=(270,1440)` = 04:30-23:59** ⇒ **00:03 不在任何窗口内** ✓
- **唯一常驻**：健康探针（每 300s）—— 只调 `get_macro_panel` / `get_sector_flow` /
  `tracker.get_etf_quotes`，**全是外部源轻量请求，不读大表** ✓
- **0 点跨日的影响**：`schedule_state.done_date` 用**北京日期**（`store._bj_date()`）⇒ 0 点一过所有
  "每日一次"标记变"今天未完成"，**但要等窗口开（最早 04:30）才会执行** ⇒ 0 点瞬间无任务被触发。
  这是设计意图（新的一天该重跑）。
- **★ 关键概念纠正**：**Supabase egress 是账号级的，本地与线上共用同一额度** —— 本地读一次
  就记在同一个账上（这才是"本地能刷爆额度"的原因），**不是"唤醒线上"**。
  本地与线上是**独立进程**，各跑各的 loop；`schedule_state` 是**互斥**机制（谁先跑谁标记，
  另一个跳过）⇒ 本地跑了某些任务，**线上反而会省**。
- **⚠️ 唯一真实路径**：本地回填 `mainflow_history` → `sync_meta.touch("mainflow")` 改版本号
  → **线上 `load_flow_map` 缓存失效 → 线上重拉一次 8.7MB**。这是设计意图（数据变了该重拉）且每天
  1~2 次；但**若本地反复重启反复回填，版本号反复变 → 线上反复重拉**。现在本地已不会反复整表拉，
  此路径已缓和。
- **给用户的建议**：不想让本地进程在 16:10 之后跑重活，**0 点前停掉即可**；或用
  `DEPLOY_READ_ONLY=1`（只读模式，只保留 API/快讯/持仓/模拟盘循环）。

**本轮改动文件**：`backend/app/flash/store.py`、`backend/app/mainforce/flow.py`。**未提交**。

## 🧰 本轮沉淀的方法论（可复用）
- **egress 排障标准动作**：`pg_stat_statements`（按 `rows` 排序）+ **必查 `pg_stat_statements_info.stats_reset`**
  否则会把 N 天累计当成一天；SQL 里 `LIKE '%...%'` 会被 psycopg2 当占位符（`IndexError`）→ 必须走参数传。
- **要看完整 SQL 就用 `SELECT query`，不要用 `LEFT(query, N)`** —— 截断会误判批大小（本次差点把 `$56`
  当成 56 只的批，实际是几百只）。
- **表级 `seq_tup_read` 高 ≠ egress 高**（服务器内部扫的行不产生出站流量）；**egress 只看返回行数 `rows`**。
- **本地/线上共用同一 Supabase 额度**（账号级），"本地跑"不是免费；但本地进程**不会唤醒线上进程**。
