# 2026-11-16（周一）

## ★★★ 线上全站超时：我昨天加的两个循环"失败即重试"（`b60e4551`）

用户："线上怎么接口请求都超时了？"

### 责任在我

这两个循环是 **2026-11-15 我加做T 与评分告警时新写的**，
写的时候只想着"不阻塞事件循环"（用了 `to_thread`，这点是对的），
**没想"失败了会怎样"**。

### 根因：成功后才写"已跑过"标记

```python
# 错误写法（我写的）
if (条件 and _LAST["day"] != d):
    rep = await asyncio.to_thread(重活)     # ← 可能抛异常 / 超时被中断
    _LAST["day"] = d                        # ← 只有成功才写
except Exception:
    print(...)                              # ← 失败 ⇒ 标记没写 ⇒ 下一轮又跑
```

**⇒ 一旦失败就变成每 N 秒重试的**风暴**。**

### 定量（这才是致命的）

| 循环 | 单次耗时 | 重试间隔 | 最坏次数 | 累计占用 |
|---|---|---|---|---|
| `score_health_loop`<br>`get_bucket_stats(120)` | **167 秒**（本地实测） | 600 秒 | 16:00~24:00 最多 **48 次** | **≈13360 秒 ≈ 3.7 小时** |
| `t_trade_scan_loop`<br>`scan_market`（全市场 1025 只） | **72 秒** | 300 秒 | 全天反复 | **≈24% 时间** |

**⇒ 两个叠加，数据库连接被长期占满 ⇒ 所有接口排队 ⇒ 全站超时。**

### 修法（`b60e4551`）

1. **先占位再跑**：进 if 就写标记，**成败都算"已跑过"**，异常只留痕不重试。
2. **`get_bucket_stats` 窗口 120 → 60 天**：单次负载减半，结论方向不变。
3. **加两个应急开关**（默认开，可 env 关）：
   ```
   T_TRADE_SCAN=0          停全市场扫描（做T 预案停止更新）
   SCORE_HEALTH_CHECK=0    停评分有效性周检
   ```

### ★ 教训（重要，比 bug 本身重要）

**1. "不阻塞事件循环"只解决了"慢"，没解决"失败"**
   `to_thread` 让慢任务不卡事件循环，但如果它**反复失败**，
   就是**用另一种方式把资源吃光**（连接、线程、上游配额）。
   ⇒ 任何"定时 + 重活"的循环，**必须回答一个问题：失败了会不会重试？**

**2. 我在本地测了 72 秒 / 167 秒的耗时，却没把它和最坏重试次数相乘**
   单次 167 秒"看着能接受"，× 48 次就是 3.7 小时。
   ⇒ **评估重活要算"最坏累计占用"，不是"单次耗时"。**

**3. 线上重活应该有"总闸"**
   每个重活循环都该有 env 开关，出事能**不改代码就停掉**。
   这次是事后补的，本来一开始就该有。

### 影响面

- **做T 盘中触发（`t_trade_loop`）不受影响**：只读内存，很轻。
- 停掉两个重活后，做T 预案不再更新（`t_plans` 停在旧日期），但不影响已有预案的盘中判断。

用户："做T 交易台的池子不会自动加入吗？"

### ① 池子确实**不自动加**（有意设计）

全市场每天 **368 只可行**，全塞进池等于噪音。
**但持仓本来就自动被监控**（`watch_codes() = 持仓 + 池`），

**⇒ 修**：`get_pool(include_holdings=1)`（默认）把持仓一并返回，标 `source`：

| `source` | 含义 |
|---|---|
| `holding` | **仅持仓**（自动监控，不需要加池） |
| `pool` | 手动加入的观察标的 |
| `both` | 既是持仓又在池 |

**前端**：池子表加「来源」列；**仅持仓的行不显示"移除"**（移除无意义）。
概览卡口径 **「做T 池」→「监控范围」**。

### ② ★ 顺带发现：用户已把持仓加到 300 股，但**仍然做不了**

**根因是浮点精度，不是逻辑**：

```
ratio 存库 round 到 3 位 ⇒ 0.333
300 × 0.333 = 99.9  ⇒  //100 * 100 = 0
```

**而用户意图正是 100 股**（300 × 1/3）。

**修法两处**：
1. **`suggest_ratio`：`round(scaled, 3)` → `round(scaled, 6)`**
2. **`_floor_lot` 容忍"整手边界上 <0.01 股"的误差**
   判据：**四舍五入后正好是整手，且与原值差 <0.01** 才进位。
   - `99.99999 → 100` ✓（是误差）
   - `99.567 → 0` ✓（真的不够）
   - `199.6 → 100` ✓（差 0.4 股，不算误差）
   ⇒ **不会因为容差太宽造成实质超买**。

### ③ 历史数据修正（278 行）

```sql
UPDATE t_plans SET ratio = 0.333333
WHERE ratio > 0.3329 AND ratio < 0.3331
```

**⚠️ 坑**：`ratio` 是 `real`，库里实际是 `0.33300000429...`
⇒ **`WHERE ratio = 0.333` 匹配 0 行**，必须用范围比较。

### ④ 实测结果（关键）

```
修复前：粤高速 底仓300  buy_ok=False  可买0股  "99 股不足 100"
修复后：粤高速 底仓300  buy_ok=True   可买100股  ✓
```

**⇒ 明天盘中真的会触发了。**

**对照**：`ratio=0.2` 的票仍归零（`300 × 0.2 = 60 < 100`）——**这是正确的**，
因为 0.2 仓比 1/3 更小，本来就不够一手。

## ★★★ 价格到位 → 自动建**模拟底仓** → 自动做T（`17d6408e`）

用户："价格到位，系统自动处理。"

### 语义边界（这是本轮最重要的设计决定）

| 环节 | 自动化程度 | 原因 |
|---|---|---|
| 建仓点命中 | **自动建"模拟"底仓** | 用户明确要求自动处理 |
| 真实下单 | **永远不自动** | 没有券商接口，物理上不可能 |
| 盘中做T | 全自动（本就如此） | 60s 读内存行情，零额外请求 |
| 推送/记账 | 全自动，**文案标"模拟"** | 不能让人以为系统花了他的钱 |

**⇒ 全链路无人值守，但**：`user_portfolio`（真实持仓）**一个字节都没动**。

### 为什么必须新建 `t_sim_positions`

`user_portfolio` 结构（`backend/schema.sql:293`）**没有 `source` 列**：

```sql
CREATE TABLE user_portfolio (
    id SERIAL PRIMARY KEY, user_id, code, name,
    shares REAL, cost REAL, note TEXT DEFAULT '', created_at TEXT
);
```

自动写入 ⇒ 用户打开持仓页会看到"我买了 300 股云南铜业"，**而其实没买**。
⇒ 独立表 `t_sim_positions`，`holdings()` 合并两层、**真实优先**：

```python
holdings() = user_portfolio（sim=False） + t_sim_positions（sim=True）
             同 code 时**真实覆盖模拟**，不叠加
```

**为什么"不叠加"关键**：若真实 500 + 模拟 500 相加成 1000，
`calc_shares` 会算出 333 股可卖 —— **卖出了不存在的股票**。

### 触发链路

```
`t_trade_loop`? 不 —— 是 `trade_plan_trigger_loop`
  ↓ 计划 status='waiting' 且 plan_type='t_build'
  ↓ |现价/buy_price − 1| ≤ 2%
  ↓ `_plan_auto_build()` → `TX.auto_build()`
  ↓ 写入 t_sim_positions（股数 = max(300, min_base_shares(ratio))）
  ↓ 计划 status → **'filled'**（不是 'hit'，hit 语义是止损/兑现）
  ↓ 次日/当日盘中 `t_trade_loop` 就能对它做T
```

**为什么计划要闭环成 `filled`**：`trade_plan_trigger_loop` 只查 `status='waiting'`，
不闭环 ⇒ 60 秒一轮反复命中 ⇒ **重复建仓 + 推送刷屏**。

### ★ 用 `plan_type` 而不是匹配中文文案

`build_plan` 生成的计划 `plan_type` 由 `trial` 改为 **`t_build`**。

**为什么不能靠 `reason` 里"做T 底仓建仓点"这几个字判断**：
文案一改就失效，而且这个字符串在别处也可能出现（本项目已多次踩"字符串匹配"的坑）。

判定收敛成纯函数 `t_trade.should_auto_build(plan_type)`：
- `t_build` ⇒ 自动建
- `trial` / 空 ⇒ **只提醒**（普通试仓是用户自己的决策，系统不代劳）
- 总开关 `T_AUTO_BUILD=0`（默认开）

### 顺带修的三个问题

1. **`watch_codes()` 要含模拟底仓** —— 否则票从池里删掉后"建了仓却不做T"，
   比不建更糟（白占一个仓位假设）。
2. **`resolve_name()` 抽出来共用** —— `add_sim` 不传 name 时显示成代码本身。
3. **`get_sim` 的 `total` 只算 holding** —— `data` 含 closed 历史行，
   用 `len(data)` 会让"模拟仓 N 只"越用越大。

真实优先              同 code 不叠加 ✓

## ★★★ 企微每 5 分钟重复「日终观察」的根因：日期格式斜杠 vs 横杠（`099308ed`）

用户："企微今天盘后一直收到日终观察：3个破位/0个新主题的相同内容"

### ★ 根因（查库实证）

```
schedule_state:  watch_alert:2026-11-16 | 2026-11-16   ← 标记明明已写
store.is_schedule_done(tag) = False                     ← 判定却不认
store._bj_date()            = '2026/11/16'             ← 斜杠（老项目兼容格式）
```

`watch_alert.run_daily()`：
- **写**：`mark_schedule_done(tag, day)`，`day = strftime("%Y-%m-%d")` ⇒ **横杠**
- **读**：`is_schedule_done(tag)` 不传日期 ⇒ 内部 `_bj_date()` ⇒ **斜杠**

**⇒ 字符串比较永远不等 ⇒ "一天一条"退化成 20:00~23:59 每 5 分钟重推。**

### 为什么只有这一个模块中招

全项目 **50+ 处**调用 `is_schedule_done` / `mark_schedule_done`：
- 绝大多数**写和读都不传日期**（斜杠 ↔ 斜杠）⇒ 一致，没事
- 少数**都显式传 `day`**（横杠 ↔ 横杠）⇒ 也一致
- **只有 `watch_alert` 是"写传 day、读不传"的混用** ⇒ 唯一中招

⇒ 这与今天早些时候的"失败重试风暴"是**两类问题**：
那次是"失败后标记没写"，这次是"标记写了但读不出来"。

### 修法（两层）

**① store 层根治**：`_norm_schedule_date()` 把日期统一为 `YYYY-MM-DD`
```python
def _norm_schedule_date(v):
    return str(v or "").strip().replace("/", "-")[:10]
```
`mark_schedule_done` / `is_schedule_done` 两边都规范化。

**★ 历史斜杠数据不用迁移**：读的时候规范化即可匹配。
**★ 保留 fail-open 语义**：DB 真读不到仍返回 False（下轮重试），
**不要把"格式不同"也当成 fail-open** —— 那正是本次根因。

**② 调用方双保险**：`watch_alert` 改成 `is_schedule_done(tag, day)` 显式传；
`_last_push_date()` 也规范化（否则"主题距今几天"会把同一天算成不同天，
