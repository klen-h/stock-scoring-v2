# 2026-11-16（周一）

## ★★★ 线上全站超时：我昨天加的两个循环"失败即重试"（`b60e4551`）

用户："线上怎么接口请求都超时了？"

### 责任在我

这两个循环是 **2026-11-15 我加做T 与评分告警时新写的**，
写的时候只想着"不阻塞事件循环"（用了 `to_thread`，这点是对的），
**没想"失败了会怎样"**。

### 根因：成功后才写"已跑过"标记

```python
# 错误写法（我写的）
if (条件 and _LAST["day"] != d):
    rep = await asyncio.to_thread(重活)     # ← 可能抛异常 / 超时被中断
    _LAST["day"] = d                        # ← 只有成功才写
except Exception:
    print(...)                              # ← 失败 ⇒ 标记没写 ⇒ 下一轮又跑
```

**⇒ 一旦失败就变成每 N 秒重试的**风暴**。**

### 定量（这才是致命的）

| 循环 | 单次耗时 | 重试间隔 | 最坏次数 | 累计占用 |
|---|---|---|---|---|
| `score_health_loop`<br>`get_bucket_stats(120)` | **167 秒**（本地实测） | 600 秒 | 16:00~24:00 最多 **48 次** | **≈13360 秒 ≈ 3.7 小时** |
| `t_trade_scan_loop`<br>`scan_market`（全市场 1025 只） | **72 秒** | 300 秒 | 全天反复 | **≈24% 时间** |

**⇒ 两个叠加，数据库连接被长期占满 ⇒ 所有接口排队 ⇒ 全站超时。**

### 修法（`b60e4551`）

1. **先占位再跑**：进 if 就写标记，**成败都算"已跑过"**，异常只留痕不重试。
2. **`get_bucket_stats` 窗口 120 → 60 天**：单次负载减半，结论方向不变。
3. **加两个应急开关**（默认开，可 env 关）：
   ```
   T_TRADE_SCAN=0          停全市场扫描（做T 预案停止更新）
   SCORE_HEALTH_CHECK=0    停评分有效性周检
   ```

### ★ 教训（重要，比 bug 本身重要）

**1. "不阻塞事件循环"只解决了"慢"，没解决"失败"**
   `to_thread` 让慢任务不卡事件循环，但如果它**反复失败**，
   就是**用另一种方式把资源吃光**（连接、线程、上游配额）。
   ⇒ 任何"定时 + 重活"的循环，**必须回答一个问题：失败了会不会重试？**

**2. 我在本地测了 72 秒 / 167 秒的耗时，却没把它和最坏重试次数相乘**
   单次 167 秒"看着能接受"，× 48 次就是 3.7 小时。
   ⇒ **评估重活要算"最坏累计占用"，不是"单次耗时"。**

**3. 线上重活应该有"总闸"**
   每个重活循环都该有 env 开关，出事能**不改代码就停掉**。
   这次是事后补的，本来一开始就该有。

### 影响面

- **做T 盘中触发（`t_trade_loop`）不受影响**：只读内存，很轻。
- 停掉两个重活后，做T 预案不再更新（`t_plans` 停在旧日期），但不影响已有预案的盘中判断。

## 止血成功 + 加固（`19382c07`）

用户："接口通了。"

### 当前状态（**必须知道**）

```
T_TRADE_SCAN=0         → 做T 预案不再每日更新（t_plans 停在旧日期）
SCORE_HEALTH_CHECK=0   → 评分有效性周检停跑
```

**⇒ 接口恢复，但这两个功能是关着的，不是"全好了"。**

### 加固两件（为安全重开做准备）

**① 耗时日志**

上次故障之所以难定位，是因为**"跑多久"没有任何日志**——只有"接口都超时了"这个现象。

现在两个循环跑完都打印 `[xxx] done in Ns`，超 180 秒额外打 `WARN`。
⇒ 下次能在"开始变慢"时就发现，而不是等它把库打满。

**② 时间窗错开：`score_health` 16:00 → 20:00**

原定周一 16:00，与盘后全市场扫描（15:40 起）**撞在同一时段**——
两个重活一起打库正是上次超时的**放大因素**。
挪到 20:00：夜间无人访问，慢一点也无感知。

### 建议的重开节奏（分步，别一次全开）

| 步骤 | 动作 | 观察 |
|---|---|---|
| 1 | 只开 `T_TRADE_SCAN`（一天一次，~72s） | 看日志 `[t-trade] scan done in Ns`，接口是否仍正常 |
| 2 | 稳定 1~2 天后，开 `SCORE_HEALTH_CHECK`（一周一次，~80s） | 看日志 `[score-health] bucket_stats done in Ns` |
| 3 | 若单次耗时 >180s ⇒ 再压（减少窗口/候选池）或降到每月一次 | — |

**⇒ 分步开**：上次就是两个一起上，出事时分不清是谁的锅。
