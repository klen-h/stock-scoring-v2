3. **唯一带 LLM 解读的规则**（用户三想法的落地）：prompt = 触发事实 +

## 🔧 Render OOM 诊断：`/api/system/memory` + 首页展示（`97870ec` / `bc5295d`）
**用户提供监控图（关键证据）**：内存呈**锯齿状反复** —— 从 ~10% **缓慢爬升**到 80~90% →
**骤降**（进程被杀 + Render 自动重启），48 小时内**至少 3~4 次**；同期 **CPU 长期 <5%**。
⇒ ① 不是算力不足，是内存；② 形态是「**几小时累积爬升**」而非瞬时尖峰 ⇒ 要回答的是
「**谁在涨**」，而总 RSS 曲线做不到这一点。**用户确认实例上限 = 500MB**。

**① 端点 `GET /api/system/memory`**（`backend/app/routers/system.py`，鉴权同 `/status`）：
- `process`：RSS / 历史峰值 / 上限 / 占用% / 线程数（优先读 `/proc/self/status`；回退
  `resource.getrusage` 并**区分 Linux=kB 与 macOS=bytes** —— 混用会差 1024 倍）
- `caches`：**52 项模块级缓存探针**（按占用降序，含条目数）
- `types`：GC 存活对象按类型计数 Top（找「某种对象异常多」的泄漏特征；RSS>85% 或 `types=0` 自动跳过）
- `diff`：与**上一次调用**对比的增量清单 ⇒ **核心用法 = 调两次看谁在涨**；`reset=true` = 进程重启过
- `summary`：人类可读 markdown 一段（curl / 前端 / 未来告警复用同一段文本）

**② 首页展示**（`Dashboard.vue`「数据新鲜度」卡片内 + `api.getSystemMemory`）：

时间序列** —— 用户无需手动调两次，也**不需要新增告警通道**（零噪音风险，符合项目对噪音的敏感度）。
占用配色：≥85% 红 / ≥70% 琥珀 / 否则绿。

**★ 实现要点（都是踩过的坑）**：
1. **探针只读 `sys.modules`（不主动 import）** ⇒ 零副作用；且未加载的模块本来就不占内存，
   报 0 反而误导

   会直接压垮进程
3. **采样必须取「前 N + 末尾 N」**：新增数据总是**追加在末尾**，只采头部会被平均掉 ——

4. **diff 同时报 MB 与精确条目数**：MB 是采样估算（有 ±），条目数是精确计数，双维度互补
5. 采样数随深度衰减（25→12→6→3→1）防分支爆炸
