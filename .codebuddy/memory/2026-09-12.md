### 归因方法修正（重要教训）
按"**返回行数**"排序会系统性漏掉「行少但每行很大」的读。改用

新 Top（MB/天）：flash_news SELECT * 60（已修）/ **kline_cache 单只 55** /
backtest_prices 单只 50（已修）/ mainflow 整表 42（已修）/ flash_analyses 40（已修）/
**flash_reviews SELECT * 32** / **market_snapshot 整份 17** / **tracking_state 整份 15** /
backtest_prices 批量 40（已修）/ **macro_history 8**。
→ 未修合计 ≈127MB/天，全是同一模式：**一份大 JSON 被反复整份读**（宽列 + 高频 + 数据每天只变一次）。
→ 面板 `SLOW QUERIES 153` ≈ 本地算的「均值 >100ms 语句 157 条」✓；资源全空闲（CPU 3%/IO 1%/连接 11/60）
  说明瓶颈纯粹是"搬的数据量"。Cached Egress 只适用 Storage，对我们无用（已查官方文档）。

### ① kline_cache 30 万次回退查库的根因（已定位 + 已修，待用户提交）
1. **`pack_source._is_stale()` 日历漏洞（主因）**：判定式 `pack_date < (今天的最近工作日 - 1 自然日)`，
   周一时右侧落到**周日**，而最新包是**周五**的 → `周五 < 周日` 成立 → **整个周一（到 21:30 当天包发布前）
   判包陈旧 → 所有 K 线读取（打分/战法闸门/详情页）全部回退查库**。长假后首个交易日同样中招。
   实测推演：周一 09:00/12:00/15:00/20:00 stale=True，22:00 转 False。
2. **`get_cached_klines_batch()` 没有 pack 通道** → 无条件 `WHERE code IN (…1567 只)` 查库，
   一次 ~10MB 的 kline_data 整包过网（16 次调用返回 2.5 万行）。
3. 单只读 30.4 万次里有 **40% 返回 0 行**（表中根本没有该代码）——包覆盖后这部分也自然消失。

**修复**：新增交易日历感知的 `_latest_available_pack_day()`（交易日 21:30 后=当天，否则=上一个交易日，
**节假日感知**），`_is_stale()` 与 `_pack_outdated()` 统一改用它；`get_cached_klines_batch` 改为先包后库只查差额。
验证：周六/周一 10:00/15:00/20:00 → 09-11（不再误判）；周一 22:00/周二 → 09-14；
**国庆后首个交易日 10-08 → 09-30**（长假坑一并修好）；`_pack_outdated` 周一不再每 30 分钟重下 127MB 包。

    不如 GitHub Pages（100GB/月免费，已在用）。

- 官方降耗建议就是我们已做的四条：精简 SELECT 列 / 少返回行 / 用缓存降调用频率 /
