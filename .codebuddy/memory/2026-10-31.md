### 两张表
- `thesis_registry`：假设登记簿（claim / nature / p_mine / p_market / market_source /
  market_as_of / deadline / resolution_rule / resolution_source / invalidation_early /
  status / backfilled / created_by / created_at）
- `thesis_events`：append-only 事件（register / revise / invalidate / evidence_manual / resolve）

### 三条铁律（本模块地基）
1. **claim / resolution_rule 登记后不可改**，只能 `revise`（改概率，必带 reason + trigger）或 `invalidate`
2. **裁决权不在 LLM**，按结构化 `resolution_rule` 求值
3. **没有 deadline / 失效条件的"长期观点"不允许登记**（那是信仰）

### 评审追加的"三刀"（缺一刀就退化成自我安慰工具）
1. `backfilled=1` **永久排除统计**（回填 9/16 样本只做 schema 演示）
2. **状态类命题不进本表**（滞胀 ON / 市场底清单 2/6 归 `scenario_watch`/`stagflation`），
   故 `nature` 只有 `prediction` / `decision`
3. **N≥30 前不产出 Brier / 折扣系数**，`stats()` 只报计数

### 双库坑规避（评审重点提醒）
- `SERIAL` 在 SQLite 不自增 → 按 `db.is_postgres` 分支：
  PG 用 `SERIAL PRIMARY KEY`，SQLite 用 `INTEGER PRIMARY KEY AUTOINCREMENT`
- JSON 一律存 **TEXT**（`resolution_rule` / `payload`），读取 `_loads()` 兼容
  "原始串 / 驱动已解析对象"两种形态
- 占位符统一 `%s`（`db` 内部自动转 `?`）
- **`db.insert()` 返回的是 rowcount 不是 id**（`insert` → `execute` → `cur.rowcount`），
  必须 `SELECT ... WHERE claim=%s ORDER BY id DESC LIMIT 1` 回查

### 踩到并修掉的 bug
`_now_bjt()` 返回 **aware** datetime（`datetime.now(timezone.utc) + 8h`），
与 `_parse_dt()` 的 **naive** 比较抛
`TypeError: can't compare offset-naive and offset-aware datetimes`。
修法：`.replace(tzinfo=None)`。
**凡是"UTC 加偏移"得到的时间，都必须显式去 tzinfo 才能和 naive 比较。**

### 自测（隔离 SQLite 临时库，不碰生产）
10 项全 PASS：斜杠日期解析排序、auto 条件 win/lose、manual 缺证据**保持 open**（不判 lose）、
录入证据后 win、修订留痕 old_p/new_p/reason、空 reason 被拒、状态类命题被拒、
backfilled 排除统计（resolved_live=3 而非 4）、同 claim 幂等。
卫生门：**无新增违规**（baseline 未升）。

### 第三张表 `thesis_evidence`（全局每日一份）
```sql
CREATE TABLE thesis_evidence (
    date TEXT PRIMARY KEY,   -- 证据日期（交易日）
    as_of TEXT,              -- macro_daily 快照日期（可能 != date，如周六补跑）
    data_ts TEXT,            -- 抓取时刻（UTC）
    payload TEXT,            -- JSON：{as_of, assets{...}, derived{...}}
    created_at TEXT
)
```

### 抄哪些（`_EVID_ASSETS` 白名单 11 项）
`brent / wti / gold / silver / copper / us10y / dxy / usdcnh / nasdaq / a50 / vix`

**不抄整份 panel**：存储已 408MB/500MB，每日整份落库是浪费；这 11 项覆盖
"滞胀 / 利率冲击 / 衰退"三档所需的全部判别变量（含**黄金**这个裁决变量）。

### 三个设计选择（都有明确理由）
1. **抄值不引用**：`macro_daily` 的行会被重算/改写（历史回填、口径调整），
   直接引用等于让历史证据随今天的数据漂移 —— 那就不是证据。
2. **`date` 用 `_batch_trading_day()`**（不是 `_now_bjt()`）：与日批其他表口径一致；
   周末补跑时 `date` 与 `as_of` 都是周五，不会凭空产生"周六一行"。
3. **失败不抛**：证据缺一天不影响主链；裁决器 v1 仍直接读 `macro_daily`。

### 日批接入
- `task_thesis_evidence()` 定义在 `task_stagflation` 之后
- `TASKS` 注册 + `DEFAULT_ORDER` 紧排 `"stagflation"` 之后（同依赖 macro_daily 当日快照）

## 003 补上最后一块：裁决器接入日批（`task_thesis_resolve`）

用户问"还需要继续吗"时发现的关键缺口：**`resolve_open_theses()` 只存在于 CLI，
日批没有任何任务调用它** ⇒ 12/9 FOMC 决议后不会有任何进程自动裁决，
假设会**永远停在 open**。

**"登记了却永远不结算"比判错更糟** —— 预登记纪律的全部意义在"到期必结算"，
不结算等于把预登记退化回"事后回忆"。

### 实现
```python
def task_thesis_resolve():
    r = tt.resolve_open_theses()      # 只处理 deadline 已过的
    # 汇总：done(resolved_win/lose) / pending(待人工录入)
```
- 注册 `TASKS["thesis_resolve"]`
- `DEFAULT_ORDER` 紧排 `"thesis_evidence"` 之后（语义：证据先采、裁决后跑）
- 未到期 skip 不算失败；manual 缺证据保持 open 并报 `#id 待录入`

### 验证
```

HYGIENE_PASS
```
（当前 id=1 未到期、id=2 已 resolved ⇒ 正确返回"无到期"。）

### 12/10 之后的实际时序（提前写清，避免误判"没自动结算=坏了"）
| 时刻 | 发生什么 |
|---|---|
| 12/09 22:00 BJT | 日批跑 → 决议还没出（03:00 才出）⇒ skip |
| 12/10 03:00 BJT | FOMC 决议 + 点阵图公布 |

## 004 滞胀状态位补上第四变量「黄金」（讨论过但一直没落地的那项）

用户："做 ①"（10-31 盘点的三件未完成中最小、最直接修正确性的一件）。

### 问题
`_raw_hit()` 只有油/债/美元三条 —— 但**滞胀与衰退前夜在这三个维度上是同一组输入**，
状态位永远只能标"滞胀"，分不开两者。而 checklist 第⑤条的观察锚是随剧本切换的
（滞胀看油、衰退前夜看黄金+breakeven）⇒ **标签分不开，第⑤条就可能一直盯错指标**。

### 修法（`backend/app/stagflation.py`）
- 新增 `STATE_PRE_RECESSION = "衰退前夜"`；
- `_raw_hit()` 签名改为 `(hit | None, gold_dir | None, evidence)`，
  `gold_dir ∈ {"up","down","flat",None}`（**None=缺数据 ≠ flat**）；
- 口径：`|gold.change_pct| <= 0.2%` 为 flat（死区），连续 **2 日**同向才确认；
- 状态机：
  ```
  退出：组合不成立持续 2 日 → 正常（两个风险档都退）
  进入：组合成立持续 2 日 ─┬ 黄金跌≥2日 → 衰退前夜
                          ├ 黄金涨≥2日 → 滞胀交易
                          └ 方向未确认  → 保守默认滞胀（不因单日就走更严重的档）
  ```
- flat 会**重置**方向计数（不把"涨-中性-涨"算成连续）；缺数据**不动**计数
  （不能用"没观测"推翻已有判断）。
- `load()` 新增 `is_pre_recession` / `is_alert`，`advisory` 分档文案。

### 前端（`MacroEnvCard.vue`）
- 横幅条件 `is_stagflation` → **`is_alert`**（覆盖两档）
- 衰退前夜用 **rose** 色（比滞胀更该降仓），滞胀仍 amber
- 证据行加黄金，但用**方向箭头 ↑/↓/→ 而不是 ✓/✗** ——
  衰退前夜时"黄金跌"才是支持证据，用 pass 的 ✓/✗ 会被误读成"这项不满足"
- hover 提示加"黄金（裁决变量）：涨>0.2%=滞胀 / 跌<-0.2%=衰退前夜"

### 实测（全量重算 41 日）
```
2026-10-22 正常     hit=1 gold=down -0.43
2026-10-23 衰退前夜  hit=1 gold=down -0.41   ← 连续 2 日 ⇒ 切档
2026-10-26 衰退前夜  hit=1 gold=down -0.26
2026-10-27 衰退前夜  hit=0 gold=down -0.38
2026-10-28 正常     hit=0 gold=flat  0.03    ← 组合不成立 2 日 ⇒ 退
2026-10-29 正常     hit=1 gold=flat -0.07    ← flat 重置方向计数
2026-10-30 滞胀交易  hit=1 gold=down -0.26   ← 只跌 1 日，未达确认 ⇒ 保守滞胀
```
历史分布：正常 37 / 滞胀 1 / **衰退前夜 3**。
`load()` 当前：`state=滞胀交易`、`is_alert=true`、`run_on=2`。

### ⚠️ 必须知道的副作用
`compute()` 是**全量重算**（滞回依赖前日状态），所以口径一改，
**历史行会被重写**：`2026-10-23~10-27` 从原来的「滞胀交易」变成了「衰退前夜」。
这不是 bug，是"口径变更后历史必须按新口径重算"的必然结果 ——
但解读历史简报时要记得这一点，别以为当时系统就标了衰退前夜。
