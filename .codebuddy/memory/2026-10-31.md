### 双库坑规避（评审重点提醒）
- `SERIAL` 在 SQLite 不自增 → 按 `db.is_postgres` 分支：
  PG 用 `SERIAL PRIMARY KEY`，SQLite 用 `INTEGER PRIMARY KEY AUTOINCREMENT`
- JSON 一律存 **TEXT**（`resolution_rule` / `payload`），读取 `_loads()` 兼容
  "原始串 / 驱动已解析对象"两种形态
- 占位符统一 `%s`（`db` 内部自动转 `?`）
- **`db.insert()` 返回的是 rowcount 不是 id**（`insert` → `execute` → `cur.rowcount`），
  必须 `SELECT ... WHERE claim=%s ORDER BY id DESC LIMIT 1` 回查

### 踩到并修掉的 bug

与 `_parse_dt()` 的 **naive** 比较抛
`TypeError: can't compare offset-naive and offset-aware datetimes`。
修法：`.replace(tzinfo=None)`。
**凡是"UTC 加偏移"得到的时间，都必须显式去 tzinfo 才能和 naive 比较。**

## 004 滞胀状态位补上第四变量「黄金」（讨论过但一直没落地的那项）

用户："做 ①"（10-31 盘点的三件未完成中最小、最直接修正确性的一件）。

### 问题
`_raw_hit()` 只有油/债/美元三条 —— 但**滞胀与衰退前夜在这三个维度上是同一组输入**，
状态位永远只能标"滞胀"，分不开两者。而 checklist 第⑤条的观察锚是随剧本切换的
（滞胀看油、衰退前夜看黄金+breakeven）⇒ **标签分不开，第⑤条就可能一直盯错指标**。

### 修法（`backend/app/stagflation.py`）
- 新增 `STATE_PRE_RECESSION = "衰退前夜"`；
- `_raw_hit()` 签名改为 `(hit | None, gold_dir | None, evidence)`，
  `gold_dir ∈ {"up","down","flat",None}`（**None=缺数据 ≠ flat**）；
- 口径：`|gold.change_pct| <= 0.2%` 为 flat（死区），连续 **2 日**同向才确认；
- 状态机：
  ```
  退出：组合不成立持续 2 日 → 正常（两个风险档都退）
  进入：组合成立持续 2 日 ─┬ 黄金跌≥2日 → 衰退前夜
                          ├ 黄金涨≥2日 → 滞胀交易
                          └ 方向未确认  → 保守默认滞胀（不因单日就走更严重的档）
  ```
- flat 会**重置**方向计数（不把"涨-中性-涨"算成连续）；缺数据**不动**计数
  （不能用"没观测"推翻已有判断）。
- `load()` 新增 `is_pre_recession` / `is_alert`，`advisory` 分档文案。

### 前端（`MacroEnvCard.vue`）
- 横幅条件 `is_stagflation` → **`is_alert`**（覆盖两档）
- 衰退前夜用 **rose** 色（比滞胀更该降仓），滞胀仍 amber

- hover 提示加"黄金（裁决变量）：涨>0.2%=滞胀 / 跌<-0.2%=衰退前夜"

## 006 Supabase 402 应急：数据库全量导出到本地

用户收到 Supabase **402 Egress Exceeded**（API 被限制，项目无法服务），
要求"先把数据库拉到本地，项目之前也有迁移过"。

### 三个关键事实（决定方案）
1. **402 只限制 PostgREST/API，PostgreSQL 直连（6543 池化）仍可用**
   —— 实测 `SELECT 1` 成功、111 张表可读 ⇒ **存在备份窗口**（这是最要紧的发现）。
2. 本机**没有** pg_dump / psql / docker（`where` 全空）
   ⇒ `deploy/migrate_supabase.sh`（依赖 docker 跑 pg_dump）**用不了**。
3. 本机**没有** PostgreSQL 服务（5432 无人监听）
   ⇒ 恢复只能走 **SQLite**（项目原生支持）或等装 PG。

### 新增三个脚本
| 脚本 | 作用 |
|---|---|
| `scripts/dump_remote_db.py` | 逐表 `COPY (SELECT *) TO STDOUT WITH CSV HEADER` → `.csv.gz`。**流式写盘**（大表不进内存），不用服务端游标（兼容 6543 事务池） |
| `scripts/dump_schema.py` | 导 `information_schema` 的**列类型/主键/索引** → `_schema.json` |
| `scripts/restore_local_db.py` | 恢复到 PG（`COPY FROM`）或 SQLite（逐行 insert），按 `_schema.json` 建对类型 |

**为什么必须单独导 schema**：CSV 没有类型。全建 TEXT 会让
`ORDER BY score DESC` 按**字符串**排序（"9" > "10"）⇒ 榜单顺序全错、`SUM()` 失效。

### 导出取舍（402 下限速 ~3-7 KB/s ⇒ 必须砍体量）
- **排除可重建的大表**（省 201MB）：`backtest_prices`(124MB) / `kline_cache`(41MB) /
  `indicator_cache`(14MB) / `ranking_live`(11MB) / `mainforce_state`(11MB)
- **必导不可重建**：`mainflow_history`(98MB) / `stock_finance_zz`(23MB) / `lhb_history`(22MB)
- 目录 `db_dump_20261031/`（已加 `.gitignore`）

### 踩到的两个坑
1. **Windows 控制台 GBK**：`✓/✗/⚠️/⇒` 抛 `UnicodeEncodeError`。
   `dump_schema.py` **文件已写成功**（178KB）却因最后一行 print 异常退出
   ⇒ 极易误判成"没导出来"。修法：`sys.stdout.reconfigure(encoding="utf-8", errors="replace")`。
2. **重定向到文件时 Python stdout 是块缓冲（4KB）** ⇒ 日志会"停住"，
   **不代表进程死了**；用**目录文件数**判断进度才准。

### 导出结果（14:40 全部完成）
```
schema 表数      : 111
manifest 导出数  : 106 / 111   （排除 5 张可重建的）
失败表           : 无
csv.gz           : 106 个 / 24.61 MB
总行数           : 588,620
mainflow_history : 11.22 MB（373,528 行）

```
**排除的 5 张**（可从 `backend-pack` 重建）：`backtest_prices` 124MB /

### 三个坑（全部是"静默挂死"，不报错）
1. **单条大 COPY 无限等待**：`COPY (SELECT * FROM mainflow_history) TO STDOUT`
   在 402 限流下让 `copy_expert` 永不返回（文件 0 字节、进程活着、
   `pg_stat_activity` 查不到会话）。⇒ 按 `id` keyset 分批。
2. **一次 `gzip.open('wb')` 连写多批会卡死**：同一条 SQL 单独跑 13~23 秒，
   但用同一个 GzipFile 句柄循环 `copy_expert`，**第一批就卡**。
   ⇒ **每批 `gzip.open('wb'/'ab')` + 立即 `close`**（多 member 拼接是合法 gzip）。
   `close` 还保证 flush —— 否则块缓冲让文件长期显示 0 字节，看起来像卡死。
3. **`--tables` 单表重跑会覆盖 manifest**：数据完好但清单变成 1 张（本次实际发生）。
   ⇒ 新增 `scripts/rebuild_manifest.py`（扫目录 + 数行数 + `_schema.json` 补列名）。

## 007 P2：DDL 跨进程跳过 —— 19.46GB egress 的真根因（`database.py`）

用户贴出 Render 日志：**每 2 分钟重启一次**（01:55:36 → 01:57:36），
每次重启都重跑整套 DDL。用户判断"流量是无限重启导致的"——方向对，机制要拆开。

### 根因
```
Render 重启 → init_tables() + 各模块 ensure_table() 重跑 111 张表 DDL
  → PostgREST 对**任何 DDL**（哪怕 IF NOT EXISTS 什么都不做）
    都触发 schema cache 全量重载（重拉全部 relation）
  → 30 次/小时 × 每天 24h × 30 天 ≈ 21~42 GB   ← 与 19.46 GB 完全吻合
```
`_DDL_DONE` 只做**进程内**去重，**跨重启完全失效**——每次重启都是新进程。

### 改法（全部集中在 `backend/app/database.py`）
1. **`execute()` 跨进程判断**：DDL 前先查目标是否已存在，存在则跳过执行。
2. **`init_tables()` 整体跳过**：解析 `schema.sql` 的 30 张表，**全部存在则直接 return**。
3. **进程级 relation 缓存 `_public_relations()`**：一次 `pg_class` 查询拉全 public，
   之后所有判断零网络。
   ★ 这是关键：远程节点**单次往返实测 1.3s**，逐个 `to_regclass` 反而要 145s，
     比它省下的 DDL 还慢 —— **缓存把优化从"更慢"救回"更快"**。
4. `_DDL_SKIPPED` 计数，`init_tables` 结束时打印。

### 实测
```
init_tables: 2.50s      （打印"schema.sql 的 30 张表均已存在 ⇒ 跳过 init_tables"）

## 011 "懒加载省内存/egress"可行性 —— 数据不支持，但指出真正的峰值点

用户问：几乎只看工作台，能否做懒加载省 Render 内存与 egress。

### 实测（`memory_probe`，2026-10-31 16:12，Render 现役实例）
```

├─ 具名缓存   41.8 MB  ← 仅 14.6%

1. **省日常驻留内存的上限 = 41.8 MB（14.6%）** ⇒ 不值得做。
2. **egress 与内存是同一枚硬币**：缓存吃内存但正是它挡住 egress；

   ⇒ **周末/盘后全量灌 5258 只**，而工作台只需自选+榜单 Top N（~150~300 只，<4%）。
4. 但已有护栏 `mem_guard.guard("restore_market_snapshot")` 高压降级为只恢复 `_valid_codes`；
   当前 286.7 MB 说明护栏可能在拦，或 100~200MB 估计偏高 —— **需看 mem_guard 实测日志才能定**。

### 结论：现在不该动
- 内存 56%，距 OOM 还有 225 MB，且 10-25 已治住爬升；
- egress 主体已确认是历史累积（`DATA_SOURCE=pack` 用户已确认）；
- 改 `restore_market_snapshot` 是**动启动主路径**，改错 = 周末首访工作台空白 30~60s。

### 若将来要做，最小改法
不动加载逻辑，只收窄恢复范围：非交易时段只恢复「自选 ∪ 近期榜单 ∪ 扫描结果」子集。
