### 四、为什么修复版（0acecde，21:30 已上线）没挡住
- `/api/health` 实测 `build=0acecde` ⇒ 部署没问题。
- 但 `_load_gate_bars` 的新鲜度守卫是这样写的：**缓存末日 < 最新信号日 ⇒ 整批回源
  `_load_prices_map`（366k 行）**。而盘后信号日=今天、本机缓存往往停在前一天

- 旁证：事后 2 分钟实测四条重语句 **增量为 0**（不是持续泄漏，是当时的批量/脚本一次性打的）。

## 103 GitHub Actions 不可用时的本地跑法（用户问"能直接在我本地跑吗"）

**能**：三个 workflow 本质都是普通 Python 脚本；Actions 只多做两件事 ——
① 用 peaceiris 把包推到 gh-pages（本地有 `scripts/publish_packs_local.py` 等价物，走 SSH）；
② `workflow_run` 串行 + `POST /api/system/batch-done` 企微通知（本地跑不会触发，无碍）。

顺序（**两条包不要并发**，同一出口 IP 会抢 WAF 配额）：
```powershell
cd d:/stock-scoring/stock-scoring-v2
$env:PYTHONIOENCODING="utf-8"
$env:PACK_QPS="1"; $env:PACK_QPS_MIN="0.3"
$env:PACK_WAF_COOLDOWN="120"; $env:PACK_WAF_MAX_COOLDOWN="600"

# 1) 前端包（2144×150，1~3h）
python scripts/generate-kline-pack.py --output-dir backend/data/kline ^
  --quotes-file backend/data/kline/realtime-quotes.json --days 150
# 2) 资金流强口径前置（5~10min）
python scripts/daily_batch.py --tasks mainflow --no-pack-check --no-quotes
# 3) 后端包（2915×750 + 指标 + 主力，2~4h）
python scripts/generate_backend_pack.py --output-dir backend/data/kline ^
  --quotes-file backend/data/kline/realtime-quotes.json
# 4) 发布（force push 单 commit 到 gh-pages；先 dry-run）
python scripts/publish_packs_local.py --dry-run
python scripts/publish_packs_local.py
# 5) 等 Pages CDN 1~2 分钟后同步到读侧目录
python scripts/sync_local.py
# 6) 日批（DATA_SOURCE=local ⇒ K 线/指标读本地包，零 Supabase）
$env:DATA_SOURCE="local"
python scripts/daily_batch.py --tasks all
```
要点：
- 生成目录必须是 `backend/data/kline`（`publish_packs_local.py` 的 DATA_DIR），不是根目录 `./data/kline`。
- `publish_packs_local.py` 会把 `frontend/dist` 一并带上（否则 gh-pages 页面 404）⇒ dist 陈旧时先 `npm run build`。
- `daily_batch` 的 `ensure_pack_fresh` 会等包日期；包已就绪仍报错才用 `--no-pack-check`（否则会错日期落库）。
- 本地日批会写 `batch_runs` ⇒ 之后 Actions 恢复时当天会被正确跳过（幂等）。
- 本机 IP 若已被 WAF 罚过，`[WAF]` 会持续出现；脚本已会 120→240→480→600s 退避 + ×0.6 降速，别手动并发重跑。

### 时间模型（用户问"为什么这么久，能不能取舍"）
- 耗时 = **请求数 ÷ 实际放行速率（≈0.3~0.4 QPS）**，与每只拉多少根**无关**：
  前端 2144 只 + 末根补齐 ~700 + 行情 ~300 ≈ 3100 请求 ⇒ 2.5~3h；
  后端 2915 只（+重试）⇒ 2.5h；日批 38 任务 ≈ 1.5h。
- **无效的提速手段**：把 750 根降到 260 根（请求数不变）、加 workers（全局限速）、调高 QPS（撞墙后更慢）。
- **有效取舍**：
  ① 跳过前端包（只影响浏览器本地评分，后端榜不受影响）→ 省 2.5h；
  ② `generate_backend_pack.py --max-codes N`（2026-10-22 新增，默认 0=不限制）——按市值截断，
     1500 只 ⇒ 后端包 ~70min；代价是未进包的小市值票未命中时回源 Supabase；
  ③ 日批只跑核心任务（见下），跳过 `backtest_preheat`/`weekly_report`/`zz_*`/`pattern_launch_scan` 等；
  ④ 双网络（Wi-Fi + 手机热点）并行两条包 —— WAF 按 IP 计，墙钟取 max 而非相加；
  ⑤ 前端包改**每周 2~3 次**（150 根数据，浏览器端可容忍滞后 1~3 天）。

### 106 "增量包可行吗"——实测与结论
- ★ **腾讯 fqkline 不支持单请求多股票**（2026-10-22 实测）：
  `param=A;b` / `A|B` / `A&param=B` 都返回 `{"msg":"param error"}`；
  重复 `param=` 只返回**最后一个** symbol。⇒ **一票一请求是硬约束**，
  增量（只拉最近几根）**不会减少请求数 ⇒ 不会缩短墙钟**（2876 ÷ 0.35 QPS ≈ 137 分钟）。
- 增量能省的是：响应体（~130MB → ~2MB）、解析/内存/落盘、发布体积，**不是时间**。
- ⚠️ **前复权（qfq）不能盲目追加**：除权后腾讯会把**历史序列整体重算**，
  只追加最后一根会让新旧复权基准混在一起（静默错历史）。真要做增量必须：
  ① 多拉最近 ~5 根与上一份包**重叠校验**；② 不一致 ⇒ 该只整段重拉。
- 前端其实**已有** `kline-delta-YYYYMMDD.json` + `applyDelta()`（`klineDB.js`），
  但 Actions 是全新 checkout ⇒ `load_previous_pack()` 拿不到上一份包 ⇒ `prev_data=None`
  ⇒ **delta 从未生成**，artifact 也没上传它 ⇒ 目前是死代码。
  补上"下载上一份包 → 生成 delta → 上传"只省**浏览器下载**，不省生成时间。

### 107 ★ zzshare 才是"绕开腾讯配额"的正解（2026-10-22 实测通过）
- **按天一次拿全市场**：`api.daily(trade_date=YYYYMMDD, fields='all', limit=6000)`
  返回 **5576 行 / 1 次请求 / ~0.5~3s**，含 `open/high/low/close/pre_close/pct_chg/
  volume/amount/factor/high_limit/low_limit/turnover_rate/amp_rate/is_st/is_paused`。
  ⇒ 750 天回填 ≈ **750 次请求**（不是 2876）；日常增量 **1 次请求**。
- 本地库 `data/zzshare_daily.db`（**4.4GB / 1672 万行 / 2005-01-04 起**），
  已用 `--smoke` 补到 **2026-10-21**（3 天、0.5 分钟、token 已配）。
  `meta` 表按日记录 `done_at`，断点续传。
- **口径对照（零 egress，20 只 × 最近重叠区间）**：
  · 日收益差：mean **3.2bp**、p95 **13.7bp**、max 1123bp（个别除权/涨跌停日）；
  · 成交量比 zzshare/腾讯：**中位数/10~90 分位都恰好 100.0** ⇒ zzshare 是**股**，
    包内是**手**，÷100 即对齐。
- ⚠️ 复权：按天模式 `adj` 无效，必须用 `factor` 自算
