### ★★★ 最终真因：前端**本地开发缓存**把空的首次响应永久钉住了

用户回"还是没有改变"。继续查发现 `frontend/.env.development`：

```
VITE_API_BASE_URL=/api
VITE_LOCAL_CACHE=1          # ★ 本地开发响应缓存，2026-11-07 为省重算加的
# VITE_LOCAL_CACHE_TTL=1800 # 注释掉 ⇒ **TTL=0 = 永不过期**
```

`src/api/index.js` 的实现：
```js
const LOCAL_CACHE = import.meta.env.VITE_LOCAL_CACHE === '1'
if (LOCAL_CACHE && method === 'get' && !config.params?.nocache) {
  const hit = _cacheGet(_cacheKey(config))
  if (hit) return Promise.reject({ __cacheHit: true, data: hit.d })  // 一次网络都不发
}
```

**因果链**：
1. 09:47 首次加载 → 后端此时确实没有当日 K 线 → 返回 `open_price=null`
2. **这份空响应被写进 localStorage，TTL=0 永不过期**
3. 之后刷新页面 / 重启前端 / 重启后端 —— 前端**直接返回缓存，一次网络都不发**
4. ⇒ 表现成"后端明明有值（我 curl 接口确认有），页面永远是 —"

**⇒ 用户问"是不是要清前端接口缓存" —— 猜对了，而且这是唯一解释。**

**修法**：一开始我给 `getAuctionPanel` 加了 `params: { nocache: 1 }`，
**但用户明确要求还原** —— 这个缓存是 2026-11-07 为了**省流量/省后端重算**
有意加的，不能因为一次踩坑就砍掉。
⇒ 已还原成原始调用，只在 `api/index.js` 上留一条注释：
> ⚠️ 本接口**走本地开发缓存**（`VITE_LOCAL_CACHE=1`，TTL=0 永不过期）。
> 若首次加载时后端还没当日 K 线（`open_price=null`），空值会被缓存住 ⇒
> 之后一直显示 `—`，**刷新/重启前后端都无效**（请求根本不发）。
> ⇒ 遇到时控制台执行 `clearApiCache()`，再刷新页面。

**★ 结论性认知（比"该不该缓存"更实用）**：
用户选择**保留缓存 + 手动清**，这在本项目的使用方式下是合理的 ——
本地开发时页面反复热更新，缓存省下的重算是真金白银；
而"清缓存"只是一个一秒钟的控制台命令，成本远低于每次刷新都等后端重算。
**关键是要知道有这回事、以及怎么清**，而不是把缓存整个禁掉。

**清缓存的两种方式**（告诉用户）：
- 控制台 `clearApiCache()`（已挂 `window`）
- F12 → Application → Local Storage → 删所有 `api_cache:*`

**排查这类"后端有值、前端没有"问题的最快分叉**：
**先直接 curl 后端接口**。
- 接口有值 ⇒ 问题在**前端**（缓存/代理/字段名/构建未生效）
- 接口也没值 ⇒ 问题在**后端**

### `app/macro_inflation.py`：把"趋势指向"落成可复算规则

框架原文「连续 2-3 个月回落，趋势指向 ≤2.8%」是自然语言，落地为：

```
falls  = 从最新月往回数连续下降的月数
slope  = (最新 − 3个月前) / 3
proj   = 最新 + slope × 2        ← "趋势指向" = 按当前斜率再走 2 个月
reached = latest ≤ 2.8 或 proj ≤ 2.8
通过    = falls ≥ 2 且 reached
```
