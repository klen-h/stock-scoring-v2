## 005 盘中实时涨跌幅的流量成本实测（2026-10-26，仅测算未改码）

- `/score/batch-prices` 20 只：**1.59KB**（gzip 0.57KB）—— 只含 code/name/price/change_pct。
- `/system/stock-facts/wide` 20 行：**15.9KB**（gzip 2.45KB）—— 15 列全字段。
- 后端 **没有 GZipMiddleware**（main.py 只挂了 CORS）⇒ 实际传输多为未压缩（边缘代理可能补，不可依赖）。
- 交易时段 4h、60s 轮询 = 240 次/日：
  · 只刷报价：≈381KB/日、11MB/月（gzip 1/3）；
  · 重拉宽表：≈3.8MB/日、114MB/月。
  Render 免费额度 100GB/月 ⇒ 都不是瓶颈，**带宽不是真问题**。
- 真成本是**外部请求数**：`tencent.get_stocks_batch()` 每次直连腾讯（无缓存）；
  而 `tencent._cache["stocks"]` 已有调度器 120s 全市场刷新 ⇒ 若新增/扩展一个
  `cached=1` 分支读内存，可使**上游请求 = 0**，也避开 WAF（项目有 501 前车之鉴）。
- 结论/建议：盘中实时价走「读内存缓存的批量报价 + 前端用日批 close 重算 ret5/ret20」，
  不要整表重拉；且只交易时段轮询、页面级单例（防多标签重复）。

## 012 事故复盘：2.18GB 流量 / 掉登录 / 跨域 / 行情停顿（`fafa1f3c`，**未 push**）

用户 2026-10-26 报四症：盘中涨跌/涨停跌停停在 10-23、控制台跨域、多次登录才进、
一天 2.18GB，已把线上**回退到 8b936a08**（该提交是 HEAD 的祖先，回退掉了 78 个提交）。

### 根因链（已核实代码 + 实测体积）
1. `klineDB.checkAndUpdate` 只判 `lastUpdate === todayStr(UTC)`，而包按**交易日**生成
   ⇒ 周末/盘前/日批前恒不等 ⇒ **每次进工作台/榜单**都重下 `kline-pack-latest` **3.80MB**
   （`data.date === lastUpdate` 只省导入不省下载）。
2. `ensureIndicatorsPack` 用 `?t=Date.now()` + `no-store`，指标包 ~5.5MB，条件成立就重下。
3. 当日 10+ 次部署 + **JWT_SECRET 未配置**（`auth.py` 每次启动随机密钥）⇒ 全员掉登录
   ⇒ 反复重进页面 ⇒ 数百次 × 4~9MB ≈ 2.18GB。
4. 行情停顿：后端重启后 `_cache` 恢复上一交易日收盘快照（盘中 restore_stocks=False），
   需 2~4 分钟刷新；频繁重启 ⇒ 一直冷启动。
5. 跨域：本地用 127.0.0.1/局域网 IP 打开 dev server 不在 allow_origins（线上 502/503
   无 CORS 头也会报跨域）。

### 已修（`fafa1f3c`）

## 016 流量 2.65GB 主因：后端包每次重启重下 62.4MB

- 实测（HEAD）data/backend-pack.db.gz = **62.40MB**（不是本地旧副本的 31.77MB）。
- pack_source._db_fresh() 用**文件 mtime ≤ 30h** 判断新鲜度；而 Render 免费版
  **文件系统临时**（render.yaml 注释已写：每次部署/重启 backend/data 清零）
  ⇒ 每次重启/休眠唤醒必重下 62.4MB（解压后 249MB 写盘）。
- 2.65GB ÷ 62.4MB ≈ **42 次重启**（今天 10+ 次部署 + OOM 被杀 + 免费版 15min 休眠唤醒）。
- 其它项：盘中增量行情 ~2MB/120s × 4h ≈ 0.24GB；前端进页面 3.8+5.5MB（GitHub Pages 口径）。
- 止血：减少部署 + 保活（cron 每 10min ping /api/health，避免休眠唤醒重下）+ 防 OOM 重启；
  根治：升级 Render 持久磁盘 / 改 DATA_SOURCE=db / 包瘦身拆分 / 放 R2。
- 注意：前端 6h 节流修复（fafa1f3c）只治 Pages 侧 9MB/次，**不治这 62MB**。

## 025 「合并轮询」优化提示词（输出类任务，未改代码）

用户要求：识别操作间的**包含关系**，把能一次轮询拿到的数据合并执行，并给出优化后的完整提示词。

沉淀的关键判断模型（后续做轮询治理可直接复用）：
- **合并分三层**：L1 调度合并（一个 ticker 触发多请求）／L2 请求合并（一次 HTTP 拿多份）／
  L3 上游合并（后端一次缓存或一次外呼供多个接口读）。三者判定标准不同，不能混说。
- **包含关系五依据**：字段包含、对象集合包含、生效时段包含、上游调用包含、派生/代际包含。
- **不算包含**：仅因果相关、时间先后依赖、汇总≠明细不可还原、不同鉴权、不同数据时刻（快照 vs 实时）。
- **可合并五条件（须同时满足）**：同 tick 门控、体积可控、新鲜度不降级、失败语义兼容、上游成本不增。
- **禁止**：把事件推送改回轮询、把按需点击请求并入常驻、把不同门控硬合成高频、把 LLM 并入高频轮询。

## 034 快讯解读「多次解读做 tab」可行性分析（未改代码）

- 单次解读内部是**总-分**：总 = `llm.conclusion / market / invalidate`；分 = 逐条 `llm.news[]`
  （gist/cause/scope）+ `holdings_impact`（投影到持仓行）。
- **跨多次解读不是总分，是覆盖**：`flash_brief` 表 `date` 为主键，`analyze()` 用
  `db.upsert(..., conflict_columns=["date"])` 直接覆盖 `llm_json/conclusion`，
  只累加 `auto_runs` 计数 ⇒ **历史解读内容没有留存**（`flash_brief.py:82-92, 520-528`）。
- 触发频率：`brief_loop` 每 120s 检查；命中异动阈值才跑；冷却 30min、日上限 8 次
  （`COOLDOWN_MIN=30`、`DAILY_MAX=8`，env 可调）；手动解读 TTL 30min。典型 1–5 次/日，最多 8 次。
- 做 tab 的前置条件：**先留历史**。两个方案：
  ① 轻量：同表加 `runs_json`（append 数组，cap 8）——改动最小；
  ② 规范：新表 `flash_brief_runs(id,date,ts,trigger,llm_json,conclusion)` + `/flash/brief` 返回
     `runs` meta（id/ts/trigger/conclusion），全文按 `?run_id=` 懒加载。
- 交互建议（与李大霄一致）：水平滚动 tab、选中居中、按 run id 记忆；**「最新结论」固定展示**，
  tab 仅用于回看历史（避免用户误把"不同时刻的判断"当成"同一时刻的不同层次"）。
