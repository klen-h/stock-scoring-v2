## 001 xiaopage：429 不换模型 + `JSON.stringify(stream)` 吞掉真实错误（`c0f6fba`）

用户跑了 `only_latest=0` 的补录（**改之前的代码**），贴回日志，暴露两个问题。

### 问题 1：429 连续重试 5 次同一个模型，不切换
```
⚠️ LLM 限流(429)，30秒后第2/5次重试...
⚠️ LLM 限流(429)，60秒后第3/5次重试...
⚠️ LLM 限流(429)，120秒后第4/5次重试...
⚠️ LLM 限流(429)，240秒后第5/5次重试...
❌ AI分析失败: LLM 请求失败(HTTP network)：read ECONNRESET
```
两层原因：
1. **那次跑的是旧代码**：`candidates = [LLM_MODEL, ...LLM_FALLBACK_MODELS]`，
   而 Secrets 里 `LLM_FALLBACK_MODELS` 为空 ⇒ **候选只有 1 个** ⇒ 没有模型可切。
   （2026-10-29 已加 `BUILTIN_FALLBACK_MODELS`，但这次运行早于该改动。）
2. **即便有新代码，也会先撞 450 秒**：Secrets 的 `LLM_MODEL` 优先级最高，
   若它仍是 `deepseek-v4-flash`，仍会先吃掉 30+60+120+240 秒才轮到备选。

修法（两处）：
- `KNOWN_DEAD_MODELS = ['deepseek-v4-flash','deepseek-v4.1-flash']` ⇒ 主模型命中就**直接替换**
  成 `DEFAULT_MODEL`（不是排后面 —— 排后面依然要等 450 秒）。
  ⚠️ 这份名单要和 stock-scoring 的 `_MODEL_KNOWN_DEAD` 一起改。
- 新增 `isQuotaExhausted(info)`：把 429 分成两类
  - 配额耗尽型（`insufficient_quota` / `ModelAccountRpmRateLimitExceeded` / `BurstRate`）
    ⇒ **睡眠不会恢复**，立即换模型（实测省 450 秒）
  - 普通 tpm/rpm ⇒ 只退避 2 次（90 秒）就切

实测：`450s → 0s`（配额型）/ `30s`（普通型），分类判断 5/5 通过。

### 问题 2【真 bug】`Converting circular structure to JSON` 掩盖了真实错误
```
❌ 音频处理失败: Converting circular structure to JSON
    --> starting at object with constructor 'TLSSocket'
```
根因在 `analyze-video.js` 的官方接口兜底 catch 里：
```js
console.warn(..., JSON.stringify(error.response?.data)?.slice(0, 200));
```
该请求是 `responseType: 'stream'` ⇒ `error.response.data` 是 `IncomingMessage`，
内含 `TLSSocket`（循环引用）⇒ `JSON.stringify` **抛异常** ⇒ **catch 自己在 catch 里崩了**。

后果远不止日志难看：
1. 真实原因（`HTTP Error 567` 风控 / `ECONNRESET`）**被完全掩盖**，没法排查；
2. 异常冒泡 ⇒ 整个视频被判"字幕获取失败" ⇒ **实测 5 个视频里有 2 个
   （`BV16FxF6YEh7`、`BV1xhxF6GE9U`）本来能下，全卡在这一行**。

修法：流对象不序列化（顺便 `destroy()` 释放连接），其余用 try 包住 ⇒ catch 里永不再抛。

### 顺带确认：HTTP 567 不是致命问题
```
ERROR: [download] Got error: HTTP Error 567: Unknown Status
↪️ 改用 B站官方接口下载...
✅ 官方接口下载成功（2.7 MB）
```
567 是 B 站风控（yt-dlp 被拦）。官方接口兜底链路**工作正常**，
所以 567 本身可恢复；真正卡住补录的是上面那个 JSON bug。

### 教训
- **catch 块里做序列化/字符串化是高风险操作**：错误对象常带 socket/stream/循环引用。
  原则：**catch 里绝对不能抛新异常**，序列化一律 try 包住或只取标量字段。
- **"重试 N 次"要先分清失败是否可恢复**：`insufficient_quota` 等配额类错误，
  退避重试是纯浪费；把它们和瞬时限流混在一起处理，是这 450 秒的来源。
- 用户贴的日志里**第一行报错往往不是根因**（"音频处理失败: Converting circular..."），
  真实原因被 catch 吞了 —— 看日志时要区分"被包装后的错误"和"原始错误"。

## 003 【破案】567 的真因：`baseUrl` 是 PCDN 节点（`b5642a1`）

用户贴来完整 B 站 Cookie。只读验证结论：

### Cookie 完全有效（**不是** Cookie 过期）
```
SESSDATA 过期时间 2027-04-26，剩余 178 天
nav → HTTP 200 code=0 isLogin=True  uname=梨来旋一个  vip=0
```
⇒ 之前怀疑"Cookie 半失效"**被证伪**。

### 真因：B站返回的首选地址是 PCDN
同一音频 `dash.audio[0]` 的三个候选（实测本机可达性）：
```
baseUrl   xy120x222x159x19xy.mcdn.bilivideo.cn:8082       → 206(本机) / 567(Actions)
backupUrl b-baaa....edge.mountaintoys.cn:4483             → 不可达（第三方 P2P）
backupUrl upos-sz-mirrorcoso1.bilivideo.com               → 206 ✅ 官方 CDN
backupUrl upos-sz-mirrorhwo1.bilivideo.com                → 206 ✅
```
原代码 `media = { url: dashAudio.baseUrl }` —— **只取 baseUrl**，
等于放着能用的官方 CDN 不用、专挑对数据中心 IP 最不友好的 PCDN 节点 ⇒ 567。

修：`urls = [baseUrl, ...backupUrl]` 按 `rankCdn` 排序（**upos-* 官方 CDN 优先**，
mcdn 最后），然后**逐个候选尝试**（最多 4 个），官方 CDN 失败才退 PCDN。

### 途中测出我自己写的 bug（值得记）
```js
if (/upos-[a-z0-9]+\.bilivideo\.com/i.test(u)) return 0;   // ✗ 错
```
官方域名是 `upos-sz-mirrorcoso1.bilivideo.com`，**中间带连字符**，
而 `[a-z0-9]+` **不含 `-`** ⇒ 匹配失败 ⇒ 官方 CDN 被判 rank 1（与第三方 P2P 同分）
⇒ 排序后 **P2P 反而排在官方 CDN 前面**，"修复"等于加剧问题。
改成 `/^https?:\/\/upos-[\w.-]*bilivideo\.com/i` 后 3/3 识别正确。
**教训：正则字符类漏掉 `-`（或 `.`）是高频事故，凡匹配域名/文件名必须实测样例。**

### 顺带验证到的事实
- 识别用 whisper base，音频码率取**最低**（实测该视频 65596 bps ≈ 64k）足够，
  原代码选**最高**（192k）既费流量又更容易撞风控。
- `playurl` 响应可达几十 KB，**读取响应必须读完整**：
  第一版测试脚本用 `resp.read(4000)` 截断 ⇒ `JSONDecodeError` ⇒
  误判"没有 dash 音频"。**这是排查工具自身的 bug，比被测代码的 bug 更隐蔽。**
- `mcdn` 节点**不支持 HEAD**（恒 404），测可达性必须用 `Range: bytes=0-1023` 的 GET。

该 Cookie 含有效登录凭证（`SESSDATA` 到 2027-04），已在本会话明文出现。
凭证明文贴到对话/代码里即视为泄露；本项目 `BILI_COOKIE` 一律只放 GitHub Secrets。
临时验证脚本用完立刻删除（本次已删 `_tmp_cookie_check.py`，未入库）。

## 004 金十 tidy-news 详情接口：需要**签名**，仅凭 URL 调不通

用户给了 `https://mp-api.jin10.com/api/tidy-news/details?id=60058`（50030 A股要闻详情）。
探测结论：

| 请求 | 结果 | 含义 |
|---|---|---|
| 不带 header | 502 `Gm-Error-Code: 81002` | 网关拒，**非网络故障** |
| `x-app-id: bVBF4FyRTn5NJF5n` + `x-version: 1.0` | 502 `81002` | app-id **有效**，缺签名 |
| 同上 + 浏览器 UA/origin/referer | 502 `81002` | 加头不解决 |
| 同上 + 小程序 UA | 502 `81002` | 加头不解决 |
| **`x-app-id: 1`（故意用错）** | 502 **`82002`** | app-id 不存在 ⇒ **证明 app-id 被校验** |
| z3c 域名下同路径 | 502 `81002` | 换域名无效（同一网关） |

⇒ **81002 = 缺签名/签名错**；**82002 = app-id 不存在**。
对比：xiaopage 能抓的快讯 `z3c.jin10.com/flash` 用 **Cookie（`JIN10_COOKIE`）** 鉴权，
而 tidy-news 走**签名** ⇒ 两套机制，不能复用 cookie 方案。

**DNS 线索**：`mp-api.jin10.com` CNAME → `*.z3c.jin10.com` → 阿里云 ALB（杭州），
与快讯同网关 ⇒ 问题不在网络，在鉴权。

**下一步**：需用户从浏览器 F12 → Copy as cURL 提供完整请求头，
重点看 `x-sign` / `x-token` / `authorization`。
若拿不到签名，改用其它源（东财/同花顺每日复盘）或网页版栏目。

**教训**：**`50x` + 自定义错误码头 ≠ "服务挂了"**。
`Gm-Error-Code` 这类网关码能直接区分"缺鉴权（81002）"和"凭据不存在（82002）"；
**故意传一个错的 app-id 作对照**，是判断"该参数到底有没有被校验"的最快办法
（若错误码不变，说明该参数根本不参与校验；变了就说明被校验到了）。

### 004-b 已打通：`x-token` 作为 **HTTP header** 即可（不需要签名）
用户提供了 `x-token`，实测通过：

| 传法 | 结果 |
|---|---|
| Cookie 整串（含 `x-token=`） | ✅ 200 |
| Cookie 只带 `x-token=...` | ✅ 200 |
| **Header `x-token: ...`** | ✅ 200 ← **最干净，推荐** |
| Cookie + Header 都带 | ✅ 200 |
| `Authorization: Bearer <token>` | ❌ 401 |


### ⚠️ 关键约束：`x-token` 是**有时效的登录态**

**这是本方案最大的运维成本点，必须在代码注释里写明。**

### 三个踩到的坑（都很容易再犯）
1. **`TASKS` / `DEFAULT_ORDER` 必须同时登记**：只加 `TASKS` 会触发断言
   `仅注册未排单=['jin10_tidy']` —— 这是 BK-47（`risk_calendar` 曾漏排单、静默断档）的机制化守卫，
   **它当场拦住了我**。凡新增日批任务，两处都要改。
2. **卫生门是纯正则，会误判注释里的示例代码**：我在注释里写了
   `requests.get(...headers=_headers()...)` 和 `datetime.now()` 作"反例说明"，
   结果 `req_no_timeout` / `naive_now` 双双报违规。
   ⇒ **注释里不要写出完整的违规代码片段**，用文字描述即可。
   另外 `_headers()` 的**嵌套括号**会让 `req_no_timeout` 正则匹配不到后面的 `timeout=15`
   ⇒ 先把请求头提成变量。
3. **关键词太宽会误判**：`存储` 命中了「海南自贸港…保税仓库**存储**汽油」，
   被打上"半导体存储"标签。改成 `DRAM/NAND/闪存/HBM/存储芯片/存储价格/存储市场` 后才正确。
   **教训：中文分词靠子串匹配时，越是常见的词越要加限定语**。
