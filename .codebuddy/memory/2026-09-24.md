## 🧭 决策：缺口②（跨 tab 深链 / 选中态）**不做完整版**，只做「零成本通道路」

**用户问**：缺口②成本中等，建议做吗？

**核实后纠正了我自己上一轮的估计（上轮说「成本中等」= 低估）**：
1. `ScoreRank.vue:1152` `activeTab = ref('top')` = **纯进程内 ref、零 URL 联动** ⇒ 加深链要
   **新引入 `useRoute` + 双向同步**（现在只 import 了 `useRouter`，仅用于 push）；还会引入
   **新行为**（刷新后停留在某 tab），可能反而干扰。

   ⇒ 「定位到某行 + `scrollIntoView`」必须**等数据到位**才能做 ⇒ ★ **真正的复杂度在异步时序，

3. ★ **关键：「差什么」悬停就能看到** —— top 的 `3/3` 标签 `title` 里**已经**有 3 条判据的
   ✓/✗ + `hint` + 建议仓位 ⇒ 「切过去定位那只票」的边际收益只剩**省一次视觉搜索** ⚠️

**⇒ 结论：值「通道路」，不值「深链机制」。**

## 🔥 线上内存实测 ⇒ 找到真根因并修复（用户 2026-09-24 提供首次线上读数）

**用户贴的读数**（诊断端点 + `memory_watch` 趋势首次真实数据）：
```
RSS 366.7MB / 500MB（73.3%）｜峰值 365.8MB｜线程 10
已知缓存 359.88MB｜**未归类仅 6.8MB**
占用最多：strategies._PRICES_CACHE 234.09MB（808条）｜flow._FLOW_MAP_CACHE 107.55MB（1条）
         store._SNAP_CACHE 7.58MB（2条）｜tencent._cache 6.52MB（3条）
趋势（24 次，跨重启）：78.4 → 79.2 → 79.2 → 81.9 → 82 → 83.8 → 83.9 → 83.9%
```

**★★ 三个关键结论**：
1. **不是泄漏，是「两个大缓存的设计上限太高」** —— **未归类仅 6.8MB** ⇒ 几乎全部内存都在
   已知模块级缓存里 ⇒ **没有框架层泄漏、不是 RSS 高水位** ⇒ **修缓存 ＝ 修问题**。
2. **我上轮的判断错了**：我曾怀疑 `tencent.KLINE_CACHE`（本地 209 条/13MB）是头号 ——
   线上它**根本没进榜**（`tencent._cache` 仅 6.52MB）⚠️ **本地量级不能外推线上**。
3. **起点基线就 78%**（重启即高）⇒ 缓爬 +5.5pt 到 84%+ 再 OOM ⇒ 与监控图锯齿吻合。

**★ 根因：同类缓存「写了两遍、只修一遍」**
| | `backtest/data.py`（**正确样板**）| `backtest/strategies.py`（**线上炸的**）|
|---|---|---|
| 条数上限 | 200 ✓ | **无** |
| 取用时清过期 | 过期即 pop ✓ | **只当 miss，条目留着占内存** |
| 单条上限 | >900 根不缓存 ✓ | **无** |
| 淘汰 | 满 200 丢最旧 1/4 ✓ | **无** |

⇒ `strategies.py` 是 `data.py` 的**残缺版**。key 是 `(code, start)` ⇒ **同一只股票的不同信号日
各自缓存一整段 bars**（数据高度重叠）⇒ 只增不减；且 `_PRICES_TTL` 只是**逻辑过期**（命中判断
`now - ts <= TTL`），过期仍占内存 ⇒ 唯一释放时机 = 回填后的 `invalidate`（**每天一次**）
⇒ 形态就是「**每天从 0 涨到 ~808 条 = 234MB，回填时清空**」= 监控图的锯齿 ✓

**★ 修法（`backend/app/backtest/strategies.py`，对齐 data.py 成熟做法）**：
新增 `_PRICES_CACHE_MAX = 200` / `_PRICES_BAR_MAX = 900` + `_prices_cache_get()`（**过期即 pop**）
+ `_prices_cache_put()`（单条 >900 不缓存 + 满 200 丢最旧 1/4）；两处读、两处写全部改走新入口。
**语义零变化**（缓存只加速，miss 即回源 pack/DB）⇒ 最坏只是回测多花点时间（低频手动操作）。

**验证 10/10**（打桩，未触网）：条数上限 len=200｜单条 >900 不缓存、=900 仍缓存（边界）｜
过期取用返回 None **且条目被物理删除**｜新鲜命中返回**同一对象**｜淘汰丢最旧｜invalidate 清空。
**外推：234MB → ≤56MB（省 ~178MB）⇒ 366MB → 约 190MB（38%）** ✓

**⚠️ 剩余（107MB，本轮未动）**：`mainforce/flow._FLOW_MAP_CACHE` = **整表资金流的 Python 表示**
（8.4 万行 × 9 字段，单条 107MB）。服务路径**真的需要**（`mainforce/state.py:197` 全池主力状态、
`gate.py:152` 批量闸门）⇒ **不能简单删**；要优化得改数据结构（dict 列表 → 紧凑结构）或分层的
「近 N 天」小 map，属**中等风险改动**，留待评估（评分冻结期不轻动）。

**⚠️ 我上一条回复的错误**：「采样趋势/企微告警不是我写的」—— **错了**，`app/memory_watch.py`
（采样落库 `memory_probe` 表 + 30 分钟定时 + 80% 阈值企微告警每日一次 + 14 天保留 + 5 分钟去抖）

### ★★ 最重要的一点：这个故障比 Render OOM **更致命**
Supabase 免费档超 500MB ⇒ **项目变只读**（写入全部失败）⇒ **日批全挂**，
而且**不会自动恢复**（不像 Render OOM 会重启）⇒ **必须提前预警，不能靠感觉**。

### 无「保留期/清理」的大表（只增不减，按增长驱动排序）
`mainforce_state`（2098行/日）> `ranking_live`（1000行/日）> `backtest_prices` > `mainflow_history`
= `zz_daily_snapshots` = `lhb_history` = `sector_daily`，以及 `news_history`、`ranking_history`、
`macro_daily`、`market_regime_history`、`contradictions`、`contradiction_reports`、
`daily_reports`、`trader_briefs`、`industry_mainline`、`gate_snapshot_history`、`signal_history`、
`strategy_results` —— **全部无裁剪、无归档、无分区、无 VACUUM**。
已有清理的（**不受威胁**）：`flash_news`(300条)、`flash_analyses`(50)、`flash_reviews`(20/phase)、
`macro_history`(150)、`etf_close`(30天)、`push_log`(30天)、`llm_usage_*`(30天)、`memory_probe`(14天)、
`kline_cache`/`indicator_cache`/`market_snapshot`（主键覆盖式，总量固定）。

### ★ 231MB 里可能有相当部分是「膨胀」而非有效数据（可零风险回收）
`kline_cache` / `indicator_cache` / `market_snapshot` 都是**每天全量覆盖**（`ON CONFLICT DO UPDATE`）
⇒ PostgreSQL 每次 UPDATE 都产生 **dead tuple**，autovacuum 回收前仍占空间。
⚠️ 注意：**普通 `VACUUM` 不缩小文件**（只标记可复用）⇒ dashboard 的 231MB **只有 `VACUUM FULL`
（有表锁 + 需临时空间）才会降**。

### 诊断 SQL（给用户在 Supabase SQL Editor 跑，10 秒看到真相）
```sql
SELECT relname AS 表, pg_size_pretty(pg_total_relation_size(relid)) AS 总大小,
       pg_total_relation_size(relid) AS 字节, n_live_tup AS 活行, n_dead_tup AS 死行
FROM pg_stat_user_tables ORDER BY pg_total_relation_size(relid) DESC LIMIT 25;

SELECT relname AS 表, n_live_tup AS 活, n_dead_tup AS 死,
       round(n_dead_tup::numeric / GREATEST(n_live_tup,1), 2) AS 死行比
FROM pg_stat_user_tables WHERE n_dead_tup > 500 ORDER BY n_dead_tup DESC LIMIT 15;

SELECT pg_size_pretty(pg_database_size(current_database())) AS 全库;
```

### 处置优先级（先量后修）
1. 跑上面的 SQL ⇒ 拿到**真实分表体积**（我们的估算是推算，精度有限）
2. 若死行比高 ⇒ `VACUUM FULL` 回收膨胀（**不删任何数据**，零风险，但会短暂锁表）
3. 给**无争议表**加保留期（`ranking_live` 90 天、`sector_daily`/`news_history`/`lhb_history` 1~2 年、
   报表类按月保留）—— ⚠️ `mainforce_state`/`backtest_prices`/`mainflow_history` **动之前要评估**
   （回测/信号跟踪依赖长历史）
4. **结构性解法**：`backtest_prices`（最大单表 82MB）**外迁到 gh-pages 数据包**
   （`backend-pack.db` 的基础设施已存在，正是同一类思路）
5. 加「DB 用量」监控（像 `memory_watch` 那样落库 + 80% 告警）⇒ 避免无预警撞线

### ✅ 已实现：`GET /api/system/db-usage` + 首页常显（用户问「去哪里跑 SQL」后落地）
**动机**：用户问「去哪里跑 SQL」⇒ 说明"要他去外部面板找"本身是摩擦 ⇒ 直接做进首页，
以后不用跑 SQL。（Supabase 的路径：Dashboard → 左侧 **SQL Editor** → New query → Run。）
**实现**（`backend/app/routers/system.py` 新增，紧邻 `/memory`）：
- `_db_usage_impl()`：PG 走 `pg_database_size(current_database())`（总量）+ `pg_stat_user_tables`
  （**分表体积** `pg_total_relation_size` / `n_live_tup` / `n_dead_tup`），**按体积降序**；
  `<1KB` 的空表不入榜；`dead_ratio = dead/live`
- `_db_num()`：PG 的 bigint/numeric → float（前端与算术都要数字）
- **SQLite 降级**：无 `pg_stat_*` ⇒ 只报库文件大小（本地开发可判读）
- **60s 进程内缓存**（首页会频繁刷新，库体积以"天"为尺度 ⇒ 缓存无副作用）
- **fail-open**：权限不足/异常 ⇒ `available=false` + `error`，**不抛错**（看护类接口不反噬主流程）
- `summary` 人类可读 markdown；**≥100% ⇒ 🔴「只读、写入会失败、不会自动恢复」**；
  ≥80% ⇒ ⚠️ 清理建议
- `dead_note`：只统计**入榜的 top N** 并在文案里写明（不让人误以为是全库）
**前端**：`api.getDbUsage` + `Dashboard.vue` 在「进程内存」下方加「数据库」块
（用量/剩余/占用最多 Top4/死行提示，配色复用 `memColor`）⇒ **两个运维出口并列常显**。
**验证**：后端编译 ✓；**测试 22 项全过**（SQLite 降级不报错｜总量 231MB→46.2%→剩余 269MB｜
按体积降序｜<1KB 过滤｜dead_ratio 0.61｜60s 内命中缓存且**未再查库**｜104% 给只读+不会自愈｜
84% 给清理建议｜异常 fail-open）；前端 `vite build` ✓ 12.19s。
⚠️ 测试脚本自己踩了**项目已记录的坑**：GBK 控制台 `print` 含 `⇒` 抛 `UnicodeEncodeError`
（`memory_watch.py` 注释里警告过）⇒ 补测时 `$env:PYTHONIOENCODING="utf-8"` 解决。
**部署后**：首页能直接看到分表体积 ⇒ 才知道"该砍谁"（**先量后修**）。
