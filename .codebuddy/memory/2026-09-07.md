## ★ 后端包「一直超时」的真正根因（2026-09-07 实测定位，已修复）
- **根因 = 腾讯 fqkline 的 count 参数超限**，不是并发/配额/超时设置！`generate-kline-pack.py` 传 `count = days*2`，后端包 days=1100 → count=2200 → 腾讯**直接拒绝返回 0 根**（0.1s 快速失败，非超时）。100% 失败 → 单只重试惩罚放大 → 1442 只必然顶穿 job 上限。前端包 days=150 → count=300 正常 → 所以"前端每次成功、后端必超时"。
- 实测上限：count=2200→0 根；1600→仅 640 根；**800 + 区间 1100 天 → 749 根**（≈2.9 年，够回测 500 交易日目标）。
- **修复**：`generate-kline-pack.py` 加 `KLINE_COUNT_CAP = min(days*2, 800)`（env `PACK_KLINE_COUNT_CAP` 可覆盖）；本地验证 000001/600519/000858 → **749 根、0.06-0.11s** ✅（修复前 0 根/10s 超时）。
- **附带修复**：`fetch_all_klines` 加中途熔断 `MIDWAY_FAIL_FAST=80`（前 80 只零成功立刻 RuntimeError 退出，不再空耗到 90-150 分钟超时才发现）；workflow 参数 PACK_REQUEST_TIMEOUT 6→15（750 根大响应）、CONSECUTIVE_COOLDOWN 6→15。
- 日志特征：`0/1442 成功` + 每 6 次失败 `暂停 30s` + **无 [WAF] 日志** = count 被拒（不是 501 封禁）。下次若再全挂，看是否熔断在 ~4 分钟内快速失败（正确行为），而非熬满 2 小时。
- 股票池 1442 只（quotes 已过滤过 ST/科创创业，故质量减法剔 0 只属正常，勿慌）；count 修复后 1442 只 5 并发预计 <10 分钟。
