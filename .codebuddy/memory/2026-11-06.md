## 洗盘 vs 破位 打分（c2357a2d）——"底部震荡"四功能之功能 2

**前置**：功能 1（`range_watch`，bdd5b577）给了"这个跌幅在箱体什么位置"。
功能 2 回答下一跳：**到了下沿，怎么知道是"洗"还是"破"？**

**实现**：`backend/app/washout_alert.py`（纯函数 + 零新增表 + 零外呼），
由 `range_watch.load()` 调用 `annotate()` 给每个 item 补 `washout` 字段。
前端在「震荡区间」卡片的持仓行/区间内榜尾加徽章，`title` 展开五项证据。

**五项分项（每项 −2 ~ +1）**：
1. 量能：缩量 <0.75 `+1` / 放量 >1.3 `−1`
2. 收盘位置：**跌穿区间 pos<0 `−2`；未跌穿 `0`（不给分）**
3. 主力 5 日：>−0.5 亿 `+1` / <−3 亿 `−1`
4. 行业同步：破位率 <20% `+1` / >60% `−1`（行业样本 <5 只跳过）
5. 跌幅形态：**先判阴跌**（20日 ≤−20% `−1`），阴跌不成立才判急杀（5日 ≤−8% `+1`）

**★★ 首版阈值翻车（最值得记的一条）**：
初版 `收盘位置 pos>=0` 给 `+1`、量比 <0.85、主力 >−1亿、行业 <30% —— 实测 **132 只样本里
118 只(89%) 被判"偏洗盘"，分数集中 +3/+4，完全没有区分度，等于没做**。
根因：**把"正常"当成了"证据"**。
- 「收盘仍在区间内」是**前提条件**（都到下沿了当然还没穿），不是洗盘证据
- 其他三个阈值也都太容易满足

⇒ 校准后：
```
收盘位置 → 只惩罚不奖励（pos<0 扣 2 分，否则 0）
VOL_SHRINK 0.85 → 0.75
FLOW_OK   −1.0  → −0.5
IND_CALM   0.30 → 0.20
```
分布变为：偏洗盘 26 / 部分洗盘证据 62 / 证据不足 44（132 只样本），**有区分度了**。

**★ 中间档**：`+2` 是最大群体（47%），原措辞"证据不足"不准确（它有 2 项确凿证据）
⇒ 加 `"部分洗盘证据"` 档。措辞要如实，否则用户会误读成"没证据"。

**★ 红线（写进 docstring，改动前必读）**：
只给证据，**不给"该卖/该拿"**。理由：
- "洗盘"与"刚开始下跌"在头 3~5 天**数据上无法区分**（形态本质，不是模型不行）

- 每个返回都带 `caveat`：分数是「证据条数」汇总，**不是概率**

> `washout` 高分组（≥3）的"10 日内收回区间内"的比例，是否显著高于低分组（≤−2）

## 日批「回测价格回填」超时 1800s（f8a68440）

**现象**（用户贴的 11-05 日批日志，49 成功 / 1 失败）：
```
> 回测价格回填（近5日必补）：单任务超时（>1800s）
[backfill_daily] 完成: 9 只 / 72 行（基准 2026-11-05｜必补 484 / 老缺口 2）
[WARN] 个股滞后 486（配额内未轮到，次日继续推进）
```

**根因链（算出来的，不是猜的）**：
```
东财 push2his  15s 超时（_MAX_RETRIES=2，backoff 2+4）≈ 36s
  → 腾讯 fqkline  WAF 501 → `_TENCENT_WAF_COOLDOWN = 300`（backtest/data.py）
  → `_stale_fail` 里 time.sleep(2)
  → 换源再试一次（又是 36s）
⇒ **单只 STALE 约 74 秒**
```
`必补 484 只 × 74s ≈ 10 小时`，被框架 1800s 杀掉时只跑了 24 只 —— 日志里"9 只"对得上。

**关键判断**：那天**源本身没有新数据**（002129 最新 10-30 < 基准 11-05），
逐只重试只是把一个"源没数据"的问题，变成"任务超时"的假故障，
还连带 486 只滞后**一只都没推进**。

**修复**（`backfill_history._run_batch_guarded`，抽成独立函数便于单测）：
- **时间预算**：fresh 900s / rest 600s（框架上限 1800s，留余量）
- **连续 STALE 熔断**：连续 `CONSEC_STALE_LIMIT = 6` 只 ⇒ 判定源不可用，本轮中止
- 判据用 `_STALE_COUNT` 的**增量**，不用 `backfill()` 返回值
  （返回 0 既可能"源没数据"也可能"已同步"，用返回值会误熔断）
- 中止时日志写**"中止"而不是"完成"**，并回显原因 + 剩余只数

**效果**：最坏情况 6 × 74s ≈ **7.4 分钟**退出，而不是 30 分钟被强杀。

**★ 两个踩坑**：
1. **两套 WAF 冷却常量**：`tencent.py` 的 `_WAF_COOLDOWN=120`（K线接口）与
   `backtest/data.py` 的 `_TENCENT_WAF_COOLDOWN=300`（历史回填）**不是一个东西**，
   日志里的 300s 来自后者。找日志对不上时先确认是哪个模块打的。
2. **`time.time()` 在 Windows 精度约 15ms**：单测里 50 次快速循环落在同一 tick，
   "预算已用尽"判断不出来 ⇒ 改 `time.monotonic()`（且不受系统校时跳变影响）。

**⚠️ 没解决的**：数据缺口本身（486 只滞后）。
熔断只是"不再空转"，源限流时当天仍然补不上，靠次日重试 + zzshare 按天通道。
日志显示 `[zz] 除权跳过 1026 只 ⇒ 交回逐只` —— 除权股无法走快速通道，
这是 484 只必补的主要来源，**要真正解决需另想除权股的回填方案**（未做）。

## ★★ P0：cache_release 把 5 个缓存清成 `{}` 导致 KeyError 至重启（98b4a9b7）

**发现路径**：用户贴部署日志，里面**每一轮**都有
```
[portfolio_radar] 主力状态读取失败（跳过）：'ts'
```

**根因**（不是今天改的代码，是既有 bug）：
```python
# cache_release._clear_one
if isinstance(c, (dict, list, set)):
    c.clear()          # ← 对 {"ts": 0.0, "data": {}} 调 clear() ⇒ {}
```
之后 `mainforce.state.load_latest()`：
```python
if _latest_cache["ts"] and ...    # KeyError: 'ts'  ← 每次调用都炸
```
**后果**：持仓雷达/评分榜的「主力状态」列**永久失效**，直到进程重启
（因为缓存再也不会被重建 —— 一进来就抛异常）。

**逐个核对初始值后，发现同类共 5 个**（都带元信息键）：
```
mainforce.state._latest_cache   {"ts": 0.0, "data": {}}   ← 已在日志暴露
mainforce.flow._FS_CACHE        {"ts": 0.0, "data": {}}   ← 被 try/except 静默吞掉
mainforce.gate._fs_cache        {"ts": 0.0, "map": None}
mainforce.trade_gate._contra_cache  {"ts": 0.0, "n": 0}
mainforce.confluence._env_cache {"ts": 0.0, "snap": None}
```
后 4 个**没在日志暴露**，因为调用方有 try/except 兜底 —— 但功能是**静默失效**的
（比如闸门资金流永远退回回源，egress 会暴涨）。这类"吞异常"比崩溃更难发现。

**修复（两层）**：
1. `cache_release._CLEAR_AS_RESET`：这类缓存清空后 **写回初始结构**
   （`c.clear()` 后 `c.update(deepcopy(reset))`）；
2. `load_latest` 用 `.get("ts")` + `setdefault("data", {})` 容错 ——
   缓存被任何方式破坏时最多"重算一次"，不能让整个功能消失。

**对照验证**：`tencent.KLINE_CACHE` 这类**空 dict 初始化**的缓存仍被完全清空（行为不变），
只有带元信息键的走 reset 路径。

**★ 通用教训**：
> "把模块级缓存登记到内存释放清单"时，必须看它的**初始结构**。
> 只要初始化里带 `ts` / `ver` / `data` 这类**元信息键**，`clear()` 就是破坏性的。
> 登记一个新缓存前，先问一句：清空之后，消费方还能正常读到它吗？

## 部署"健康检查 40 秒未通过"：真凶是**停止卡 90 秒**（21c2f050）

**用户贴的 journalctl 时间线（关键，读法很重要）**：
```
00:45:36  Stopping → 00:45:37 Stopped（1 秒，正常）
00:45:44  Application startup complete（启动只花 7 秒）

00:57:25  Stopping → 00:58:55 SIGKILL（卡 90 秒 = systemd TimeoutStopSec）
01:07:28  Stopping → 01:08:58 SIGKILL（又卡 90 秒）
01:09:04  Application startup complete（最后还是起来了）
```

**结论与表面相反**：
- **服务启动只要 4~7 秒，一直是好的**；
- 卡的是**停止**：`systemctl restart` 阻塞在 stop 阶段 90 秒被 SIGKILL；
- deploy.sh 的健康检查因此看起来"40 秒未通过"。

**根因**：`main.py` lifespan 里
```python
await asyncio.to_thread(pack_source._ensure_ready)   # 下载 62MB gz + 解压 250MB db
```
- `asyncio.to_thread` 的 executor **线程不可取消**：`task.cancel()` 只让 `await` 抛
  CancelledError，**线程继续下载**；
- uvicorn 退出时 `asyncio.run` 会 `shutdown_default_executor()` **等线程结束**
  ⇒ lifespan 卡死 ⇒ systemd 到 90 秒 SIGKILL。

**证据**：新进程 00:45:44 启动后**全程没有** `[main] 后端数据包就绪`，
说明包没下完，停止时正卡在下载里。

**修复**：
1. `_pack_bootstrap` 从 `asyncio.to_thread` 改为 **daemon 线程**（解释器退出不等它）。
   **安全依据**：`_ensure_ready` 是**原子写**（下载 `.tmp` → `os.replace`），
   中途被杀最多留一个 `.tmp`，下次覆盖，不会把半成品当成品。
2. `deploy.sh` 健康检查失败时补三段现场诊断：
   ① `systemctl status`（看是不是 inactive）② `ss -lntp | grep 8000`（端口有没有监听）
   ③ `curl -w http_code/time`（拒绝连接 vs 超时）
   —— 因为这次日志里**一条 `/api/health` 访问记录都没有**，
   说明 curl 根本没连上，而"服务没起来"和"端口没监听"是两回事。

**⚠️ 另一个尚未定论的点**：健康检查 40 秒窗口内（01:09:04~01:09:38）
服务已 startup complete，却没有任何 `/api/health` 访问记录 ⇒
要么 8000 没监听、要么 `HEALTH_URL` 与实际端口不一致。
需要现场跑 `ss -lntp | grep 8000` 才能定论（代码侧无法判断）。

**★ 通用教训**：
> `asyncio.to_thread` 里跑的**长任务**（下载大文件、全量计算）会成为
> **进程退出的隐形阻塞点** —— 因为它不可取消，而解释器退出要 join executor。
> 一次性、可中断、原子写的后台任务，应该用 `threading.Thread(daemon=True)`。

否则就是这种**静默失效**（既不报错也没有日志，卡面上只显示"暂无"）。

**修复**：`scheduler.py` 新增 `people_watch_loop()`，
窗口 `PEOPLE_WINDOW = (1320, 1439)` = 北京 22:00-23:59。

**时点为什么是 22:00**：金十这个接口是**编辑整理后**发布的，有延迟 ——
实测 11-05 22:00 时最新一条是 11-05 01:29。太早拉等于白跑。
`days=30` 全量 + `ON CONFLICT DO NOTHING` ⇒ 当天漏的次日自动补。

**两个刻意的设计**：
1. **不加 `is_trading_day`** —— 周末/节假日照样有人讲话（央行行长周末访谈很常见）；
2. **全部人失败时不 `mark_schedule_done`** —— 多半是 `JIN10_X_TOKEN` 失效，
   记账就会把"一次 token 过期"变成"一整天空白"，而且没人知道；
   不记账 ⇒ 5 分钟后自动重试，日志里也能看到原因。

**前端文案同步改**：`等日批拉取` → `每日 22:00 自动拉取`。

## ★ 8000 端口 `Connection refused` 的排查顺序（重要，别再误判）

**用户现场**：`curl` 得 `code=000 / 0.0002s / Connection refused`，
但 `systemctl status` 显示 `active (running) since ... 7min ago`，
`ExecStart` 明写 `--host 127.0.0.1 --port 8000`。

**必须分清三种状态，它们的处置完全不同**：

| 现象组合 | 含义 |
|---|---|
| `active` + `ss` 有 8000 + curl 200 | 正常 |
| `active` + `ss` **无** 8000 + **CPU 0%** + `Application startup complete` 后无 `Uvicorn running on` | **真卡住**（bind 没走到） |
| `active` + `ss` 无 8000 + 进程**刚起几秒** | **只是还在启动**，别急着下结论 |

**这次的真实结论**：`kill -9` 后重起的进程，`sleep 6` 那一刻去测还是 refused，
但 **20 秒后再看已经好了** —— 本项目完整启动约 **15 秒**
（Python import 4 秒 + lifespan + 27 项宏观数据抓取 + 数据包校验）。
`[snapshot] 已从收盘快照恢复行情: 5257 只` / `[scheduler] 已启动` /
`[main] 后端数据包就绪` 这些**全部在同一秒**打出来，然后才有 `Uvicorn running on`。

**⇒ 以后判断"起没起来"，等 **30 秒**再测，不要在 6 秒时就断言"卡死"。**

**但第一次（PID 91677）不是慢，是真异常**：7 分钟没 bind、CPU 0.0%、
`TIME+ 0:02.84`、`Tasks: 8`。**未定论**（抓栈前已 kill -9，没抓到证据）。
最可能的解释（未证实）：`restore_market_snapshot` 返回 False 走进
`_bootstrap_snapshot` → `refresh_all_stocks`（5257 只）把
`ThreadPoolExecutor(max_workers=6)` 占满，而 uvicorn bind 前的
`getaddrinfo` 用的正是同一个默认 executor ⇒ 排队、永远轮不到。
**下次再遇到，先 `py-spy dump --pid $(systemctl show -p MainPID --value stock-scoring)`，别急着 kill。**

**排查顺序（省事的那个先做）**：
```bash
systemctl status stock-scoring --no-pager -l | head -20
systemctl cat stock-scoring | grep -A3 ExecStart
sudo ss -lntp | grep 8000
top -b -n1 -p <PID> | tail -3          # CPU 0% = 在等，100% = 在算
# 都不行再上 py-spy（能在卡住时看 Python 栈，kill 之前抓）
```
