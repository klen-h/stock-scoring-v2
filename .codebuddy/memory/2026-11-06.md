## 洗盘 vs 破位 打分（c2357a2d）——"底部震荡"四功能之功能 2

**前置**：功能 1（`range_watch`，bdd5b577）给了"这个跌幅在箱体什么位置"。
功能 2 回答下一跳：**到了下沿，怎么知道是"洗"还是"破"？**

**实现**：`backend/app/washout_alert.py`（纯函数 + 零新增表 + 零外呼），
由 `range_watch.load()` 调用 `annotate()` 给每个 item 补 `washout` 字段。
前端在「震荡区间」卡片的持仓行/区间内榜尾加徽章，`title` 展开五项证据。

**五项分项（每项 −2 ~ +1）**：
1. 量能：缩量 <0.75 `+1` / 放量 >1.3 `−1`
2. 收盘位置：**跌穿区间 pos<0 `−2`；未跌穿 `0`（不给分）**
3. 主力 5 日：>−0.5 亿 `+1` / <−3 亿 `−1`
4. 行业同步：破位率 <20% `+1` / >60% `−1`（行业样本 <5 只跳过）
5. 跌幅形态：**先判阴跌**（20日 ≤−20% `−1`），阴跌不成立才判急杀（5日 ≤−8% `+1`）

**★★ 首版阈值翻车（最值得记的一条）**：
初版 `收盘位置 pos>=0` 给 `+1`、量比 <0.85、主力 >−1亿、行业 <30% —— 实测 **132 只样本里
118 只(89%) 被判"偏洗盘"，分数集中 +3/+4，完全没有区分度，等于没做**。
根因：**把"正常"当成了"证据"**。
- 「收盘仍在区间内」是**前提条件**（都到下沿了当然还没穿），不是洗盘证据
- 其他三个阈值也都太容易满足

⇒ 校准后：
```
收盘位置 → 只惩罚不奖励（pos<0 扣 2 分，否则 0）
VOL_SHRINK 0.85 → 0.75
FLOW_OK   −1.0  → −0.5
IND_CALM   0.30 → 0.20
```
分布变为：偏洗盘 26 / 部分洗盘证据 62 / 证据不足 44（132 只样本），**有区分度了**。

**★ 中间档**：`+2` 是最大群体（47%），原措辞"证据不足"不准确（它有 2 项确凿证据）
⇒ 加 `"部分洗盘证据"` 档。措辞要如实，否则用户会误读成"没证据"。

**★ 红线（写进 docstring，改动前必读）**：
只给证据，**不给"该卖/该拿"**。理由：
- "洗盘"与"刚开始下跌"在头 3~5 天**数据上无法区分**（形态本质，不是模型不行）
- 任何声称能即时识别洗盘的规则都是事后叙述 —— 同 `thesis_tracker` 拒绝 LLM 裁决
- 每个返回都带 `caveat`：分数是「证据条数」汇总，**不是概率**

**⚠️ 阈值未回测验证**：当前只是"让分布散开"的初校准。
真正确认要看方案 §5.2 的预登记检验：
> `washout` 高分组（≥3）的"10 日内收回区间内"的比例，是否显著高于低分组（≤−2）

若两组无差异 ⇒ **功能该砍掉**，而不是硬上。

**数据口径坑**：`range_watch` 与 `stock_facts_wide` 的日期可能不同（数据包滞后），
`load_stats()` 取 stock_facts 自己的最新日，返回值带 `washout_stats_date` 供前端标注。

**实测样例**（东方电子 000682，score +4）：
```
+ 量能     量比 0.72    缩量下跌，主力未出
· 收盘位置  pos 0.18    收盘仍在区间内（前提，不计分）
+ 主力5日  -0.19亿     主力未持续流出
+ 行业同步  破位 18%     个股行为，非系统性下跌
+ 跌幅形态  5日 -9.4%   5 日急杀，横住后可观察承接
```

**未做**：功能 3（持仓耐心度，会改 `hold_3d_review` 固定 3 日，需影子运行）、
功能 4（区间内异动 vs 真突破区分）。

## 日批「回测价格回填」超时 1800s（f8a68440）

**现象**（用户贴的 11-05 日批日志，49 成功 / 1 失败）：
```
> 回测价格回填（近5日必补）：单任务超时（>1800s）
[backfill_daily] 完成: 9 只 / 72 行（基准 2026-11-05｜必补 484 / 老缺口 2）
[WARN] 个股滞后 486（配额内未轮到，次日继续推进）
```

**根因链（算出来的，不是猜的）**：
```
东财 push2his  15s 超时（_MAX_RETRIES=2，backoff 2+4）≈ 36s
  → 腾讯 fqkline  WAF 501 → `_TENCENT_WAF_COOLDOWN = 300`（backtest/data.py）
  → `_stale_fail` 里 time.sleep(2)
  → 换源再试一次（又是 36s）
⇒ **单只 STALE 约 74 秒**
```
`必补 484 只 × 74s ≈ 10 小时`，被框架 1800s 杀掉时只跑了 24 只 —— 日志里"9 只"对得上。

**关键判断**：那天**源本身没有新数据**（002129 最新 10-30 < 基准 11-05），
逐只重试只是把一个"源没数据"的问题，变成"任务超时"的假故障，
还连带 486 只滞后**一只都没推进**。

**修复**（`backfill_history._run_batch_guarded`，抽成独立函数便于单测）：
- **时间预算**：fresh 900s / rest 600s（框架上限 1800s，留余量）
- **连续 STALE 熔断**：连续 `CONSEC_STALE_LIMIT = 6` 只 ⇒ 判定源不可用，本轮中止
- 判据用 `_STALE_COUNT` 的**增量**，不用 `backfill()` 返回值
  （返回 0 既可能"源没数据"也可能"已同步"，用返回值会误熔断）
- 中止时日志写**"中止"而不是"完成"**，并回显原因 + 剩余只数

**效果**：最坏情况 6 × 74s ≈ **7.4 分钟**退出，而不是 30 分钟被强杀。

**★ 两个踩坑**：
1. **两套 WAF 冷却常量**：`tencent.py` 的 `_WAF_COOLDOWN=120`（K线接口）与
   `backtest/data.py` 的 `_TENCENT_WAF_COOLDOWN=300`（历史回填）**不是一个东西**，
   日志里的 300s 来自后者。找日志对不上时先确认是哪个模块打的。
2. **`time.time()` 在 Windows 精度约 15ms**：单测里 50 次快速循环落在同一 tick，
   "预算已用尽"判断不出来 ⇒ 改 `time.monotonic()`（且不受系统校时跳变影响）。

**⚠️ 没解决的**：数据缺口本身（486 只滞后）。
熔断只是"不再空转"，源限流时当天仍然补不上，靠次日重试 + zzshare 按天通道。
日志显示 `[zz] 除权跳过 1026 只 ⇒ 交回逐只` —— 除权股无法走快速通道，
这是 484 只必补的主要来源，**要真正解决需另想除权股的回填方案**（未做）。

## 当日收尾审查（a14f67cf）——发现并修复一个 P0

**用户要求审查当天改动**。当天 4 个提交：功能 2（洗盘打分）+ 回填熔断 + 2 个记忆。

**★ 审查发现的真 BUG（P0）**：`range_watch.load()` 的 `mine`（我的持仓）只从
`items` 里筛，而 `items` 受 `limit`（默认 200）截断：
```python
rows = db.fetch("... ORDER BY in_range DESC, pos_in_range ASC LIMIT 200")
mine = [it for it in items if it["code"] in holds]   # ← 排到 201 位就整个丢掉
```
实测：持仓 000429 排第 **164** 位，`limit=200` 时侥幸在内；
只要持仓票排到 200 名以后就**完全消失** —— 而"我的持仓"是这张卡最重要的部分。

**修复**：
1. 对不在 `items` 里的持仓**单独补查**，合并后再 `annotate`
2. 抽 `_to_item()` 单点转换（主查询与补查共用，避免字段漂移）
3. 新增 `mine_missing`：**没被覆盖的持仓不能静默消失**（K 线不足 120 根 / 被跳过），
   前端显示"未纳入区间计算：601398（K 线不足 120 根或被跳过）"
4. 清理死代码：`compute()` 里的 `names: Dict = {}` 从未被写入，
   `name` 恒为空串，后来又被 `stock_facts_wide` 的 `nm` 覆盖

**验证**（limit 1/3/200 三档）：
```
持仓 = mine ∪ mine_missing，一个都不丢 ✓
补查进来的持仓字段完整（含 washout 占位）✓
```

**日批耗时影响**：`market_observers` 加入 `range_watch` 后，
全市场 2864 只（批量插入）约 **2~3 分钟**，原来 47s ⇒ 预计 ~3.5 分钟。
可接受，但要知道这个变化。

**顺序无关性**：`range_watch` 在日批里早于 `stock_facts_wide`
⇒ `compute()` 里取 name 用的是**昨天的** `stock_facts_wide`（`MAX(date)`），
名称本来也不变，无影响。
