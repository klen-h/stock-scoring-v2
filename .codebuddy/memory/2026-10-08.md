## ③ 上游兜底 guard 修复（2026-10-08，用户随后贴了 backend-pack 运行列表）

### 先更正我上一条里的错误猜测
我上轮写"cron-job.org 时刻对不上，**疑被配成 UTC**" —— **错了**。用户提供的上游列表证明：
`Manually run by klen-h` **每天 19:00 北京准时**（= cron-job.org 的 dispatch，时间没错）。
```
Manually: 10-01 19:00 / 10-02 19:00 / 10-05 19:00 / 10-06 19:00 / 10-07 19:00  （均 1h18m~1h31m）
Scheduled: 10-01 02:52 / 10-02 03:19 / 10-03 03:02 / 10-06 05:23 / 10-07 03:20 / 10-08 03:47
```
⇒ 兜底 cron 名义 14:00 UTC（北京 22:00），**实测总晚 4~7h** 才起跑（GitHub schedule 延迟），
落在北京 02:52~05:23 —— 这才是"凌晨那次"的来源。

### 端到端时序被两边数据互相验证（铁证）
```
上游 19:00 + 1h18m31s = 20:18:31 → 日批 20:23 起 → 53m56s（10-07）
上游 03:47 + 1h18m31s = 05:05:31 → 日批 05:05 起 → 57m37s（今天 #41）
     └─ 且 daily_reports(date=09-30) 的 created_at = 2026-10-08T06:03:02
        ≈ 05:05 + 57m37s ⇒ 链条完全吻合（说明列表时间是**开始时间**）
```

### 根因（从代码钉死，非猜测）：guard 从未生效
`backend-pack.yml` 的 `guard` job **只有 1 个 step，没有 `actions/checkout`** ⇒ 工作区无 `.git`；
而 **`gh` 不读 `GITHUB_REPOSITORY`**，它从 **CWD 的 git remote**（或 `GH_REPO`/`--repo`）推断仓库
⇒ `gh run list` 直接报 "not a git repository" ⇒ 被 **`2>/dev/null || echo 0` 吞成 0**
⇒ `OK=0` ⇒ **永不 skip**。旁证：兜底那几次时长都是 1h12m~1h31m（整包跑满；skip 的话只有几秒）。

### 已修（`.github/workflows/backend-pack.yml`，+28/-5，单次编辑）
- guard job 加 `permissions: {actions: read}`（默认权限受限时 gh 会 403）
- step env 加 **`GH_REPO: ${{ github.repository }}`**（等价 `--repo`，比加 checkout 轻）
- **不再吞错**：`if OK=$(gh run list ... --limit 20 ...); then ... else echo "::warning::…"; OK=0; fi`
  ⇒ 查询失败时**按"不跳过"处理**（宁多跑一次，不误跳一天）
- 验证：`yaml.safe_load` ✓（guard.permissions/GH_REPO 就位）；全仓库仅此一处用 `gh`（`daily-batch.yml` 的
  guard 不依赖 API ✓）
⚠️ **需提交并推到 `main`**（schedule 用默认分支的 workflow 文件）才生效。

### 收益
每天少跑一次完整链：包 ~1h20m + 日批 ~55m ≈ **2h15m/天**（按 ~21 个工作日 ≈ **~2800 分钟/月**）。
若仓库是**私有**，免费额度 2000 分钟/月 ⇒ 单这一条就超额度（值得确认仓库可见性与计费告警）。
