### 一、现象与诊断（三连法：进程 CPU / 日志推进 / 75 秒对比）
- 进程活着（PID 2888）但 **CPU 75 秒零增长 + 日志不动** ⇒ 不是死也不是慢，是**阻塞**。
- 日志：`[196/250] 2026-07-16: ★ 单日失败（SSL connection closed）⇒ 跳过` —— **韧性防线
  第一次实战成功**（单日失败没带崩进程，按设计跳过）；但**下一天的第一条 DB 查询挂死
  在已断的 SSL socket 上**（阻塞读不抛异常 ⇒ database.py 的"异常才重置重连"自愈永远不触发）。

### 二、根因与修复
- `_get_pg_conn` 已有 keepalives（30s idle）+ connect_timeout，但**没有 statement_timeout**
  ⇒ "连接活着但查询永远不回"的形态防不住。
- **修复 = 脚本层 db 调用看门狗**（不动生产 database.py）：包装 `db.execute/fetch`，
  后台线程跑原调用，主线程 join 240s 超时后 **`conn.cancel()`**（psycopg2 官方跨线程
  中断机制）⇒ 阻塞调用立刻抛 QueryCanceled ⇒ **database.py 既有自愈（重置+重试）接管**，
  下一天自动换新连接。
- 杀掉挂死进程（2888）→ 补丁 → 重启续传（370/426，flow 缓存因宇宙并集 941→947 变化
  重读一次，属一次性成本）。

### 一、归因（用户报"昨天 1.557GB / 今天 560MB"，用项目自带 egress_probe diff 实测）

### 二、根因（两重浪费叠加）
1. **SQL 侧没有行数截断**：回退查询每票返回全历史 ~500 行，内存里才截 BARS=260；
2. **逐日重复读**：pack 未覆盖的 ~9% 票（每日 ~88 只，多为"如今不在当前市值池"的票）
   的同一段历史被 426 天反复读。
★ 方法论：**"本地跑不是免费的"**（EGRESS.md 核心原则一）——pack 未覆盖的 fallback
路径必须**缓存 + SQL 侧截断**，逐日循环里绝不允许重复拉同一数据。

### 三、修复（已生效，重启续传 370/426）
`BarsSource` 重构：fallback 票**一次性**直读（SQL 侧 `ROW_NUMBER()` 截 260 根 +
重试）→ 本地 JSON 缓存 `mf_edge_bars_cache.json` → 逐日复用**零 egress**。
意外利好：**昨晚 Actions 新包已含科创板**（pack 2736→2968 只）⇒ fallback 票骤减，
剩余 56 天 ≈ 零 egress。
