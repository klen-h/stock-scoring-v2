
### 审查结论（改前逐项核对语义）

| 项 | 风险核对 | 结论 |
|---|---|---|
| ① `_load_bars_batch` 窗口函数 | 只用 `bs[-120:]`，改后语义等价 | 安全 |
| ② 列探测缓存 | 表结构运行时不变量；异常早退不置位 | 安全 |
| ③ 行业映射走缓存 | `ind.get(code)` / `imap.get(code,"其它行业")` 对缺失都安全 | 安全 |
| ④ 排除 `candidates_json` | 全库搜索确认**只写不读** | 安全 |

### ① 最大头：实测行数 -80%、耗时快 5 倍

```
60 只票：
  旧  36,100 行 / 246.63s
  新   7,200 行 /  48.23s
  行数 -80.1%，耗时 -80.4%
逐票比对最后 120 根的 date/high/low/close ⇒ 全部一致 ✓
```

**验证时 200 只票的旧查询直接把 SSL 连接撑断了**（11.4 万行）——
这本身就是改动必要性的现场证据。

按 5 次/天 × 200 只推算：日传输 60 万行 → 12 万行，**省约 122MB/天**。

### ② 列探测缓存

`information_schema.columns` 一天 **1553 次**（全库调用次数第一）。
加 `_COLS_READY` / `_ALERT_COLS_READY` 进程级标志。

**⚠️ 关键细节：探测异常时早退不置位**，否则一次网络抖动会让补列永远不执行。

### ③ 行业映射走缓存

`stock_industry` 全表 5932 行 ≈ 1MB，一天被 12 次重复读。

实测：首次 **38.4 秒**（远程库确实慢），二次 **0.00000 秒**，
与直读底表结果**完全一致**（5932 条）⇒ 约省 11MB/天 + 11 次长往返。

### ④ 排除 `candidates_json`

平均 **276 字节/行**，`/plans` 一天 374 次 × 约 160 行 ⇒ 约 **16MB/天**。

改成显式列清单 `_PLAN_SELECT_COLS`。
**⚠️ 注释写明：将来给 `t_plans` 加列要同步加进清单**，否则读出来是 None 且不报错
—— 这是放弃 `SELECT *` 的代价，必须留痕。

```
350MB/天  → 约 200MB/天（-43%）
```
