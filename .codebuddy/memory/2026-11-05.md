## CI 产包失败：data/kline 目录在干净 workspace 不存在（54962642）

**现象**：`backend-pack.yml` 的增量步骤重试 6 次全失败（6 × 10 分钟白等）：
```
FileNotFoundError: './data/kline/_backend_prev.db.download.gz'
  at update_backend_pack_incremental.py:53  _download_raw → open(dest,'wb')
```

**根因**：`.gitignore` 里有 `data/` ⇒ CI 的干净 workspace **没有 `data/kline` 这个目录**；
而 workflow 直接传 `--pack-dir ./data/kline`，脚本 `_download_raw` 又**假定父目录存在**，
`open(...,'wb')` 直接炸。目录不会自己长出来 ⇒ 重试必然全废。

**⚠️ 这类错本地永远复现不了**：本地跑过一次就有目录了，之后怎么跑都正常。
以后凡是"写文件"的脚本，都要先 `os.makedirs(os.path.dirname(dest), exist_ok=True)`。

**修复（双保险）**：
1. `_download_raw` 下载前建父目录（幂等）；
2. workflow 该步骤加 `mkdir -p ./data/kline`（显式，也便于排障）。
验证：目标目录预置不存在 → 调 `_download_raw` → 目录被创建（下载本身按预期 ConnectionError）。

**注意**：本次失败意味着**当天的后端包没生成** ⇒ 下游 `daily-batch` 的 `ensure_pack_fresh`
会一直等不到新包（它按 22:00 分界判"应可用"）。修复推送后需**重跑 backend-pack**。

## 纳指隔夜口径错 + 持仓市值与成本价耦合（b825be7e）

**① 教练"纳指隔夜 -1.14%"，用户看 11/4 纳指是涨的 —— 两个口径混用**
实测（11-05 21:40，`get_macro_panel()`）：

```
nasdaq   28338.75  -0.80%   ← hf_NQ **期货**，change_pct 相对"上一结算价"
us_ixic  25736.51  +1.44%   ← 现货 IXIC，**11/4 收盘**
us_spx    7688.62  +1.58%   ← 11/4 收盘
us_dji   53356.12  +3.03%   ← 11/4 收盘
```
`coach/rules._macro()` 原用 `nq.change_pct`（期货）当"纳指隔夜"。
但北京时间 09:25 时，期货反映的是**美股盘前电子盘**（含 11/5 盘前），
而"昨夜美股收盘涨跌"是**现货指数**的日涨跌 —— 语义完全不同。
用户看到的 -1.14% 是前者，他记忆中的 +1.44% 是后者，各自都对。
⇒ 改用 `us_ixic.change_pct`（取不到才回退期货，并带 `nasdaq_src` 标注）。
⚠️ 阈值 `nq_pct: -0.76` 是按期货口径定的，换现货后**未重新校准**（现货日波动略小，
该阈值偏保守=更易触发），先观察。

**② 持仓市值 0 万 —— `mv` 被嵌在盈亏分支里**
`portfolio_radar.build()` 原代码：
```python
if price and h["cost"] > 0:
    item["pnl_pct"] = ...
    item["mv"] = round(price * h["shares"], 2) if h["shares"] else None   # ← 在这里
```
市值只需要 `price × shares`，**与成本价无关**；成本为 0/缺失的持仓（手工录入常见）
⇒ `mv` 字段整个不存在 ⇒ `amreview` 的 `total_mv += float(it.get("mv") or 0)` = 0。
⇒ 已拆开：市值独立算，盈亏才依赖 cost。

**③ 另一个可能成因（未确认）**：`peek()` 只读进程缓存，脚本里调 `peek()` 返回
`items: 0`（缓存空是正常的）。若线上 `price` 拿不到（`tencent._cache` 为空/未预热），
`mv`/`pnl` 同样整个缺失 ⇒ 也是 0。需看工作台"持仓雷达"卡片是否正常来区分。

**④ 宏观面板 vs 隔夜块（回答用户"是不是相加"）**：**不是相加，是两个独立指标**
- 面板每项 = 该项**自己的当日涨跌**（相对昨结算/昨收），实时值；
- 「隔夜变化」块（`get_overnight_change`）= **自最近一次 A 股收盘后快照（如 15:03）以来**的累计。
实测同时刻：纳指期货面板 -0.80%，隔夜块 +0.22% —— 时间窗口不同，同时显示不矛盾。

## 快讯解读把昨天的板块涨幅当今天盘面（2d616cf2）

**用户给的实例**（2026-11-05 09:56 的快讯解读）：
> 盘面半导体、电子化学品领涨，**贵金属大涨 10.08%** 与快讯利空矛盾，需警惕情绪透支。

**证据（确认用户正确）**：
```
sector_daily  贵金属 2026-11-04 = +10.45%   ← AI 引用的就是这个量级
东财实时      贵金属 2026-11-05 = +5.84%    ← 当天实际
个股 11-04：赤峰 +10.00%（涨停）/ 银泰 +10.01% / 中金 +9.39%
个股 11-05：赤峰 +8.80% / 山金 +5.03% / 中金 +3.14% / 紫金 +0.79%
```

**根因**：`flash_brief._sector_section()` 调 `eastmoney.get_sectors()`，
而它的降级链是 **东财主站 → 东财 delay → zzshare（日频）→ 新浪**。
落到 zzshare 时 `change_pct` 就是**上一交易日收盘**的板块涨幅，
而 `_user_prompt` 里只有一行 `### 板块（涨跌幅）`——**没有任何日期**。
⇒ LLM 拿昨天的 10% 当"今天盘面"讲，还据此判"贵金属与快讯利空矛盾 → 情绪透支"。
⚠️ **指数是实时的（腾讯）而板块是日频的** ⇒ 模型在做"今日指数 vs 昨日板块"的
混合对比，这类结论**整段不可信**。

**修复（两层）**：
1. `_sector_section()` 增 `stale` / `as_of` / `src`：只有**全部行的 source 都是
   `zzshare`** 才判日频（东财/新浪分支的 dict 无 source 字段 = 实时）。
   日频时从 `sector_daily` 取 `MAX(date)` 作为 as_of。
2. prompt 段落头改成 `### 板块（涨跌幅）⚠️ 数据日 2026-11-04（日频快照，不是今日实时）`；
   SYSTEM 加第 6 条：**引用日频段落必须带上日期，严禁说成「今日盘面」**，
   当日实时缺失时宁可不描述。

实测渲染：日频 → 带 ⚠️ 与日期；实时 → `### 板块（涨跌幅，实时）`。

**方法论收获**：这属于"**混合时点数据拼进同一个 prompt**"——比单纯"数据过期"更隐蔽，
因为**逐项看都新鲜**（指数实时），只有一两个维度是旧的。以后往 prompt 塞多源数据，
每段都必须自带时点。

## 关键位轻量实时化（303bd01a）+ 发现既存数据 bug

**用户决策**：三个观察器里只做关键位实时（拥挤/推演不做，理由见前一轮）。

**方案（关键取舍）**：**只覆盖"现价/涨跌/距离"，不动 `support` 与 `broke`**
- `support`（前低60/整数位/年内低点）一天只变一次，重算毫无意义；
- `broke` 是"首次失守"的**状态量**，盘中翻转会污染它（模块注释早有此警告）；
- 盘中真正在变的只有"现价离支撑多远" ⇒ 一次指数报价即可，**零 K 线请求**。
新增字段：`live` / `live_as_of` / `live_broke`（盘中是否正在跌破）/ `support_suspect`。

**只在"看最近交易日"时覆盖**：判据用 `requested >= latest_completed_trading_day()`
（不查 `MAX(date)` —— 多一次 Supabase 往返多 1~2 秒）。回放历史日原样返回当日结论。

**性能**：6 个指数原先**串行 10.1 秒** ⇒ `ThreadPoolExecutor` 并发后
冷 4.6s / 热（15s 缓存）1.2s。前端 120s 轮询够用。

**★★ 顺带发现一个既存的数据 bug（不是本次引入）**：
`key_level_watch` 2026-11-04 落库：
```
000905 中证500   close=8.33    support=8.04     ← 实际 6740
000985 中证全指  close=15.95   support=14.66    ← 实际 5211
```
两只指数的 K 线被取成了**别的标的**（价格量级差 3 个数量级）。
之前没人发现，是因为**距离百分比自己跟自己比**（8.33/8.04=3.6%）看起来完全正常。
本次实时化把"实时 6740 vs 落库支撑 8.04"放在一起算，才暴露成 83742%。
⇒ 已加护栏：支撑位与现价差 10 倍以上就不再重算距离（沿用落库值 + 标 `support_suspect`）。
⚠️ **根因未修**：`compute()` 里 `_load_index_kline("000905"/"000985")` 取错了 K 线，
需要单独查（可能是东财兜底的 secid 或代码前缀映射）。

**答非所问比不做还糟。**
试过 `stock_industry.main_industry_code`（申万细分），也不够：A 股没有"黄金""石油"
这两个细分名，且约一半取值是 `new_dzxx` 这类**代码**而非中文。
⇒ 最终：**粗行业圈范围 + 名称关键词收口**（`THEME_INDUSTRY` 里每个行业带 `name_kw`）。
关键词**宁可窄不可宽**——宽了正是第一版失败的原因。

**★ PostgreSQL 的坑（通用，容易再犯）**：
`ORDER BY score_total DESC` 在 PG 里默认 **NULLS FIRST**，直接 `LIMIT 5` 取到
5 只 `score=None`（不在精算榜的票）。必须显式 `NULLS LAST`。
另：`stock_facts_wide` 只有**精算榜 top1000** 有 `score_total`，其余为 NULL（不是 0）。

**实测结论**：`化工行业` 里一个"石化/炼化/油服/油气"都没有（全归在"石油行业"，
只有 10 只且本来就准）⇒ 该组已删除，避免永远空着一行让人以为数据缺失。

**下一步（未做）**：金十「重要人物讲话」→ 人物立场时间线。
价值不在"再加新闻源"，而在**同一人 48 小时内立场反转**（Trump 11-03 打击设施
→ 11-04 可签协议 → 11-05 承认是败选主因）。`jin10_tidy` 只覆盖 4 个栏目不含人物，
需**先实测人物接口**（不可再像 10-30 那样猜 id 扫描）。

## 人物立场时间线（03d46242）——接口实测 + 标红是关键

**接口**（用户提供，已实测）：
```
GET https://mp-api.jin10.com/api/free-flash/list
    ?people_org_id=83&limit=20&page=1&date=2026-08-05&date_end=2026-11-05
```
**鉴权实测三档**（本地验证，环境无 token）：
```
裸 header              → HTTP 502（空响应）
+x-app-id/x-version    → HTTP 200 但 {"status":401,"message":"请登录"}
+x-token               → 正常
```
⇒ 与 `tidy-news` **共用 `JIN10_X_TOKEN`**，直接复用 `jin10_tidy._headers()`。

**★★ 核心发现：金十自己把关键句标红了**
```html
<span style="color: rgb(235, 69, 57);">如果伊朗表现良好，我们可以签署一些协议。</span>
```
另有 `<b>` 粗体强调。⇒ **不需要 LLM 判断哪句重要**，直接取编辑高亮。
省 token，也避免"模型总结损耗原文"（同 `jin10_tidy` 的原文直出立场）。
⚠️ 必须按**原文位置**排序（红 span 与 b 可能穿插），顺序本身是判断立场演进的信息。
⚠️ 只认 `rgb(235,69,57)` 这一个色值 —— 正文还有别的 span 用于排版，全取会退化成整段照抄。

**★ 实时性：用户判断正确，接口不是实时的**
实测：11-05 22:00 时最新一条 `publish_time=11-04T17:29Z`（北京 11-05 01:29），
而快讯里 11-05 21:50 已有哈玛克讲话。
⇒ 本接口 = 编辑**整理后**发布，T+1 才有。
⇒ 设计分工：**历史结构化用本接口，当日实时看 `flash_brief`（快讯流）**。
   不为必然延迟的源做"伪实时"，否则出现两个口径。

`flash_news` 能否实时过滤人物（实测近 19 天 / 818 条）：
```

黄仁勋 1 / 奥尔特曼 1 / 苏姿丰 0 / 鲍威尔 0
```
⇒ 只覆盖高频人物，**不能替代人物接口**，但够给"当日实时"兜底。

**★ 时区坑**：`publish_time` 是 UTC ISO，`2026-11-04T17:29:27Z` 在北京是 **11-05 01:29**。
直接截前 10 位会把整条时间线错位一天。必须转 `+08:00` 再取日期。

**实现**：`backend/app/people_watch.py` + `GET /system/people-watch`（读库，零外呼）
+ `POST /system/people-watch/refresh`（手动拉）+ 日批 `task_people_watch`
（紧跟 `jin10_tidy`，共用 token；`days=7` 增量）+ 观察器第 4 行「人物立场」（懒加载）。

（同 `thesis_tracker` 的顾虑）。

## 震荡区间识别（bdd5b577）——"底部震荡洗盘"四功能之功能 1

**用户诉求**："底部震荡常匪夷所思、散户易被洗下车"，要求分析 + 功能设想。
方案给了 4 个功能（震荡区间 / 洗盘打分 / 持仓耐心度 / 异动区分），
用户 2026-11-05 明确 **"先只做功能 1"**。

**排查出的结构性缺陷（这是整个方案的地基，比功能本身重要）**：
- `exit_advice.py` 9 档优先级**全是幅度判据**：−8% / 跌破支撑 / 回撤 8% / 浮盈 30% …
- `rules.yaml` 持仓纪律：`stop_loss_hit` / `hold_3d_review`（**固定 3 日**）/ `loss_over_7pct` / …
- **没有一条"环境"判据**（这个跌幅在箱体什么位置）
- ⇒ 在区间下沿，−8% 可能只是日常试探，但规则眼里和"趋势破位"长得一模一样。
- `mainforce/phases.py` 虽有 `shakeout`，但要求 `ret_20 > 8 and px > ma60`（上涨中洗盘）。
  实测 11-04 全市场：decline 1903(66%) / sideways 596 / accumulation 198 / markup 138
  / distribution 12 / **shakeout 仅 6 只(0.2%)** —— 底部场景**永不触发**。

**实现**：`backend/app/range_watch.py` + `GET /system/range-watch`
+ 日批 `task_range_watch`（并入 `market_observers` 四合一）+ 观察器「震荡区间」卡。

**口径（三个关键取舍，改前必读模块 docstring）**：
1. 上下沿取**前 59 日** highs/lows，**不含当日** —— 否则当日永远在自己区间内，
   "今天突破了"在数据上永远不成立。
2. `range_days` = 收盘价**连续待在 [lo,hi] 内的天数**，回溯窗口必须 **120 根**
   （`MIN_BARS=120`）。只回溯 60 根会恒等于 59（窗口内收盘必然在区间内），毫无信息。
   用 close 而非 high/low：盘中刺破后收回恰恰是洗盘的定义。
3. 振幅须在 **15%~35%** 且持续 ≥15 日才算"区间"。太窄是死水，太宽已是趋势。

**★ 三个实测踩坑（都花了时间，必须记住）**：

① **逐行 INSERT 慢到不可用**：600 行 = **715 秒**（1.2 秒/行，每次一个到 Supabase 往返）。
   ⇒ 改 150 行一批批量 INSERT 后同批 **30 秒**（24 倍）。
   ⚠️ 凡是"一天一行 × 全市场"的表，**必须批量写**，参考 `stock_facts.build`。
   之前没暴露是因为 `ai_basket_watch` 只有 7 行。

② **保留策略不能用自然日**：原 `DELETE WHERE date < (今天-5天)`，
   而数据包 K 线日期可能滞后（本地实测只到 **2026-10-22**），
   `date < 2026-10-31` 会把**刚写入的数据立刻删光**
   （现象：`compute` 报 594 行，查库只剩 31 行旧数据 —— 极难排查）。
   ⇒ 改成"取库里最近 KEEP_DAYS 个**数据日期**，NOT IN 的删掉"，与自然日无关。

③ **破位阈值比突破要敏感**：初版 `BREAK_DN=0.995` 导致"收 2.03 / 下沿 2.04"
   （比值 0.9951）被算成**下沿**而非破位 ⇒ 全市场 909 只挤在"下沿"，状态分布失真。
   ⇒ 改为 `BREAK_DN=0.999`（跌破前 59 日最低价 0.1% 即破位），
      `BREAK_UP=1.005` 保持不变（假突破太常见，需 0.5% 确认）。

**性能**：`crowding_watch._PackView.get_klines` **每只新开 sqlite 连接**，
逐只 2864 只跑到超时 ⇒ `_bulk_klines()` 按 300 只一批、复用连接、
用窗口函数取每只最后 120 根（不按日期字符串过滤，格式未约定会静默失效）。

**实测结果**（600 只样本）：区间内 216 / 下沿 284 / 破位 133 / 中部 168 / 上沿 7 / 突破 2。

**⚠️ 本地数据包只到 2026-10-22**（线上日批会更新包），所以本地样本不代表当日实况。
