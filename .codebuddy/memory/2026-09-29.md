## ★★ 竞价看板「一会一个、一会三个」= **真 bug**（名单来源写错），已修

**用户**："盘中的竞价看板「一会一个、一会三个」也是正常的吗？"
⇒ 我前一天的答复（"竞价窗口内开盘价逐步到位"）**只答对一半**：那只解释 9:15–9:25 的小波动，
   解释不了"**盘中**还在跳"。本轮查清并修复。

### 一、真因：名单来源在开盘前后**整批切换**

`routers/market.py` 的 `gaps`（= 面板上的 `count` / `avg_gap` / `Top5`）原来遍历 `limit_up_codes`：

```python
limit_up_codes = [c for c, s in stocks.items() if (s.get("change_pct") or 0) >= 9.5]
```

它筛的是**行情缓存里的「当日涨幅」**：

- 开盘**前**：行情缓存还是上一交易日快照 ⇒ 筛出的是「**昨**日涨停」（与面板文案相符）；
- 开盘**后**：`change_pct` 变成当日 ⇒ 筛出的是「**今**日涨停」！

⇒ 同一份代码在开盘前后筛出**完全不同的名单**，且盘中名单**随涨停家数一路变**
⇒ `count / avg_gap / Top5` 必然乱跳（用户看到的"一会一个、一会三个"）。

★ **旁证**：`avg_gap = -7.44%`（"昨日涨停股今日平均高开 -7.44%"）在正常市场极罕见 ——
  它实际算的是「**当日涨停股**的开盘涨幅」（当日涨停多为低开后拉板 ⇒ 开盘普遍很负）。

★ **正解就在上方 ~30 行**：`prev_limit` 是**由历史收盘算出的真正「昨日涨停名单」**
  （`d_prev` 相对 `d_prev2` 涨幅 ≥9.5%，同函数内已用于 `money` 赚钱效应）—— 它当天**恒定**。

### 二、修法（`routers/market.py` 3 处 + 前端 1 处）

1. `for code in limit_up_codes:` → `for code in prev_limit:`
2. `"limit_up_total": len(limit_up_codes)` → `len(prev_limit)`
   （昨日新加的分母必须同源，否则"11/40"的分母是"当日涨停家数"、分子是"昨日涨停股"= **不同日**）
3. 新增 `"covered"`：`closes` 里 `d_prev` 有值的股票数（让前端能解释"数字偏少"）
4. 前端：给"竞价看板 · 昨日涨停"加 hover，写明**口径与两条边界**（见下）

### 三、★★ 本轮拿到、以后会反复用到的数据事实

| 事实 | 值 | 影响 |
|---|---|---|
| `backtest_prices` 覆盖 | **839 只**（非全市场，全市场 ~2083）| 由它自算的涨停名单**必然少于**真实涨停家数（已结算昨日涨停 ~47 只）|
| `_prev_trading_day('2026-09-28')` | = **2026-09-24**（不是 09-25）| **2026-09-25 休市（中秋）** ⇒ 09-25 缺数据**不是缺口**，`prev_limit` 可用 |
| `_prev_trading_day` 用**交易日历**（非"有数据的日期"）| — | 日线缺某天**不会**让 `d_prev/d_prev2` 错位 |

**实测**：`limit_up_total(prev_limit) = 11`（与用户看到的"11 只"完全吻合）、`covered = 839`；
本地无行情缓存 ⇒ `count = 0`（预期）。

**证据链（逐只精确吻合，可复现）**：

| 代码 | 线上 `/score/batch/top` 的 `change_pct` | 库里 `backtest_prices` 09-24 涨幅 | 本地新拉腾讯（=09-28 收盘） |

| 000612 | **-2.10** | -2.10 ✓ | -4.86 |

证据 —— `_price_date()` 是**日历推断**（盘中=今天 / 否则=最近已完成交易日），与缓存真实内容无关。
⇒ 这是"日历口径"与"数据口径"混用的典型陷阱。

### 二、机制（`tencent.py` 106-123 行的注释**早就写明**，只是消费者没用）

⇒ 要显示"数据截至"**必须用 `data_ts`**。而持仓卡显示的是 `as_of`（= 本次**计算**时刻 00:21）

`print`，日志一滚即丢）⇒ 缓存两天不动，最后由**用户肉眼**发现。这正是本项目最贵的"静默失效"。

## ★ 顶栏浮层溢出屏幕（「宏观与环境」/「系统状态」）—— 2026-09-29

**用户**："顶部的宏观与环境点击显示的弹窗长度都溢出屏幕了，看不完整"

**先排除误判**：`max-h-[70vh]` 类**确实已生成**（`dist/.../index-*.css` 里有 `max-height:70vh`）
⇒ 不是"Tailwind 没扫到"。真因是 **`absolute left-0 top-full` + 视口比例高度**这两点：

1. **水平溢出（"看不完整"的主因）**：触发按钮在顶栏**右侧**，而 `left-0` 把面板**左边缘**
   对齐按钮 ⇒ 最宽 720px 的面板**向右伸出视口**。
2. **垂直没扣顶栏**：`max-h-[70vh]` 按视口算，未扣掉起点 —— `App.vue` 顶部导航是
   `sticky top-0 z-50`（48px），且该浮层挂在**可换行（flex-wrap）的顶栏行内**。

**改法**（`Workbench.vue`）：
- 宏观浮层 ⇒ `<Teleport to="body">` + `fixed left-1/2 -translate-x-1/2 top-[3.25rem]
  w-[min(92vw,720px)] max-h-[calc(100vh_-_4rem)] overflow-y-auto overscroll-contain rounded-lg shadow-2xl`
  ⇒ 两侧都不可能出屏；底部恒在屏内 12px 处，超出走内部滚动；
  Teleport 还顺带摆脱祖先 `overflow/sticky` 的裁剪与层叠（与 `Strategies.vue` 详情弹窗同款做法）。
- 系统状态浮层 ⇒ 仍在左侧 `left-0`（无横向风险），仅高度上限改
  `max-h-[calc(100vh_-_6rem)]` + `overscroll-contain`。
- ⚠️ Tailwind 任意值里 `calc` 的空格必须写 `_`（`calc(100vh_-_4rem)`）；压缩后会被转成
  `64px` 之类 ⇒ 核对生成结果应 grep `max-height:calc`，别 grep 原字面量（会误判为"没生成"）。

**验证**：`npm run build` 通过（709 modules，12.01s，0 error）；`read_lints` 0 error；

### 追加：浮层"横滚出去的那块背景是透明的"（同日用户追问）

用户："点击显示之后，滚动到最右边，溢出部分的背景色怎么是透明的"

**原因（两层）**：
1. 滚动容器当时只写了 `overflow-y-auto` —— 按 CSS 规则，**另一轴是 `visible` 时会被计算成 `auto`**
   ⇒ 面板其实**会横滚**（用户能"滚动到最右边"就是证据）；
2. 但**容器自身没有底色**。而卡内首行是 `flex` + 多个 `flex-shrink-0` 段
   （`MacroEnvCard` 刻意"严格单行不换行"，注释里写明）⇒ 面板变窄时内容比容器宽；
   卡片是 `w-full` 块级元素、**底色只覆盖自身矩形** ⇒ 横向滚出它右边缘的那片区域无人上色
   ⇒ 露出页面（视觉上就是"透明的"）。

**改法**：滚动容器补 `bg-card` + **显式** `overflow-x-auto`（自述"会横滚、且已兜色"）。
⚠️ **不用 `overflow-x-hidden` 压制** —— 那会把"事件诊断/叙事"整段裁掉
（本项目纪律：宁可能滚，不可丢信息）。

**验证**：`npm run build` 通过（709 modules，17.24s，0 error）；`read_lints` 0 error。**待部署**前端。

### ★★ 解屏蔽（A）容量评估（用户问"Render/Supabase 支撑得起吗"）——实测答案

**结论：分层看 —— 行情缓存 ✅ 撑得住；价格数据源 ❌ 撑不住。**

| 维度 | 实测 | 解屏蔽后 | 判定 |
|---|---|---|---|

**★ 真正的瓶颈（不在 Render/Supabase 的"量"，而在架构）**：

**所以 A 应拆两步**：
- **A1（低风险，现在可做）**：解屏蔽**行情缓存**（涨跌家数/成交额/情绪/涨停统计变全市场口径）
  —— 但评分/战法仍只能对有 K 线的股票生效（数据缺口未解）。
- **A2（需架构调整，另立项目）**：价格数据源扩全市场 ⇒ **不能再用"整表常驻内存"模式**

  —— 重扫用的是本地 `zzshare_daily.db`（1.6GB，线上放不下），这也是线上全市场化的硬约束。

**建议路径**：先做 **B（展示层修正）** → 再评估 **A1** → **A2 单独立项**（含数据源架构选型）。
