## 99 ★ 盘中「变化检测器」上线（用户：先上变化检测器）

### 一、定位
用户原问"盘中每半小时用 LLM 分析工作台是否可行"。结论：机制可行，但工作台大半数据是
**日频**（mainforce/评分快照/教练卡/行业映射）⇒ 8 档里多数会复读；LLM 还有额度/熔断成本。
⇒ 先上**零 LLM 的规则采样**，用 `worth_rate` 回答"8 档里几个真有料"，再决定是否付费。

### 二、实现
- **新增 `backend/app/workbench_scan.py`**：
  · 采样点 `SLOTS` = 09:45/10:15/10:45/11:15/13:15/13:45/14:15/14:45（宽限 35 分钟补采）。
  · 采集：3 个核心指数（**1 次**腾讯请求）+ 宽度（`routers/market._breadth_now`，零网络）
    + 板块强弱（`sector_industry.industry_amount_share`，内存+映射，零外部请求，剔"其它/综合行业"、
    成分 <10 只的板块）+ 近 30 分钟快讯（`load_raw_items` 缓存，含高信号关键词）。
  · 差分：**交易分钟**而非墙钟（11:15→13:15 = 30 分钟；`_trading_minutes` 已实测）。
  · 判定：规则打分 0~100，`score>=40` = worth；tag 见下。
  · 落库 `workbench_scan`（key=`date|slot`，幂等；8 行/日，保留 120 天）。
- **调度器**：`flash/scheduler.workbench_scan_loop()` 每 60s 醒，交易时段命中采样点才采；
  **只读模式保留**；每档只 3 个指数请求，比任何现有盘中循环都轻。
- **API**（`routers/system.py`）：`GET /api/system/workbench-scan?date=`、
  `/workbench-scan/summary?days=7`、`/workbench-scan/preview`（只读、不写库）。
- **脚本**：`scripts/workbench_scan_probe.py --preview|--run|--summary|--day`。

## 100 ★ 前端 K 线包被 WAF 拖到 timeout（用户贴日志："昨天开始才出现的问题"）

### 一、定位
- 日志来自 **`kline-data.yml` 的 frontend-pack**（2144 只 / 并发 1 / 2 QPS / 150 分钟 timeout）。
- `[3/4]` 之后每 ~50 只成功就一次 `[WAF] 第 N 次拦截 ... 本次冷却 120s`；
  两次拦截之间的成功数 **132 → 48 → 34 → 26 → 20 → 12** 逐级下滑
  ⇒ 实际放行速率 ≈ **0.4 QPS**，2144 只至少要 ~90 分钟，叠加末根补齐/重试轮后
  150 分钟跑不完 ⇒ GitHub 把超时表现为 `cancelled`（连带 Pages 发布 skipped）。
- 脚本自 **10-11 起未改** ⇒ 不是代码回归，是腾讯配额收紧（本地单请求仍 200，
  说明不是硬封 IP，是**滑动窗口配额**）。

### 二、三个叠加的代码缺陷（这次一起修）
1. **退避加倍条件永不成立**：`_waf_record_501` 只在「**冷却期内**再收到 501」时 ×2，
   但冷却是全局门 ⇒ 冷却期根本发不出请求 ⇒ 单线程下退避恒为 1.0（日志每次都 120s）。
2. **成功路径的重置是死代码**：`fetch_kline` 里 `_waf_backoff = 1.0` 没写 `global`
   ⇒ 只是建了个**局部变量**，模块级退避从未被"成功"重置。
   （本次给 `_waf_success_streak += 1` 时踩出 `UnboundLocalError` 才发现。）
3. **501 被当成"这只股票失败"**：`return None` ⇒ 进 failed 列表 ⇒ 下一轮再请求
   ⇒ 每撞一次墙多制造一次请求（正反馈，越封越多）。

### 三、改动
| 位置 | 内容 |
|---|---|
| `generate-kline-pack.py` | 退避改为按**两次 501 的间隔**判断（<15 分钟 ⇒ ×2，封顶 300s）；只有「连续成功 ≥300 且距上次 501 ≥15 分钟」才回落；撞墙同时**自适应降速 ×0.6（下限 0.25 QPS，只降不升）** |
| 同上 | 501 → 等待后**重排该股**（不消耗 `KLINE_RETRIES` 真实预算，单只最多 `WAF_RETRY_MAX=3` 次）；拦截达 `WAF_MAX_EVENTS` **主动抛错**（failure 而不是 cancelled） |
| 同上 | `PACK_QPS` 默认 **2 → 1**；新增 `PACK_QPS_MIN / WAF_QUIET_RESET_SEC / WAF_SUCCESS_RESET / WAF_MAX_EVENTS / WAF_RETRY_MAX` |
| `kline-data.yml` | timeout **150 → 240**；显式 `PACK_QPS=1 / QPS_MIN=0.3 / WAF_MAX_EVENTS=40` |

### 四、验证
- 无网络单测（临时脚本已删）：连续撞墙 1→2→4 + QPS 2→1.2→0.72→0.432 ✓；
  间隔 >15 分钟回落 1.0 ✓；2 次 501 后成功（3 请求拿到 30 根）✓；
  4 次 501 放弃该股 ✓；事件达上限抛 RuntimeError ✓。
- 真实请求 1 只（days=40）：200，40 根，末根 2026-10-21，WAF=0 ✓
  （顺带发现 `days<30` 必然失败 —— 成功判据硬编码 `len(result)>=30`）。
- **未 commit**（仅这两个文件）。

### 六、追加（用户补后端包日志："之前就有超时的情况"）
- **后端包 2915 只 × 750 根**（`generate_backend_pack.py` 直接 import `generate-kline-pack.py`，
  所以上面的 WAF 修复对它同样生效）。日志：1 QPS / 并发 5，**第 1 次 WAF 只出现在 99 只**，
  之后 120→240→300 连环冷却，1 轮都跑不完。
- ★★ **关键发现：两条包任务会重叠**。前端包 18:00 启动，正常 18:37 结束 —— 但被 WAF
  拖到 150~240 分钟时，会与 **19:00 启动的后端包**重叠 90~150 分钟。两个 job 虽在不同
  runner，但 GitHub 托管 runner 的出口 IP **不保证不同**（同区域 NAT 复用），而腾讯是
  IP 级滑动窗口 ⇒ 后端一开局就只有 ~100 个请求额度（99 只即撞墙就是这个形态）。

- ★ 同源 bug：`backend-pack` 的**兜底 guard 只看"最近 12h 是否有 success"** —— 现在 job 可能
  跑到 22:00 之后，22:00 的兜底 schedule 会在第一次还没跑完时触发 ⇒ 排队再跑一遍 2.5 小时。
  已加"是否已有本 workflow 在跑/排队"判断（**排除当前 run_id**），命中即 skip。

  180 等待 + 139 < 360）、`PACK_WAF_MAX_COOLDOWN=600`（300s 实测排不空窗口）。
