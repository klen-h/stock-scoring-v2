## 教练「加仓」三条规则互相打架（ab590c65）

**用户报**：11-06 09:15 教练卡两条记录矛盾 ——
```
大涨日不追   已执行   【涨了别追】今日全市场等权涨幅 +2.21%
加仓条件命中 已放弃   【加仓条件确认（连续 2 日）】涨跌比 0.88 且跌停 0 家
```

**实测落库其实是三条**（同一天 09:15）：
```
no_chase_rally   market_avg_pct=2.21   → 大涨不追
gate_add         ratio=0.884, ld=0     → 加仓条件确认（可加）
gate_no_add      regime=defensive      → 环境不支持加仓
```
**11-03 / 11-05 / 11-06 三个交易日全部这样**，不是偶发。

**根因**：三条判定各自独立、彼此不知情 —— `_ev_gate_no_add` 只看 regime、
`_ev_gate_add` 只看 breadth、`_ev_no_chase_rally` 只看等权涨幅；
`coach_tick()` 拿到 `evaluate_all()` 结果直接落库推送，**中间没有任何消解层**。

**修复（方案 1+2）**：
1. 新增 `_arbitrate(advices)`，在 `evaluate_all()` 出口调用。
   `gate_add` **不删除**（"条件满足"是真事实、有信息量），但降级为
   「加仓条件满足，但今日不执行」，逐条列出否决原因（regime / 大涨）。
   `label` 改「加仓条件（被否决）」，`numbers.blocked=True`、`blocked_by=[...]`。
   ★ **只动市场级（`code` 为空）**，个股风控（止损/持有/出货/拥挤）一律不碰。
2. 新增 `_data_stamp()`：读 `tencent._cache["data_date"]`（**项目里唯一把
   "写入时刻"与"数据时刻"分开的字段**，见 tencent.py `_cache` 结构注释），
   数据日 ≠ 今天才追加"，数据截至 2026-11-05 收盘"。
   `no_chase_rally` 文案去掉误导性的"今日"。

**为什么盘前会错位**：`stock_cache_refresh_loop` 只在 `market["is_open"]` 时刷新，
09:15 未开盘 ⇒ 缓存里是**上一交易日收盘**，而文案写的是"今日"。
这与 11-05「快讯解读把昨日板块涨幅当今日盘面」是同一种病：**写入时刻冒充数据时刻**。

**测试**：`test_coach_rules.py` 从 38 → **46 条全过**。新增六项：
三条同时命中仍输出但降级 / 原因写明 / `blocked=True` / label 改变 /
无冲突时不改写（回归保护）/ 个股风控不受影响。
测试里 monkeypatch `_gate_add_prev_day_hit`，保证离线不查库。

**未做（方案 3）**：`_gate_add_prev_day_hit` 仍按 `alert_date`（运行日）判连续，
而 `alert_date` 记运行日、数据日可能是 T-1 ⇒ 11-05 09:43（盘中数据）+
11-06 09:15（11-05 收盘数据）会被当成"连续两日"。要修需让每行带数据日字段。

### ② 教练卡折叠（已完成）

现在：按钮放 tab 行右侧、只在「教练卡」tab 显示；收起态显示

（原来只在内存，刷新就回弹）。

### ① `scripts/export_local_sqlite.py`（已提交，正在跑）

远程 PG → `backend/data/app.db`。默认：小表全量 + 大表最近 90 天
（`backtest_prices` 125MB→约 16MB；`kline_cache` 无日期列只能全量）。
切库只需注释掉 `backend/.env:51` 的 `DATABASE_URL` 并重启。

**★★ 三个实测坑（脚本注释里都写了，改这个脚本前必读）**：

1. **每张表导完必须 `conn.commit()`** ——
   Supabase 走 PgBouncer（6543 事务池化），**只读事务长时间 open 会被服务端直接断连**。
   实测导到第 32 张表报 `SSL connection has been closed unexpectedly`，
   之后 **82 张表全部 `connection already closed`** —— 一次断连毁掉整轮。
2. **大 JSON 表会永久卡死，不是慢** ——
   `indicator_cache` 的 `fetchmany(2000)` CPU 0%、既不返回也不报错，
   只能 kill 进程（卡了 3 分钟以上）。根因：一次往返要传几十上百 MB。
   ⇒ 大行表单独小批量（`_SMALL_BATCH`，200）+ 连接 `options="-c statement_timeout=180000"`
   让**服务端**主动报错，至少能记一笔继续下一张。
3. **必须能续传** —— 中断后从头再来等于白烧 egress。
   加 `--resume`：不备份旧文件、跳过目标库已有数据的表。

**其他参数**：`--dry-run`（只统计行数）、`--tables a,b`（只导指定表）、`--days N`。

**⚠️ 日期过滤要按列类型分支**：`date` 是 DATE、`flash_news.time` 是 TEXT，
统一 `::text` 会废掉索引，直接用 TEXT 比 DATE 会隐式转换 ——
`_where_clause()` 里按 `data_type` 分别处理（TEXT 用 `to_char(...,'YYYY-MM-DD')`）。

**⚠️ 本地库是快照**，不自动更新；要看最新数据重跑脚本。
写操作（教练落库/模拟盘）会写进副本，不影响线上。

## 本地响应缓存（3996dfb2）——用户："第二次请求直接用"

**用户问**："可以将请求的数据缓存在本地的方式吗？第二次请求就直接使用就可以了呀？"

**★★ 先说清两件事的分工**（用户可能以为和导库重复）：
- **导库**（`export_local_sqlite.py`）= 省**查库的 egress**
- **响应缓存** = 省**重复计算**（评分精算 / 雷达 / 复盘聚合，重的要几秒）
两者不重叠，各管一段。

**实现**：`frontend/src/api/index.js` 加 localStorage 缓存层，
`frontend/.env.development` 开 `VITE_LOCAL_CACHE=1`。

**为什么放前端而不是后端中间件**：
① 不动生产代码（后端中间件要读 body、还得重拼 StreamingResponse）；
② 本地开发只有一个浏览器，localStorage 够用；
③ `.env.server` / `.env.production` 不含该变量 ⇒ 线上零影响。

**边界（注释里写全了）**：
- 只缓存 **GET**；POST 一律透传（落库/刷新按钮本来就该走网络）
- 单条 >150KB 不缓存（榜单/宽表，localStorage 5MB 装不下几条）
- 总量 >3MB 按时间 LRU 清理
- 数据**停在缓存那一刻** ⇒ `clearApiCache()`（已挂 `window`）
  或单请求 `params: { nocache: 1 }`

**★ 实现细节（容易踩）**：axios 的 request 拦截器**没有"直接返回响应"的官方口子**
⇒ 用 `Promise.reject({ __cacheHit: true, data, config })` 短路，
再由 response 拦截器 error 分支还原成正常响应。
写缓存时**同 key 不覆盖**（保住最早的时间戳，否则每次绕过缓存的请求都会刷新 t，
LRU 永远淘汰不到它）。

**⚠️ 改 `VITE_LOCAL_CACHE` 后必须重启 `npm run dev`**（Vite 环境变量是启动时注入）。
