**写进铁律的 7 条（按"违反代价"排序）**：
1. **先确认 ref 谁新谁旧** —— 9-12 用户给的"新项目直连串"其实是**旧项目**
   （`opzpugbgabwolcvmfkky` 与 `backend/.env` 一模一样），照做等于往自己身上导。
2. 运行时用 Pooler(6543)，dump/restore 用 Session(5432) 或直连；
   6543 不支持 pg_dump 的目录查询。
3. `db.<ref>.supabase.co` 可能是 **IPv6-only** ⇒ 服务器无 IPv6 时优先 `pooler:5432`。
4. pg_dump 大版本必须 ≥ 源库（Supabase 现 PG17.6，用 16 会直接 abort）。
5. **Supabase CLI 只搬结构不搬数据**（`link`/`db push` 都不搬）。
6. 目标库先建 `extensions` schema（dump 里有 `CREATE EXTENSION ... WITH SCHEMA extensions`）。
7. 验收用 `COUNT(*)` + `MAX(date)`，**不要用 `pg_stat_statements` 累计返回行数当表大小**
   （`stock_finance_zz` 21×1991=41811 是累计值，表只有 1991 行）。

**★ 给用户的三个前置判断（比步骤更重要）**：
1. **迁移目的**：若为了**延迟**（11-04 实测 298ms/次），换 Supabase 账号**无效** ——
   还是同一家云、同一区域。延迟要解决只能换同地域自建库/RDS。
2. **容量**：11-04 实测 **397.8MB / 免费档 500MB = 80%**，
   最大三张 `backtest_prices 124.9MB` / `mainflow_history 78.6MB` / `kline_cache 41.7MB`。
   平移到新账号仍是 80%，几个月后要再迁一次 ⇒ 迁之前先决定清理还是开付费档。
3. **区域**：新项目选与服务器同区（国内→新加坡），跨洋 RTT 会把"一页查 5 次"
   放大成秒级。
