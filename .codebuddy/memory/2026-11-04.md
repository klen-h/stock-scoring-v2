## 001｜服务器 `git pull` 超时 → 用 `git archive` 打包传文件（绕开 git 网络）

**现象**：阿里云北京的服务器 `git pull` 超时（clone 当时能过，pull 卡住）——GitHub 链路不稳定。

**兜底方案（已在本地验证可行）**：
```powershell
# 本地仓库根目录
git archive --format=tar.gz -o ..\src-latest.tar.gz HEAD
```
- 只打包 **tracked 文件** ⇒ **天然排除** `backend/.env`、`backend/data/`、`node_modules`
  ⇒ 解压不会覆盖凭证与运行数据，这是它比 `rsync 整目录` 安全的地方
- 当前包：`D:\stock-scoring\src-latest.tar.gz`，**4.5 MB**，对应 HEAD `759277fa`

**服务器侧**：
```bash
cd /www/wwwroot/stock-scoring-v2
sudo tar -xzf src-latest.tar.gz
sudo chown -R admin:admin .          # sudo 解压会变 root 属主，必须改回
sudo systemctl restart stock-scoring
```

**其它可尝试的**（优先级低于打包）：
1. `git config --global http.postBuffer 524288000` + `http.lowSpeedLimit 1000` + `http.lowSpeedTime 60`
2. 临时换镜像 remote（`https://ghfast.top/` 之类），**只用于 pull，不要用于 push**

⚠️ 以后每次服务器更新若 git 仍不通，就重复「本地 git archive → 上传 → 解压」这条路。

### ⚠️ 我前几轮给错了一个命令
服务器部署步骤里我写的是 `cd frontend && npm run build` —— **错的**。
- `build`        → Pages 口径：`base=/stock-scoring-v2/`，API 指 Render ⇒ 服务器上 404 / CORS 全崩
- `build:server` → 读 `.env.server`（`VITE_BASE=/`、`VITE_API_BASE_URL=/api`）⇐ **服务器唯一正确做法**

**教训：给部署命令前先看 `vite.config.js` / `package.json` 的 scripts，不要凭记忆。**

### `deploy.sh`（根目录，`create mode 100755`）
- 自动探测 venv（`backend/venv` → `venv` → `backend/.venv` → `python3`）
- 依赖按 `requirements.txt` 的 md5 增量安装（`.deps.stamp`）
- 前端 `build:server`（并**先看可用内存**，<400MB 时警告可能 OOM）
- **重启前 `compileall`**：语法错就中止，让旧进程继续顶着（避免"重启后起不来"）
- 重启后 `curl /api/health` 最多等 40s，失败自动打印 `journalctl -n 50`
- 参数：`--skip-pull`（tar 部署）/ `--skip-frontend`（省内存）/ `--no-restart`

### 换行符陷阱
Windows 上 `core.autocrlf=true`，bash 脚本若带 CRLF 到服务器会报 `$'\r': command not found`
（**报错只说"第 N 行有问题"，完全看不出是换行符**）。
⇒ 新增 `.gitattributes`：`*.sh text eol=lf`（只约束 .sh，不动其他文件，避免大面积 diff）。
⚠️ 另记一个测量陷阱：`git show FILE | python` 经 **PowerShell 管道**会被插入 `\r\n`，
   得出"仓库里是 CRLF"的假结论。要测字节必须用 `subprocess.run(..., capture_output=True).stdout`。

## 008｜npm EACCES：宝塔全局缓存目录不可写（`35f9514a`）

**用户报错**：
```
npm error code EACCES  syscall mkdir  errno -13
npm error path /www/server/nodejs/cache/_cacache
```
环境：宝塔装的 **node 22.1.0**。

**根因**：宝塔把 npm 的**全局缓存**放在 `/www/server/nodejs/cache`，属主 root；
用普通用户（宝塔 www 一般是 1000/1001）跑 npm ⇒ 连 cache 都建不了。

**处理原则：不要去 chown 那个全局目录。**
npm 建议的 `sudo chown -R 1001:1001 /www/server/nodejs/cache` 是**把共享目录交给某个 uid** ——
同机若还有别的站点/用户用这套 node，会互相踩。正确做法是**只给本项目指定缓存**：

```bash
export npm_config_cache="$PWD/.npm-cache"     # 或 npm ci --cache /path/.npm-cache
```
`deploy.sh` 已内置（`npm_config_cache` 仅脚本内生效，不写 `.npmrc`、不动宝塔目录）；
`.gitignore` 加 `.npm-cache/`。

**同源但更隐蔽的第二种 EACCES**：之前用 `sudo npm` 跑过 ⇒ `node_modules` 变 root 拥有，
普通用户永远写不进去，**报错一模一样**，极易误判成 cache 问题。
⇒ `deploy.sh` 现在先预检 `frontend/` 与 `node_modules` 的**可写性**，
   并直接打印可复制的修复命令 `sudo chown -R $(id -u):$(id -g) ...`。

**另一个宝塔坑（顺手补）**：`/www/server/nodejs/v22.1.0/bin` **未必在 PATH 里** ⇒
`npm: command not found`。脚本现在探测 `/www/server/nodejs/*/bin`（`sort -V` 取最高版本）自动加 PATH。

### 纪律
**不要用 `sudo npm`**。身份要统一：项目目录属主是谁就用谁跑 deploy.sh，
只有 `systemctl restart` 走 sudo（脚本里已处理）。

## 009｜宝塔 `.user.ini` 挡住 vite 构建（`3f0963a5`）

**用户实测报错**（服务器 `./deploy.sh`）：
```
✓ 716 modules transformed.
x Build failed in 23.59s
ENOTDIR: not a directory, scandir '/www/wwwroot/stock-scoring-v2/frontend/dist/.user.ini'
    at readdirSync → _rmdirSync → rimrafSync → rmSync → emptyDir → prepareOutDir
```
**根因**：宝塔"防跨站攻击"在**网站根目录**（本项目 nginx root = `frontend/dist`）放了 `.user.ini`
（内容形如 `open_basedir=...`，通常还带 `chattr +i`）；而 **vite 构建前必先 `emptyDir(outDir)`**
⇒ 删到它必然失败。

**解法（三选一，选了第二种）**：
1. 删/改 `.user.ini` —— 要 root + `chattr -i`，宝塔还会重建，且动了安全设置 ❌
2. **构建到 `dist-build`，成功后再同步回 `dist` 并保留 `.user.ini`** ✅（已实装于 `deploy.sh`）
3. 改 nginx root 指向新目录 —— 牵动全局，❌

同步命令（`find` 排除而非先删后建）：
```bash
find dist -mindepth 1 -maxdepth 1 ! -name '.user.ini' -exec rm -rf {} +
cp -a dist-build/. dist/
```
**附带好处**：构建失败时 `dist` 原样保留 ⇒ 不会出现"构建挂了、站点白屏"。

### ⚠️ 两个白试的方向（实测无效，别再走）
- `npm run build:server -- --outDir dist-build` → **无效**，产物照样进 `dist`
- `npm run build:server -- --outDir dist-build`（空格形式）→ 更糟：`dist-build` 被当成 **root**，
  报 `Could not resolve entry module "dist-build/index.html"`
- 只有**直调** `node node_modules/vite/bin/vite.js build --mode server --outDir dist-build` 才有效
⇒ 最终改用**配置**：`vite.config.js` 里 `build.outDir: process.env.VITE_OUT_DIR || 'dist'`，
  `deploy.sh` 用 `VITE_OUT_DIR=dist-build npm run build:server`。
  ⚠️ 必须读 `process.env` —— `loadEnv()` **只读 `.env.*` 文件，看不到 shell 变量**
  （与 `base` 那个坑同源）。

**已验证**：本地端到端复刻（dist 放 .user.ini → 构建 → 同步）：
`.user.ini` 保留、旧文件清掉、`index.html` 中 `src="/assets/..."`（base=/ 正确）。

### 修法
pull 前后比对 **deploy.sh 自身 md5**，变了就 `exec bash "$SELF" --skip-pull "$@"`

新版执行且参数正确传递（`--skip-pull --skip-frontend`）。

### ★ 由此得到一条通用纪律

判断信号很简单：**日志里的行为与 HEAD 的代码不一致** ⇒ 先怀疑"执行的是旧文件"。

## 017｜李大霄补拉失败：raw.githubusercontent 被 RST（`67e332e4`）

**用户报错**：
```
更新失败：上游拉取失败: ('Connection aborted.', ConnectionResetError(104, 'Connection reset by peer'))
```

**根因**：`lidaxiao_views._DEFAULT_UPSTREAM` 直连
`raw.githubusercontent.com/klen-h/xiaopage/main/public/data/views-lite.json`，
国内服务器**被 RST / 连接超时**。

### ★ 这里有个容易误判的盲点
同一台机器的 **`git pull` 是好的**（日志 `From https://ghfast.top/https://github.com/...`）
⇒ 看日志会以为"网络没问题"。真相是：
**git 配了 `ghfast.top` 镜像，而 `requests` 直连不会走 git 的配置** ——
两条链路完全独立，"git 能拉"证明不了"requests 能连"。

### 修法：多镜像回退（`_mirror_urls()`）
同一文件（150.5KB）实测：
| 源 | 结果 |
|---|---|
| `gh-proxy.com` | ✅ 0.30s |
| `cdn.jsdelivr.net` | ✅ 0.58s |
| `ghfast.top` | ✅ 1.22s |
| `raw.githubusercontent.com` 直连 | ❌ ConnectTimeout |

顺序：`LIDX_MIRROR_PREFIX`(可选自建) → gh-proxy → ghfast → jsDelivr → raw 兜底。
另加 **90s 总预算** —— 否则镜像全挂时 8 个 URL 各自等超时，按钮会转圈数分钟。
`LIDX_UPSTREAM_URL`（完整 URL）仍最高优先；走它时不再试镜像。

⚠️ `_ETAG` 按 URL 分别缓存：切镜像后第一次会全量拉一次（150KB，可接受）。

### 顺带排查
仓库里**只有这一处**直连 raw（`scripts/backfill_lidaxiao.py` 读本地文件，不联网）；
`pack_source.py` 走的是 `klen-h.github.io`（Pages CDN），未受影响。

### 可复用的判断
**凡是"境外资源 + 国内服务器"的请求，都要假设直连不通**：
显式给镜像链，并且**别用 git/浏览器能访问来推断 `requests` 能访问**。

信息更少的环境反而给出更极端的分数 —— 与"缺数据应更保守"的直觉相反。

远程由 GitHub 后台逐步回收。

⇒ 白天打开看到的必然是前一天的，中间有 13 小时空白。`system.py` 的 docstring 里
其实早写明了这是"节奏问题，不是故障"。

**用户选 B+C**（原话："B + C，如果请求到今天了，就不要再定时刷新了"）：

- **C（窗口）**：`compute(days=3)` → `compute(days=7)`。三处同步：
  `jin10_tidy.py` 默认值、`scripts/daily_batch.py` 显式传参、`system.py` docstring。
  12 请求 → 28 请求。**为什么 3 天不够**：日批一天只跑一次，连放三天假窗口就滑过去了，
  **永久补不回来**（除非命令行 `compute(day=...)`）。

- **B（惰性刷新）**：`Workbench.vue` 新增 `maybeAutoRefreshJin10()`，在
  `loadRiskWatch()` 末尾调用。三道闸，**缺一不可**：
  1. `selectedDate === todayStr`（回放历史日绝不外呼，否则每切一次日期打 28 个请求）
  2. `jin10.date !== todayStr` —— 用**数据实际日期**判断，不是请求日期；
     后端 fallback 时 `date` 是昨天，用它才不会把"请求了今天"当成"拿到了今天"
  3. 10 分钟节流，key = `localStorage['jin10:auto:<todayStr>']`
     ⚠️ **必须用 localStorage 而非模块变量**：模块变量在刷新页面后清零，
     而"反复开页面"最常表现为刷新 ⇒ 每刷一次就打 28 个请求。

- 自动刷新走 `summarize=false`（**不烧 LLM**）。失败时：非 token 错误静默
  （用户没点按钮，弹出来只会困惑），**token 失效（401）必须提示**——
  这是全链路唯一需要人工介入的故障。

**副作用（已告知用户）**：当天一旦抓到数据就不再自动刷 ⇒ 金十后续追加的内容
（如「A股回顾」盘后才发）要手动点「抓最新」。用户明确接受这个取舍。

**顺手改**：折叠态摘要加日期前缀（非今天才标 `11-03`），不展开就能看出数据新旧。

## 教练卡「15:40 才触发」：两条落库路径分离（dfbd18fe）

**用户报**：15:40 看到「高位+主力出货（不等7%直接砍）粤高速Ａ」，问
"已经 15:40 了，收盘了才触发吗？早盘复盘的"。

**根因（不是数据问题，是路径问题）**：
`distribution_cut` 属 `HEAVY_RULES`（要读 K 线/筹码），30s 盘中轮询**不跑**它
（`evaluate_all("light")` 会跳过）。它只在两个地方求值：

1. `coach/monitor.py::health_card()` —— 10:30 / 14:45 关键时点体检卡，`tier="all"`
   ⇒ **只 `_push` 企微，从不 `record_advices`**（不落库）
2. `coach/monitor.py::daily_close_job()` —— 15:40 起盘后一次性，`tier="all"`
   ⇒ **`push=False` 只落库**（注释写"避免夜间轰炸"）

⇒ 盘中命中的 heavy 结论**只进企微、不进教练卡列表**；盘后落库的才进列表。
用户看到的 15:40 是 `created_at`（**落库时间**），不是判定时间。

**修复**：`health_card()` 算完就 `audit.record_advices(..., push=False)`。
- `push=False` 是安全的：`distribution_cut` / `crowded_trim` 在 `rules.yaml` 里
  本来就是 `push: false`（只进列表不推企微）⇒ **不增加任何企微消息量**
- `dedupe_key = 日|规则|标的` ⇒ 15:40 重跑不重复建行，保留**首次触发时间**
- 落库失败 try/except 吞掉，绝不挡住推送（体检卡价值在及时提醒）

**遗留**：若早盘 10:30 时数据本身就不满足（昨天收盘口径不满足），改完也不会出现
—— 那属日频数据的本质约束，不是 bug。验证看日志有无 `[coach] 体检卡落库 N 条`。

## 市场底清单：第⑤条改实时 + 修掉 12.7 秒的扫库（bd88e115）

**用户**："观察器我想实时，尤其是市场底确认清单"（他贴的是 1/6）。

**根因**：`policy_bottom_watch._macro_snapshot()` 只读 `macro_daily`（**日频**，日批写一次）
⇒ 第⑤条的 10Y / 布伦特盘中是**旧值**，而这两项早就有实时源（东财 `171.US10Y`、布伦特）。

**改动**：
1. 新增 `_live_macro()` —— 读 `app.macro.get_macro_panel()`（`TTL_QUOTES=60` 共享缓存，
   **零边际请求**）。失败返回 None，回退 `macro_daily`（宁可显示旧值也不整条变"不可用"）。
2. 抽出 `_item_us10y_oil()`，`evaluate()` 与 `load()` 共用；
   `load()` 每次请求**只重算第⑤条**（其余五条是日频量，重算要打外部请求，不值）。
   勾选状态真变了才重算 `n_checked` / `position_hint`，否则顶部 "N/6" 会与条目自相矛盾。
3. 实时价参与峰值：`peak = max(_brent_peak(), br)`。

**性能坑（本轮最重要的发现）**：
`macro_daily` 只有 **44 行**，但单行 `data_json` 有**几百 KB**（整份 macro 快照）
⇒ `SELECT date, data_json` 全表 = 十几 MB ⇒ 国内拉 Supabase **12.7 秒**
（`_macro_snapshot` 更慢，**26.9 秒**）。以前只在日批跑一次看不出来，
改成"每次请求重算第⑤条"后前端必然超时。
- 修法①：SQL 用 PG 的 `data_json::jsonb->'panel'->'brent'->>'price'` 在**服务端**取值，
  传输量 MB → KB，冷缓存 **12.7s → 3.6s**（SQLite 测试环境语法不支持，捕获后回退旧语法）。
- 修法②：`load()` 把落库的 `peak` 通过 `peak_override` 传进来，**完全不扫库**
  （峰值是历史高点，一天只变一次）；老数据没有 `peak` 字段时回退一次。
- 修法③：`_peak_cache` / `_snapshot_cache` 进程内按「截止日」缓存。

**数据核对（回答"系统反映不对"）**：
`macro_daily` 里布伦特 44 条（8/24~11/4），**最高 112.78（10/23）**，不是用户说的 132。
用户引用的 110.67 是 **10/29** 的值；当前（11/4 实时）**101.2**，回落 **10.3% < 15%**。
⇒ 第⑤条 `checked=False` 是**正确**的：`10Y 4.94% < 5%` 已满足，但油价侧两条都不满足。
（用户按"高点 132"算会得到回落 23% 的相反结论 —— 口径差异，不是 bug。）
