## 001｜服务器 `git pull` 超时 → 用 `git archive` 打包传文件（绕开 git 网络）

**现象**：阿里云北京的服务器 `git pull` 超时（clone 当时能过，pull 卡住）——GitHub 链路不稳定。

**兜底方案（已在本地验证可行）**：
```powershell
# 本地仓库根目录
git archive --format=tar.gz -o ..\src-latest.tar.gz HEAD
```
- 只打包 **tracked 文件** ⇒ **天然排除** `backend/.env`、`backend/data/`、`node_modules`
  ⇒ 解压不会覆盖凭证与运行数据，这是它比 `rsync 整目录` 安全的地方
- 当前包：`D:\stock-scoring\src-latest.tar.gz`，**4.5 MB**，对应 HEAD `759277fa`

**服务器侧**：
```bash
cd /www/wwwroot/stock-scoring-v2
sudo tar -xzf src-latest.tar.gz
sudo chown -R admin:admin .          # sudo 解压会变 root 属主，必须改回
sudo systemctl restart stock-scoring
```

**其它可尝试的**（优先级低于打包）：
1. `git config --global http.postBuffer 524288000` + `http.lowSpeedLimit 1000` + `http.lowSpeedTime 60`
2. 临时换镜像 remote（`https://ghfast.top/` 之类），**只用于 pull，不要用于 push**

⚠️ 以后每次服务器更新若 git 仍不通，就重复「本地 git archive → 上传 → 解压」这条路。

### ⚠️ 我前几轮给错了一个命令
服务器部署步骤里我写的是 `cd frontend && npm run build` —— **错的**。
- `build`        → Pages 口径：`base=/stock-scoring-v2/`，API 指 Render ⇒ 服务器上 404 / CORS 全崩
- `build:server` → 读 `.env.server`（`VITE_BASE=/`、`VITE_API_BASE_URL=/api`）⇐ **服务器唯一正确做法**
这个坑项目里 2026-11-03 已经踩过两次并写在 `frontend/vite.config.js` 头部，我却没照着做。
**教训：给部署命令前先看 `vite.config.js` / `package.json` 的 scripts，不要凭记忆。**

### `deploy.sh`（根目录，`create mode 100755`）
- 自动探测 venv（`backend/venv` → `venv` → `backend/.venv` → `python3`）
- 依赖按 `requirements.txt` 的 md5 增量安装（`.deps.stamp`）
- 前端 `build:server`（并**先看可用内存**，<400MB 时警告可能 OOM）
- **重启前 `compileall`**：语法错就中止，让旧进程继续顶着（避免"重启后起不来"）
- 重启后 `curl /api/health` 最多等 40s，失败自动打印 `journalctl -n 50`
- 参数：`--skip-pull`（tar 部署）/ `--skip-frontend`（省内存）/ `--no-restart`

### 换行符陷阱
Windows 上 `core.autocrlf=true`，bash 脚本若带 CRLF 到服务器会报 `$'\r': command not found`
（**报错只说"第 N 行有问题"，完全看不出是换行符**）。
⇒ 新增 `.gitattributes`：`*.sh text eol=lf`（只约束 .sh，不动其他文件，避免大面积 diff）。
⚠️ 另记一个测量陷阱：`git show FILE | python` 经 **PowerShell 管道**会被插入 `\r\n`，
   得出"仓库里是 CRLF"的假结论。要测字节必须用 `subprocess.run(..., capture_output=True).stdout`。

## 008｜npm EACCES：宝塔全局缓存目录不可写（`35f9514a`）

**用户报错**：
```
npm error code EACCES  syscall mkdir  errno -13
npm error path /www/server/nodejs/cache/_cacache
```
环境：宝塔装的 **node 22.1.0**。

**根因**：宝塔把 npm 的**全局缓存**放在 `/www/server/nodejs/cache`，属主 root；
用普通用户（宝塔 www 一般是 1000/1001）跑 npm ⇒ 连 cache 都建不了。

**处理原则：不要去 chown 那个全局目录。**
npm 建议的 `sudo chown -R 1001:1001 /www/server/nodejs/cache` 是**把共享目录交给某个 uid** ——
同机若还有别的站点/用户用这套 node，会互相踩。正确做法是**只给本项目指定缓存**：

```bash
export npm_config_cache="$PWD/.npm-cache"     # 或 npm ci --cache /path/.npm-cache
```
`deploy.sh` 已内置（`npm_config_cache` 仅脚本内生效，不写 `.npmrc`、不动宝塔目录）；
`.gitignore` 加 `.npm-cache/`。

**同源但更隐蔽的第二种 EACCES**：之前用 `sudo npm` 跑过 ⇒ `node_modules` 变 root 拥有，
普通用户永远写不进去，**报错一模一样**，极易误判成 cache 问题。
⇒ `deploy.sh` 现在先预检 `frontend/` 与 `node_modules` 的**可写性**，
   并直接打印可复制的修复命令 `sudo chown -R $(id -u):$(id -g) ...`。

**另一个宝塔坑（顺手补）**：`/www/server/nodejs/v22.1.0/bin` **未必在 PATH 里** ⇒
`npm: command not found`。脚本现在探测 `/www/server/nodejs/*/bin`（`sort -V` 取最高版本）自动加 PATH。

### 纪律
**不要用 `sudo npm`**。身份要统一：项目目录属主是谁就用谁跑 deploy.sh，
只有 `systemctl restart` 走 sudo（脚本里已处理）。

## 009｜宝塔 `.user.ini` 挡住 vite 构建（`3f0963a5`）

**用户实测报错**（服务器 `./deploy.sh`）：
```
✓ 716 modules transformed.
x Build failed in 23.59s
ENOTDIR: not a directory, scandir '/www/wwwroot/stock-scoring-v2/frontend/dist/.user.ini'
    at readdirSync → _rmdirSync → rimrafSync → rmSync → emptyDir → prepareOutDir
```
**根因**：宝塔"防跨站攻击"在**网站根目录**（本项目 nginx root = `frontend/dist`）放了 `.user.ini`
（内容形如 `open_basedir=...`，通常还带 `chattr +i`）；而 **vite 构建前必先 `emptyDir(outDir)`**
⇒ 删到它必然失败。

**解法（三选一，选了第二种）**：
1. 删/改 `.user.ini` —— 要 root + `chattr -i`，宝塔还会重建，且动了安全设置 ❌
2. **构建到 `dist-build`，成功后再同步回 `dist` 并保留 `.user.ini`** ✅（已实装于 `deploy.sh`）
3. 改 nginx root 指向新目录 —— 牵动全局，❌

同步命令（`find` 排除而非先删后建）：
```bash
find dist -mindepth 1 -maxdepth 1 ! -name '.user.ini' -exec rm -rf {} +
cp -a dist-build/. dist/
```
**附带好处**：构建失败时 `dist` 原样保留 ⇒ 不会出现"构建挂了、站点白屏"。

### ⚠️ 两个白试的方向（实测无效，别再走）
- `npm run build:server -- --outDir dist-build` → **无效**，产物照样进 `dist`
- `npm run build:server -- --outDir dist-build`（空格形式）→ 更糟：`dist-build` 被当成 **root**，
  报 `Could not resolve entry module "dist-build/index.html"`
- 只有**直调** `node node_modules/vite/bin/vite.js build --mode server --outDir dist-build` 才有效
⇒ 最终改用**配置**：`vite.config.js` 里 `build.outDir: process.env.VITE_OUT_DIR || 'dist'`，
  `deploy.sh` 用 `VITE_OUT_DIR=dist-build npm run build:server`。
  ⚠️ 必须读 `process.env` —— `loadEnv()` **只读 `.env.*` 文件，看不到 shell 变量**
  （与 `base` 那个坑同源）。

**已验证**：本地端到端复刻（dist 放 .user.ini → 构建 → 同步）：
`.user.ini` 保留、旧文件清掉、`index.html` 中 `src="/assets/..."`（base=/ 正确）。

## 011｜真凶：**脚本不能就地更新自己**（`bc5dc97f`）——并纠正 010 的错误结论

### 修法
pull 前后比对 **deploy.sh 自身 md5**，变了就 `exec bash "$SELF" --skip-pull "$@"`
（`exec` 重新打开文件 → 读到新内容）。已验证：旧版打印 → 检测到 md5 变化 → exec →
新版执行且参数正确传递（`--skip-pull --skip-frontend`）。

### ★ 由此得到一条通用纪律
**任何"自我更新"的脚本都必须 exec 重入**，否则"改了不生效"会被误判成代码/环境问题，
而且**排查方向会完全跑偏**（我为此多花了两轮，先怪 npm 传参、又怪环境变量）。
判断信号很简单：**日志里的行为与 HEAD 的代码不一致** ⇒ 先怀疑"执行的是旧文件"。

## 012｜两版宏观分差 25 分：a50 标的选错 + 新浪封 IDC（`ced78eee`）

**现象**：Render 版 `-12.8（中性）` vs 阿里云版 `-38.1（偏空）`，同一时刻同一份代码。
逐项对比后定位到**两个独立原因**：

### ① a50 用错标的（分数差的主要来源）
```
100.XIN9   富时中国A50      12857.16  -0.91%   ← 现货指数（我之前选的 "东财口径为现货指数"）
104.CN00Y  A50期指当月连续   12812.00  +0.27%   ← 期货（新浪 hf_CHA50CFD 是期货）
```
规则 `a50_overnight` 问的是 **A50 隔夜走势**，现货指数夜间不动 ⇒ 用现货判隔夜，
**触发方向直接反了**：中国组 `-2.9` → `-24.9`（差 22 分，占总差异绝大部分）。
⇒ 改 `_EM_MAP["a50"] = "104.CN00Y"`，与新浪同口径。

### ② 阿里云 IDC 的 IP 被新浪整段封（数据覆盖率差异）
本地（家宽）跑同一份代码：**新浪只缺 3 项**（gold/gold_spot/kospi），
而阿里云缺一大批。这解释了为什么"同样的代码、不同的分数"。
（用户日志里 `usdcny/vix/rebar/iron` 全 = `—`，Render 上都有值。）

### 顺带补上黑色系（东财有主连合约）
```
113.rbm  螺纹钢主连  2996.0  -0.2%   ← 与新浪 nf_RB0 逐位一致
114.im   铁矿石主连  676.5   +0.74%  ← 与新浪 nf_I0 逐位一致
```
⇒ `_EM_MAP` 补 `rebar`/`iron`，`black_demand` 在阿里云上不再恒缺。
⚠️ 代码是**小写** `rbm`/`im`；大写 `RB0`/`I0` 试过无效。

### 补不了的（如实说明，别硬凑）
- **VIX**：东财无 VIX 指数（只有 `107.VIXY/VXX/UVXY` 等 **ETF**，数值完全不同，绝不能用）；
  腾讯 `usVIX` 是**僵尸数据**（`[3]=21.67` 涨跌 0.00，时间戳停在 `2026-09-14`）；
  Yahoo `^VIX` 返回 **403**。⇒ 阿里云上 `vix_*` 三条规则只能不参与打分。
- **在岸人民币 `usdcny`**：东财无（`133.USDCNY` 不存在），新浪 `USDCNY` 国内被封
  ⇒ `cny_cnh_basis`（离岸在岸价差）在阿里云上无数据。
- `sox`(费半) / `gld` 同样缺，但不进规则，仅展示。

### 结论
两版**不是算法不同，是可用样本不同**。系统对缺数据是"不计分、也不计入分母"，
所以缺项不会让分数"算错"，只会让**样本更少、方向更钝**。
修完 a50 后，阿里云预期从 `-38.1` 回到约 `-15`，与 Render `-12.8` 的残差
来自 VIX（±1）与金银比（±1，两边各缺一头）。
