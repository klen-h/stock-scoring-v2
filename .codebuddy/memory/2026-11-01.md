## 004 ★入场确认回放：结论推翻「改状态机」的判断（`14723d94`）

### 回放方法（不改代码，纯 SQL）
数据源：`tracking_state.data_json` 的 `history`（按 id 去重）+ `priceHistory`（48 天，
2026-08-20 ~ 10-30，覆盖全部样本）。对每笔交易算：
- `sup_gap_pct` = (support − 信号创建日前收盘) / 前收盘
- `box_pct` = (resistance − support) / 前收盘
- `fwd3_pct` = 信号创建日之后第 3 个交易日的涨跌

### 结论一：按「支撑距市价」「支撑阻力间距」切分，都区分不出胜负
盈利 3 笔的 gap：-1.56% / -1.50% / (缺)
亏损的 gap：-0.35 ~ -5.74 全都有
盈利 2 笔的 box：4.10% / 4.69%；亏损的 box 也有 5.07% / 6.45% / 8.75%
⇒ **「跌穿幅度」不是区分胜负的关键**，我上一轮说的「入场确认是分水岭」**是错的**。

### ★结论二：LLM 的方向判断系统性错误
14 笔有 `fwd3` 数据的样本：
- **未来 3 天上涨：2 笔**（人工智能 8-27 +2.91%、10-22 +0.21%）
- **未来 3 天下跌：12 笔**
⇒ **85.7% 的做多信号，发出后 3 天内是跌的**
且 **18 笔里 direction 全部是 `long`，没有一笔 `short`**

最极端的：
| ETF | 日期 | fwd3 | 结果 |
|---|---|---|---|
| 黄金ETF | 8-31 | **-6.05%** | -2.55% |
| 半导体ETF | 10-12 | **-6.13%** | -3.23% |
| 半导体ETF | 8-21 | -2.79% | -2.92% |

唯一方向真对的人工智能 8-27（+2.91%）赚了 +4.76%。
地产 8-21（fwd3 -2.54% 但赚 +4.77%）属于「方向错但中途反转」，是运气。

### 根因：prompt 的三个结构性问题
1. **强制给信号**：原文「从给出的 ETF 中**选 1-3 个**给出具体建议」
   ⇒ 每天必须交易，即使没有机会 ⇒ 与 `_SIGNAL_SCHEMA_HINT` 末尾
   「没有把握时输出空数组」**直接冲突**，LLM 倾向服从「1-3 个」。
2. **few-shot 只有做多**：示例 `"direction": "long"` 是唯一例子 ⇒ 锚定做多。
3. **盘前没有市况闸门**：P1-5 的 regime 闸门只对 `lunchbreak` 生效，
   defensive 市的盘前照样给做多。

### 已改（`14723d94`）
`flash/llm.py`：
- 盘前第 5 条 / 午盘第 6 条：`选 1-3 个` → **`只在确有把握时给出（0-2 个）`**，
  并明写「没有符合条件的就明说无信号并输出空数组——宁可不做，绝不凑数」。
- `_SIGNAL_SCHEMA_HINT` 的 direction 说明加一句：
  「下跌趋势中给 short 是正常决策。不要因为示例是 long，就一律输出做多。」

### 未做（下一步候选，按价值排序）
1. **盘前也加 regime 闸门**（复用 `_midday_regime_gate` 的判定，改成全时段）
   —— 但要注意：盘前给的是当日盘前判断，defensive 下"只做空"比"全拒"更合理。
2. **观察窗口**：改 prompt 后至少观察 5-10 个交易日，看 `rejected/空数组` 比例是否上升、
   胜率是否改善，再决定要不要动状态机。
3. 「入场确认」（跌破支撑不买）**暂缓**——回放证明它解决不了主要问题。

### 教训
**先验证方向，再优化执行。** 我上一轮基于「亏损单 entry<support」就断定入场确认是分水岭，
但回放显示 85.7% 的信号方向本身就错——**在错误的方向上优化执行，收益上限为零。**

## 011 休盘日仍在倒计时/轮询（`2da118dd`）

### 现象（用户 2026-11-01 周日）
「评分 Top10 · 后端批次 · 36s 后刷新」——休盘时间倒计时还在走。

### 根因
`Workbench.vue` 的 `computePhase()` **只按时刻判断，完全不看星期几**：
```js
const m = d.getHours() * 60 + d.getMinutes()
if (m >= 570 && m < 690) return 'intraday'   // 9:30-11:30
```
⇒ 周日 10:00 命中 `intraday` ⇒ `isLivePhase()` 为真 ⇒
① 卡片显示倒计时；② 60s/120s 两个轮询组整段空转（纯 egress 浪费）。

### 修复
1. **`computePhase()` 补周末判断**：`d.getDay()` 为 0/6 ⇒ 直接返回 `'review'`
2. **`isLivePhase()` 补节假日兜底**：`emotion.value?.trading_day === false` ⇒ false
   - `emotion.trading_day` 由 `/market/emotion` 下发（后端 `flash.rules.is_trading_day`，
     含外部交易日历）⇒ 法定节假日（落在工作日）也能停
   - 只在**明确 false** 时拦截 ⇒ 字段缺失/请求失败不误判（fail-open）

### 影响面
- `computePhase()` 还用于 `selectedPhase` 初始化 ⇒ 周末进入 `review` 阶段（合理）
- `isLivePhase()` 是轮询/倒计时/强制刷新共用判据 ⇒ 一处修复同时覆盖三处
- `refreshLeft` 的 1s ticker 本就 `if (!isLivePhase()) refreshLeft = 0`
  ⇒ 修好判据后倒计时自动归零，不用改 ticker

### 已知限制
前端仍无节假日日历（`usePortfolio.isTradingDay` 同样只判周末）。
现在靠 `emotion.trading_day` 兜住，但要求 `/market/emotion` 已返回
（轮询首次返回前是 fail-open）。若要把这条路彻底做干净，
应把 `trading_day` 提到一个轻量接口（如 `/system/status`）随首屏一起下发。

1. `grouped` computed：按 `cluster` 分组；`cards` 已按时间倒序 ⇒ **组内天然时间线**；
   组间按"首次出现"排 = 最新组在前
2. 组头：`cluster 标签 + N 条 + 最新时间 + "展开 M 条"`
3. `groupHead = 2`：每组默认展开最新 2 条
4. `openGroups` ref + `groupItems()` / `toggleGroup()` 控制展开
5. **每组各画一条竖轴**（模板里竖轴移进组内容器）——跨组连成一条会误导
6. 条目内的 `cluster` 标签移入组头（避免重复）；**历史 tab 无 cluster ⇒

### ★★ 关键：两套行情字段不一致，必须归一
`fetchRealtimeQuotes`（浏览器直连腾讯）与后端 `get_stock` **不是同一套字段**：

| 项 | 直连 `api/tencent.js` | 后端 `tencent.get_stock` | 处理 |
|---|---|---|---|
| 昨收 | `yesterday_close` | `prev_close` | 映射 |
| 涨跌额 | **不解析** | `change_amt` | 用 `price - 昨收` 算 |
| **成交量** | **股**（已 ×100） | **手** | **÷100 转回手** |

**成交量这条最危险**：不除回 100，`formatVol` 会显示成 100 倍的数
（如 1.23 亿股 vs 123 万手），而且"看起来像真的"。

### 测试抓到的两个 bug（都是我第一版写错的）
1. **昨收为 0 时算出 `change_amt = 现价`**
   `parseFloat(0)` 是有限数字，单靠 `Number.isFinite` 拦不住停牌/新股首日，
   会显示"涨了 10.5 元"。⇒ 改成 `Number.isFinite(x) && x > 0`。
2. **价格无效时仍做部分更新**

## 029 ✅ `/score/weights` 首次慢的根因与修复（`783ce7bc`）

用户："首次打开有点慢，是 /api/score/weights 这个接口原因吗？"（localhost:3000）

**回答：是，但慢的不是"算权重"，而是三笔远程 DB 往返 + 一次事件循环阻塞。**

### 实测拆解
```
db.fetch_one('SELECT 1')          2814.8 ms   ← 首次连接建立（Supabase TLS）
_ensure_history_table()           2429.9 ms   ← 连接已热仍 2.4s！
SELECT ... LIMIT 1                 649.5 ms   ← 每次 ~640ms（远程往返固有）
restore（连接热）                  1874.1 ms
```
⇒ `restore` = 建表 2.4s + 查询 0.64s（+ 冷连接 2.8s）= **3~7 秒**。

### 更严重的一层：它卡住的是**整个事件循环**
`scheduler.start()`（`async def`）里**同步**调用 `restore_regime_cache_from_db()`
⇒ 3~7 秒内**所有 HTTP 请求排队**，用户看到的就是"首次打开很慢"。
本地 dev `--reload` 每次改代码重启都重付一遍。

### 修复（两处）
1. **`_ensure_history_table` 加进程级一次性标志**（`_HISTORY_TABLE_READY`）
   —— 表只需首次部署建一次，之后 `IF NOT EXISTS` 纯属白付往返。
   实测：第 1 次 4387ms → 第 2/3 次 **0ms**。
   ⚠️ 只有全部成功才置 True（建表失败必须能重试）。
2. **`scheduler.start()` 的恢复改 `await asyncio.to_thread(...)`**
   —— 不再阻塞事件循环；未就绪的那几秒里 `/score/weights` 会自己再恢复
   （幂等，`_REGIME_CACHE` 覆盖写）。

### 剩余（可接受）
`/score/weights` 首次约 **0.6~0.9s**（一次远程查询往返），之后 0ms。
这是 Supabase 远程库的固有延迟，除非本地缓存持久化（未做）。

### 本项目性能问题的统一根因（截至今天的认知）
**每次 Supabase 往返 0.5~1.2 秒** —— 所有"多次点查"的接口都慢，
优化方向永远是"**合并往返/加进程缓存/砍掉不必要的往返**"，而不是优化计算。

## 032 ✅ "是不是 Supabase 限速？"——不是，是物理距离（实测）

用户："本地和生成的接口都有点慢，是 supabase 限速了吗？"

### 实测（连续 12 次 SELECT 1，连接复用）
```
#1  2636ms（首连 TCP+TLS）  #2~#12  566~576ms（极稳，±5ms）
偶发 960ms ×2（网络抖动）
host: aws-0-ap-southeast-1.pooler.supabase.com   端口 6543（pooler）
```

### 判读：**不是限速，是物理距离**
- 实例在 **新加坡（ap-southeast-1）**，本机（大陆）RTT ~250-280ms；
  一次简单查询要 2 个网络来回 ⇒ **~570ms 固定延迟**。
- **限速的表现**是"突发变慢/被拒绝/随请求数恶化"；实际是**每次查询都稳定
  多付固定延迟**，与频率无关 ⇒ 排除限速。
- "生成的接口"（GitHub Actions）runner 在欧美 ⇒ 到新加坡同样 100~300ms/往返
  ⇒ 同因，非限速。

### 对策（按可行性）
| 方案 | 可行性 |
|---|---|
| 换 Supabase 区域 | ❌ Supabase 不支持改 region，只能新建项目迁移 |
| **减少往返次数**（缓存/合并查询/砍点查） | ✅ 已在做（026/027/029/031 全是这类） |
| 本地包承载更多读（读多写少数据落 pack） | ✅ 既有体系，可扩展 |
| 连接池参数调优 | 边际收益小（连接已复用） |

### 长期事实已写入 `MEMORY.md`
`ap-southeast-1 / ~570ms每往返 / 非限速 / 优化第一定律=减少往返次数`。

  不是"每起一个进程就读 2.29MB"。
- 今天 `research-cache.db` 12:02 有写入 ⇒ 发生过一次研究缓存重建（分块读 mainflow_history，
  量级几 MB~几十 MB）。

`pg_stat_statements` 是**累计值**，无法事后按天拆分。要精确归因必须**先取基线**：
```
python scripts/egress_probe.py snapshot --tag before
# …做事（改代码/跑脚本/开页面）…
python scripts/egress_probe.py snapshot --tag after
python scripts/egress_probe.py diff --from before --to after
```
⚠️ `egress_probe diff` 的 MB 是**上限**（部分列查询按整行宽算），看**相对排名**比看绝对值可靠。

## 037｜**更正 035**：调大 `mainflow_history` 分块大小**不能降 egress**

用户追问"分块读的块大小调大是什么意思"，顺着查清了 —— 035 里把它列为"降 egress 第 1 项"是**错的**。

### `CH = 120` 到底是什么
`research_cache._top_up_flow` 内的 `_fetch(codes, since)`：
```
codes 按 120 个一组切块 → 每块一条 SQL（WHERE code IN (120 个占位符)）
```
块大小只决定**把同一批行分成几次送**，不改变**总行数**。

### 为什么它不降 egress
- 返回行数/字节**完全不变**；
- 省的只是 RTT 与每条查询的协议头（实测口径：3,533 次 × ~1KB ≈ 3.5MB，对 ~5.8GB 可忽略）。
⇒ **块大小影响的是"延迟"，不是"流量"。**

### 真正的根因（已核实）
`_top_up_flow` 有两条分支：
- `need_tail`：本机已有该码、只是差最后几根 ⇒ 只补增量（小）
- **`need_full`：本机完全没有该码 ⇒ 取该码全量历史（~146 行/码）** ← 15,499 行/次就是这个

而 `.github/workflows/daily-batch.yml` **没有任何 `actions/cache` 步骤**（实测 grep：只有 ci.yml 有，
backend-pack/kline-data 用的是 upload-artifact）⇒ **每次都是全新 runner** ⇒
`backend/data/research-cache.db` 不存在 ⇒ **全部 ~1500 只都算"全新代码"** ⇒
`task_gate_snapshot → scoring.gate_watch → gate._load_gate_flow → research_cache.flow_map()`
每次都把 mainflow_history **全量历史重读一遍**。

### 正确修法（按收益/风险排序）
1. **给 daily-batch 加 `actions/cache` 缓存 `backend/data/research-cache.db`（含 flow-map.db）**
   —— 一次配置，之后只走 `need_tail` 增量（几 MB）。**收益最大、风险最低**。
2. 若不愿依赖 cache：`_load_gate_flow` 回源改窗口读（gate 只用到 flow5，days=20 够）——
   但要处理 `_stale_flow_codes` 的 GROUP BY（`flow.py` 注释实测窗口读一次 444 秒，pooler 慢，需谨慎）。
3. 给 `_fetch(need_full)` 加日期下限 —— 会改变 chip 网格口径（`n` 会变），**需先回测评估**。

### 教训
**"减少调用次数" ≠ "减少出口流量"。** 前者优化延迟/连接开销，后者只能靠"少取行、少取列"。
以后再提"降 egress"，必须先回答：这个改动会让**返回的行数或字节**变少吗？不变就不是 egress 优化。

## 038｜`daily-batch.yml` 加 `actions/cache`（`126cdf1f`）—— 落实 037 的修法①

用户："改 workflow 加 cache"。

### 改了什么
`daily-batch` job 的 `Set up Python` 之后、`Install dependencies` 之前，插入：
```yaml
- name: Restore local DB caches (egress)
  uses: actions/cache@v4
  with:
    path: |
      backend/data/research-cache.db
      backend/data/flow-map.db
      backend/data/market-snapshot-cache.db
    key: localdb-${{ runner.os }}-${{ github.run_id }}
    restore-keys: |
      localdb-${{ runner.os }}-
```

### 三个路径已逐一核实（不是猜的）
- `research_cache._PATH` = `backend/data/research-cache.db`（`_top_up_flow` 的 flow 表所在）
- `flow._FLOW_DISK_PATH` = `backend/data/flow-map.db`（整表读落盘）
- `store._SNAP_DISK_PATH` = `backend/data/market-snapshot-cache.db`（行情快照，2.38MB）

### key 为什么用 `run_id`
GitHub 缓存**不可变**：同 key 第二次起直接命中旧文件、**不再保存**。
若用固定 key ⇒ 缓存永远停在第一次 ⇒ 本地末根停在很久以前 ⇒ `since = min(local_max)`
退化为"从很久以前补起"，比不加缓存更贵。⇒ 每次唯一 key 保存，`restore-keys` 前缀恢复最近一份。

### 代价与上限
每天新增 1~3 份 ~110MB 条目；仓库缓存上限 10GB，7 天未被命中即淘汰 ⇒ 稳态约 1~2GB。
若逼近上限，改按日期分桶 + 只留 restore-keys。

### 预期
`need_full` 从「全部 ~1500 只」降到 0（或仅新股），改走 `need_tail`（全池各补 1 根 ≈1.5k 行）。
按探针口径，那条占全周七成的语句应降到 1/100 量级。

### 未做（有意）
`backend-pack.yml` 没加 —— 它本身就是"全量重建数据包"，读全量是**目的**不是浪费，
加缓存帮不上忙。真正受益的只有"按增量语义设计、却被新环境逼成全量"的 daily-batch。
