## 001 线上日志体检 → 修 3 个（`5615e757`）

### ① 【严重】竞价时段「涨停家数」显示 0（已修）
日志原句：
```
[market][shadow] limit counts: approx(mem) up=21 down=13 | rt_k(exact) up=0 down=0 | delta up=-21 down=-13 | data_date=2026-10-29 intraday=True age=16.2s
```
- 根因：`rt_k` 在 **09:15~09:25 集合竞价**时 `close` 尚未成交（=0），而 `high_limit` 有值
  ⇒ 逐票 `close >= high_limit × (1-tol)` **全不成立** ⇒ `up=0 down=0`。
- 为什么没被拦住：`counts_best` 的两道闸门是 `require_intraday`（看 `is_intraday`）和
  `min_trading`（**调用方没传**）。而 09:22 的 `data_date` 已是今天 ⇒ `is_intraday=True` ⇒ 放行。
- 用户可见后果：盘前页面「涨停 0 / 跌停 0」。**0 比 21 更误导**（会以为今天真没涨停）。
- 修：`limit_stats.counts_best` 加**全零保护** —— `touched == 0` 且内存侧有数 ⇒ rt_k 不可用，
  回退 `board_approx`；同时 `routers/market._limit_counts_best` 补传 `min_trading=4000`
  （防"3 批挂 1 批"时家数被安静低估，却仍标"精确口径"）。
- 四分支桩测：竞价全零→近似(21/13)｜极冰点(内存也 0)→rt_k(0/0)｜正常盘中→rt_k(69/3)｜
  trading=3600→近似。全过。

### ② 【噪音】fuyao `code=5003` 每 60s 打一次（已修）

### 通用教训
- **`is_intraday` 不等于"数据可用"**：`data_date == today` 只能说明"这是今天的数据文件"，
  不能说明"里面已经有成交"。竞价时段的 rt_k 就是"今天的空壳"。
  ⇒ 凡是拿 `is_intraday` 当唯一闸门的地方，都要再补一个**内容有效性**判据（家数/样本量/非零）。
- **"必然失败的外呼"要主动删**：注释里写着"已停披"却仍在调用的代码，是最容易被忽略的浪费源。

## 002 用户报"今天爆内存" → 库里的数据**不支持**这个结论（`354b25bf` / `8adabf81`）

用户只发了一句话（**没有附日志内容**），我从 `memory_probe` 自己取证：

```
10-29 全天 RSS：最高 246.9MB（49.4%）   ≥70% 的采样：**0 条**
全天唯一真断档：10:19:53 → 13:02:47，断了 **163 分钟**
断档前最后一条：10:19:53  rss=155.0MB  pct=31.0%
```

⇒ **按进程 RSS 看，被杀前只有 155MB（31%），根本不可能被 OOM。**
（其余"30 分钟断档"是 10-28 下午之前采样间隔本来就是 30 分钟，不是断档。）

三种互斥解释，**现有数据无法定论**（需 Render 事件日志）：
1. 155MB → 512MB 在 10 分钟采样间隔内暴涨（采样没抓到那一下）；
2. **不是 OOM**，是部署/健康检查/平台侧重启（163 分钟远超一次 Redeploy）；
3. **`VmRSS` ≠ 容器内存** —— 平台判的是 cgroup `memory.current`，
   含 **page cache**；本项目 `pack_source` mmap 一个 ~126MB 库文件，
   这部分大部分记在 page cache（算容器、不算进程 RSS）⇒ 可以"进程说 31%、平台说 100%"。

### 已落地的改进（无论哪种解释都该有）
- `routers/system._read_container_mem()`：读 cgroup v2（`memory.current` / `memory.max`）
  → 回退 v1；`collect_memory_snapshot` 新增 `container_mb / container_limit_mb /
  container_pct / container_src / page_cache_mb`（= 容器 − 进程 RSS）。
- `memory_probe` 加三列 `container_mb / container_pct / page_cache_mb`
  （**升级老表必须 ALTER**；`CREATE IF NOT EXISTS` 不会改已存在的表；
  SQLite 无 `ADD COLUMN IF NOT EXISTS` ⇒ 先探测列再 ALTER，
  加不上就**不写该列**，否则整个 upsert 会连原有采样一起丢）。
- 本地 Windows 无 cgroup ⇒ 全 None（不猜测）。

### 教训
- **监控指标选错了，比没有监控更糟**：`memory_probe` 跑了三天、采样 400 条，
  却在用户报"爆内存"时**给出反向证据**（31%），因为量的是进程而不是容器。
  ⇒ 监控某资源前先问一句：**"平台是按什么口径杀我的？"** 口径不同等于没监控。
- 日志/证据缺失时**不要顺着用户的结论走**。用户说"爆内存"，数据说"31%"，
  正确做法是把矛盾直接摊开 + 说明还需要什么，而不是编一个"内存泄漏"的因。
- 卫生门 `except_pass`（GUARDRAILS #11）会拦 `except: pass`；
  探测型异常分支要**显式赋值**（`_exists = False`）或**打日志**，不能空 pass。

## 003 真凶确认：pack 页缓存撑爆容器（`968a0a09`）

用户补了日志，**02:10~02:20 每 2 分钟重启一次、共 5 次**（`Started server process [1]` × 5）
⇒ 典型的 **OOM 崩溃循环**，与 002 里"库里只看到 155MB"完全对得上：
**采样器 10 分钟一次，爆点发生在启动后 30~60 秒内 ⇒ 永远抓不到。**

### 机制（把三条线索串起来）
1. 日志每次启动都有：
   `[data_files] BAD 后端数据包: 文件不存在` → `[pack_source] 下载数据包`
   ⇒ **容器文件系统是临时的，每次重启都要重下**。
2. `[pack_source] 已就绪: .../backend-pack.db (250.2 MB)` —— 包已长到 **250MB**（登记时还是 126MB）。
   下载 gz + 解压出 250MB db ⇒ **两次写盘 ≈350MB 页缓存**。
3. **page cache 不算进程 RSS，但算容器内存（cgroup `memory.current`）**
   ⇒ 进程 155MB + 页缓存 350MB ≈ 505MB ≈ 撞 512MB 上限 ⇒ 被杀 ⇒ 文件随容器销毁 ⇒ 再下 ⇒ 再爆。

### 为什么之前一直没发现
- `memory_probe` 量的是 `VmRSS`（只看进程）⇒ 页缓存份额**从来没被观测**。
- 采样间隔 10 分钟，而爆点在启动后 1 分钟内 ⇒ 时间上也是盲区。
- 两条盲区叠加 ⇒ 监控"显示健康"（31%）而平台"判定超限"，**两个数字都对，只是量的不是一件事**。

### 修法（`pack_source`）
1. 写完**先 `fsync`**（脏页变干净页）**再 `posix_fadvise(DONTNEED)`** —— 顺序不能反，
   DONTNEED 只回收干净页；gz 与 db 各丢一次。
2. **gz 用完即删**（`os.remove`，不再 `os.replace` 留档）—— 全项目没有代码再读它
   （`redownload()` 只是删除），留着白占 250MB 磁盘 + 等量页缓存，正是循环的燃料。
3. 非 Linux / 无 `os.posix_fadvise` ⇒ 静默跳过（本地 Windows 跑不出效果，只能靠线上验证）。

### 已知未做（若仍循环，下一步）
- **`scheduler.start()` 与 `_pack_bootstrap()` 并发**：日志里
  `[02:19:49] 开始增量刷新行情...(5257 只)` 与 `下载数据包` 同一秒 ⇒ **双内存峰叠加**。
  彻底解需要"行情刷新等 pack 就绪"或反过来，属启动流程重构，风险高于本次改动，先观察。

### 教训
- **"监控显示健康 + 平台判定超限"不是矛盾，是口径不同**：容器内存 = 进程 RSS + page cache + tmpfs。
  以后看到"两边对不上"，第一反应应该是**核对口径**，而不是猜泄漏。
- **临时文件系统 + 大文件下载 = 崩溃循环的自催化**：每次重启都重做一遍最重的动作，
  失败一次就永久失败。凡"启动时下载大文件"的地方，都要问：**重启会不会放大它**？
