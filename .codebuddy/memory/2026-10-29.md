## 002 用户报"今天爆内存" → 库里的数据**不支持**这个结论（`354b25bf` / `8adabf81`）

用户只发了一句话（**没有附日志内容**），我从 `memory_probe` 自己取证：

```
10-29 全天 RSS：最高 246.9MB（49.4%）   ≥70% 的采样：**0 条**
全天唯一真断档：10:19:53 → 13:02:47，断了 **163 分钟**
断档前最后一条：10:19:53  rss=155.0MB  pct=31.0%
```

⇒ **按进程 RSS 看，被杀前只有 155MB（31%），根本不可能被 OOM。**
（其余"30 分钟断档"是 10-28 下午之前采样间隔本来就是 30 分钟，不是断档。）

三种互斥解释，**现有数据无法定论**（需 Render 事件日志）：
1. 155MB → 512MB 在 10 分钟采样间隔内暴涨（采样没抓到那一下）；
2. **不是 OOM**，是部署/健康检查/平台侧重启（163 分钟远超一次 Redeploy）；
3. **`VmRSS` ≠ 容器内存** —— 平台判的是 cgroup `memory.current`，
   含 **page cache**；本项目 `pack_source` mmap 一个 ~126MB 库文件，
   这部分大部分记在 page cache（算容器、不算进程 RSS）⇒ 可以"进程说 31%、平台说 100%"。

### 已落地的改进（无论哪种解释都该有）
- `routers/system._read_container_mem()`：读 cgroup v2（`memory.current` / `memory.max`）
  → 回退 v1；`collect_memory_snapshot` 新增 `container_mb / container_limit_mb /
  container_pct / container_src / page_cache_mb`（= 容器 − 进程 RSS）。
- `memory_probe` 加三列 `container_mb / container_pct / page_cache_mb`
  （**升级老表必须 ALTER**；`CREATE IF NOT EXISTS` 不会改已存在的表；
  SQLite 无 `ADD COLUMN IF NOT EXISTS` ⇒ 先探测列再 ALTER，
  加不上就**不写该列**，否则整个 upsert 会连原有采样一起丢）。
- 本地 Windows 无 cgroup ⇒ 全 None（不猜测）。

### 教训
- **监控指标选错了，比没有监控更糟**：`memory_probe` 跑了三天、采样 400 条，
  却在用户报"爆内存"时**给出反向证据**（31%），因为量的是进程而不是容器。
  ⇒ 监控某资源前先问一句：**"平台是按什么口径杀我的？"** 口径不同等于没监控。
- 日志/证据缺失时**不要顺着用户的结论走**。用户说"爆内存"，数据说"31%"，
  正确做法是把矛盾直接摊开 + 说明还需要什么，而不是编一个"内存泄漏"的因。
- 卫生门 `except_pass`（GUARDRAILS #11）会拦 `except: pass`；
  探测型异常分支要**显式赋值**（`_exists = False`）或**打日志**，不能空 pass。

## 003 真凶确认：pack 页缓存撑爆容器（`968a0a09`）

用户补了日志，**02:10~02:20 每 2 分钟重启一次、共 5 次**（`Started server process [1]` × 5）
⇒ 典型的 **OOM 崩溃循环**，与 002 里"库里只看到 155MB"完全对得上：
**采样器 10 分钟一次，爆点发生在启动后 30~60 秒内 ⇒ 永远抓不到。**

### 机制（把三条线索串起来）
1. 日志每次启动都有：
   `[data_files] BAD 后端数据包: 文件不存在` → `[pack_source] 下载数据包`
   ⇒ **容器文件系统是临时的，每次重启都要重下**。
2. `[pack_source] 已就绪: .../backend-pack.db (250.2 MB)` —— 包已长到 **250MB**（登记时还是 126MB）。
   下载 gz + 解压出 250MB db ⇒ **两次写盘 ≈350MB 页缓存**。
3. **page cache 不算进程 RSS，但算容器内存（cgroup `memory.current`）**
   ⇒ 进程 155MB + 页缓存 350MB ≈ 505MB ≈ 撞 512MB 上限 ⇒ 被杀 ⇒ 文件随容器销毁 ⇒ 再下 ⇒ 再爆。

### 为什么之前一直没发现
- `memory_probe` 量的是 `VmRSS`（只看进程）⇒ 页缓存份额**从来没被观测**。
- 采样间隔 10 分钟，而爆点在启动后 1 分钟内 ⇒ 时间上也是盲区。
- 两条盲区叠加 ⇒ 监控"显示健康"（31%）而平台"判定超限"，**两个数字都对，只是量的不是一件事**。

### 修法（`pack_source`）
1. 写完**先 `fsync`**（脏页变干净页）**再 `posix_fadvise(DONTNEED)`** —— 顺序不能反，
   DONTNEED 只回收干净页；gz 与 db 各丢一次。
2. **gz 用完即删**（`os.remove`，不再 `os.replace` 留档）—— 全项目没有代码再读它
   （`redownload()` 只是删除），留着白占 250MB 磁盘 + 等量页缓存，正是循环的燃料。
3. 非 Linux / 无 `os.posix_fadvise` ⇒ 静默跳过（本地 Windows 跑不出效果，只能靠线上验证）。

### 已知未做（若仍循环，下一步）
- **`scheduler.start()` 与 `_pack_bootstrap()` 并发**：日志里
  `[02:19:49] 开始增量刷新行情...(5257 只)` 与 `下载数据包` 同一秒 ⇒ **双内存峰叠加**。
  彻底解需要"行情刷新等 pack 就绪"或反过来，属启动流程重构，风险高于本次改动，先观察。

### 教训
- **"监控显示健康 + 平台判定超限"不是矛盾，是口径不同**：容器内存 = 进程 RSS + page cache + tmpfs。
  以后看到"两边对不上"，第一反应应该是**核对口径**，而不是猜泄漏。
- **临时文件系统 + 大文件下载 = 崩溃循环的自催化**：每次重启都重做一遍最重的动作，
  失败一次就永久失败。凡"启动时下载大文件"的地方，都要问：**重启会不会放大它**？

## 004 包体瘦身（`faf8099f`）：249.9MB → 184MB，-26.4%

### 诊断（本地就有包，直接审计）
`backend-pack.db` 只有 **4 张表**，`klines` 独占全部：
```
klines      2,103,667 行  (2023-09-15 ~ 2026-10-26)
codes       2,884 行
indicators  2,884 行
meta        1 行
```
- 数据本身 ≈ **112MB**（每行 56 字节：code 9 + date 10 + 5×REAL 40 ≈ 59）
- 文件 **249.9MB** ⇒ **索引+页头+碎片 ≈ 137MB（55%！）**
- 索引只有一条：`PRIMARY KEY (code, date)` 的隐式索引

### 根因：普通表 = **两份存储**
`CREATE TABLE ... PRIMARY KEY (code,date)` 但**没有 `WITHOUT ROWID`** ⇒
① 按 rowid 堆存的行 + ② 主键索引（每条再存一遍 code+date）
⇒ 2.1M 行存两遍，`code`(9B) 与 `date`(10B) 各出现两次。

### 实测四档（本地副本上跑，不碰原文件）
| 方案 | 体积 | 省 |
|---|---|---|
| 原样 | 249.9 MB | — |
| 仅 VACUUM | 242.7 MB | 2.9% |
| **WITHOUT ROWID** | **184.0 MB** | **26.4%** |
| + 砍 2023 | 172.5 MB | 31.0% |
| + 只留 2025~ | 132.6 MB | 47.0%（**丢 2024 整年，不建议**） |

**采用第二档**：零数据损失、纯结构优化。
（`VACUUM` 只省 2.9% 说明碎屑不是主因，是**结构本身**冗余。）

### 数据一致性已验证
全量重建后 **2103667 → 2103667 行，`SUM(close)` 差 = 0.0**；
本项目实际用到的四种查询（单只按日期 / 区间 / COUNT / `INSERT OR REPLACE` 同主键覆盖）全部行为不变。

### 一个关键链路发现

  **`update_backend_pack_incremental.py`**（增量）。
- 幸运的是增量脚本第 346 行 `gbp.write_sqlite(...)` **复用同一个写库函数**
  ⇒ 改一处即可覆盖全量与增量两条路径。**改前必须确认"真正执行的那条路"**。

### 顺手修的第二个内存炸弹

## 005 前端本地存储：早就有，但「增量」是伪增量（只分析，未改）

用户问"改成存在前端本地、每天增量，可行吗"。查证结论分三层：

### ① 前端本地存储 **已经实现**，不是要不要做的问题
`frontend/src/utils/klineDB.js`（IndexedDB，DB v2，3 个 store）：
- `stocks` / `indicators` / `meta`
- `importKlinePack` 全量导入、`applyDelta` 增量（`mergeKlines` 按日期去重合并）
- `checkAndUpdate`：**先试 `kline-delta-{today}.json`，404 才下全量 gz**
- 版本控制 `pack_version`（结构升级强制重下）+ `pack_check_at` 6 小时窗口
  （后者是 2026-10-26「一天 2.18GB」事故的补丁：每次进页面都重下 3.8~5.5MB）

### ② 但 delta **是伪增量**（真问题）
`scripts/generate-kline-pack.py: compute_delta`：
```python
if prev_last != curr_last:
    delta[code] = data      # ← 整段 150 天历史重发，只加 1 根也全给
```
⇒ delta（裸 JSON）≈ **12MB**，而全量 gz 只有 **2.68MB**
⇒ 有 delta 的日子，前端**反而比下全量多花 4 倍流量**。
真正该传的是 `date > 上一份最后一根日期` 的那 1 行/只 ⇒ 约 **60KB（150 倍）**。

### ③ 改真增量 **必须两端配合**，否则丢数据
只改生成侧会出事：delta 只含"今天 vs 昨天"的 1 根，用户若 3 天没打开，
只会补 1 根 ⇒ **中间 2 天永久缺失**（K 线缺 → 指标错 → 评分错，且不报错）。
⇒ 必须：delta 带 `base: prev_pack_date`，前端校验 `base == 本地 last_update`，
不等则**回退全量**。`applyDelta` 本身不用改（`mergeKlines` 已能合并）。

### ③-b 已做 gzip（`3533ebb9`）—— **但真实收益远小于我的预估，必须记下来**
改：生成侧写 `kline-delta-{date}.json.gz`（不再产 `.json`），前端 fetch 后走 `decompressGzip`。
实测（1500 只 × 150 根的真实数据）：
```
裸 JSON  10.11 MB
gzip 后   3.17 MB（31%）
全量包    2.68 MB   ← gzip 后的 delta 仍比全量大 18%
```
**⚠️ 关键纠正**：我上一轮说"12MB → 3MB，省 4 倍"是**错的**——那 10MB 是**裸 JSON 大小**，
而 **GitHub Pages（Fastly CDN）本来就会对 `.json` 做 gzip/brotli 传输** ⇒
改前实际传输也约 3MB。**所以这条改动的网络收益 ≈ 0**，只是把"靠 CDN 压缩"变成"自己压"，
好处是**可控、不依赖 CDN 对扩展名的策略**。
⇒ 真正值钱的是**修伪增量本身**（10MB → 约 60KB，150 倍），不是 gzip。
⇒ **教训：算"省多少流量"必须用「网络传输体积」而不是「文件字节数」**，
   先确认 CDN/网关有没有已经压过 —— 否则会把 0 收益当成 4 倍收益汇报出去。

### ③-c 真增量已实现（`d44c158d`）—— 这是唯一真正省流量的改动
**生成侧**（`generate-kline-pack.py`）：
```python
prev_last = str(prev_klines[-1][0] or "")
new_bars = [k for k in curr_klines if str(k[0] or "") > prev_last]
```
- 新增股票（本地没有）仍整只给，否则前端拿不到历史；
- `delta_pack` 加 **`"base": prev_pack_date`**（这份 delta 从哪一份包算出来的）。

**前端**（`klineDB.checkAndUpdate`）：
- 抽出 `_downloadFullPack()` —— 全量入口现在有 4 个（首次/结构升级/增量 404/base 不匹配），
  复制四遍必然漂移（旧版两处判重逻辑就已经不一致）；
- delta 应用前校验 `delta.base === 本地 last_update`，**不等或无 base 一律回退全量**。

**三场景测试（全过）**：
| 场景 | 结果 |
|---|---|
| 正常（本地 = base） | delta 每只只 1 根；合并后 **== 全量包** ✓ |
| 离线 2 天（本地早于 base） | 强行应用会缺 `2026-06-10` ⇒ 校验拦住、回退全量 ✓ |
| 首次安装（无本地） | 直接走 `_downloadFullPack`，不碰 delta ✓ |

**体积**（1500 只口径）：旧 ~10MB 裸 / 3.17MB gzip → 新 ~90KB 裸 / 约 25KB gzip。

**测试数据踩的两个坑（值得记）**：
1. 手拼 `f"2026-10-{i:02d}"` 超过 31 会造出 `2026-10-32` 非法日期 ⇒ 排序全乱、结论不可信；
2. `bars()` 用 `random.uniform` 而不固定 seed ⇒ `bars(10)` 与 `bars(11)` 前 10 根数值不同，
   "合并后是否等于全量"必然假失败 —— **那是测试数据的问题，不是被测代码的问题**。

### ④ 它**替代不了**后端 pack
后端 pack 服务的是 **FastAPI**（微信推送、GitHub Actions 日批、任何非浏览器客户端），
与浏览器本地存储无关。去掉后端 pack ⇒ 回退 Supabase 直连 ⇒ egress 暴涨
（这正是当初做 pack 的原因，见 `pack_source` 模块头）。
⇒ 两者是**互补**，不是替代：前端本地省"浏览器→后端"的请求，后端 pack 省"后端→Supabase"。
