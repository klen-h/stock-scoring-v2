## 001｜迁移到自有服务器：方案与三个坑（尚未执行）

### 用户新购服务器（今天开通，到期 2027-11-03）
宝塔 Linux 面板 9.2.0（阿里云专享版）｜2 vCPU / **2 GiB** / 40 GiB ESSD
公网 `101.201.222.167`，内网 `172.24.14.59`

### 现有架构（迁移前）
```
GitHub Pages (klen-h.github.io)  ──HTTPS──▶  Render 后端（新加坡，512MB，READ_ONLY=1）
GitHub Actions 日批               ────────▶  Supabase（新加坡）
```
- 前端 `baseURL = import.meta.env.VITE_API_BASE_URL || '/api'`
- 后端 CORS 白名单含 `https://klen-h.github.io`

### 推荐方案：**前后端同机 + nginx 反代 /api + IP:80 访问**
理由：同源 ⇒ 无 CORS、无 HTTPS 混合内容问题；**IP 直接访问 80 端口不需要 ICP 备案**
（备案是"域名 + 大陆服务器"的要求）。前端 `baseURL` 默认 `/api` **不用改代码**。

### 三个必须知道的坑
1. **`frontend/Dockerfile` 用 `node:16`，而 vite 是 `^5.4.0`（要 Node 18+）**
   ⇒ 那个 Dockerfile **构建会失败**。前端不要走 Docker：本地 `npm run build` 后把
   `frontend/dist` 传上去，用宝塔静态站点托管。
2. **若前端继续留在 GitHub Pages（HTTPS），后端必须 HTTPS**
   —— 否则浏览器拦 mixed content。要么给后端配域名+证书（大陆需备案），
   要么把前端一起搬过来（推荐）。
3. **2 GiB 仍要防闸门 210MB**：`gate_states_for_signals` 单次构建就 ~210MB，
   加上基础占用 ~200MB。今天已验证的"逐条增量 + 单飞锁"必须在生产生效，
   否则 2G 也会被吃穿。

### 迁移收益（可量化）
- 内存上限 512MB → **2 GiB**（今天爆了 8 次 OOM）
- Supabase 往返：本机实测 570ms/次 → 阿里云北京到新加坡约 **200~300ms/次**
  ⇒ 所有"慢接口"会同时变快（这是比扩容更实际的收益）

### 002｜服务器运维小记（迁移进行中）
- 登录用户是 **`admin`（非 root）** ⇒ 所有 `bt` 命令必须 `sudo bt ...`，
  否则 `/www/server/panel/*` 全部 Permission denied，输出里**端口和密码是空的**（不是面板没装）。

### 003｜生产部署配置已落地（`4fd373d3`）
新增两个文件（**不是**开发用的根目录 compose）：

- `deploy/docker-compose.prod.yml`：**只起 backend**
  - `ports: 127.0.0.1:8000:8000` —— 不对外暴露，外网统一走 nginx
  - `mem_limit: 1536m`（2G 机器；闸门 210MB + 基础 200MB 有余量）
  - `environment`: `TZ` / `MALLOC_ARENA_MAX=2` / `ASYNCIO_POOL_WORKERS=6`
  - `volumes: ../backend/data` —— 不挂则容器重建丢 tracking/diagnosis/research-cache.db
  - healthcheck 用 `python -c urllib`（slim 镜像无 curl）
- `deploy/nginx-site.conf`：静态 dist + `/api` 反代
  - `proxy_pass http://127.0.0.1:8000;` **不带 URI**（带了会多拼一层 `/api` 全 404）
  - `proxy_read_timeout 180s`（LLM 同步调用前端给 120s，nginx 默认 60s 会先 504）
  - `index.html` 必须 `no-store`（否则发版后白屏），`/assets/` 长效缓存

**为什么前端不走 Docker**：`frontend/Dockerfile` 是 `node:16`，而 vite `^5.4.0`
要 Node 18+ ⇒ 构建必失败。改为本地 build → 传 `dist` → 宝塔静态站点。

**服务器上的目标结构**
```

  backend/.env                          从 Render 控制台复制（不入库）

  frontend/dist/                        本地 build 后上传
```

### 004｜构建上下文配错导致「没有 requirements.txt」（`f5cbaa35`）

**用户报错**：服务器上执行 compose 构建，提示 `requirements.txt` 不存在，问是否要手工创建。

**真相：文件在，是我的 compose 写错了。**
`Dockerfile` 里的 `COPY ./requirements.txt .` / `COPY . .` 路径是**相对构建上下文**
（不是相对 Dockerfile 所在目录）。而 `requirements.txt` 只在 `backend/` 下，
仓库根目录**没有** ⇒ `context: ..`（根）时第一条 COPY 就 "not found"。

**修法**：`context: ../backend` + `dockerfile: Dockerfile`（prod），
根目录开发用 `docker-compose.yml` 同样是错的，一并改成 `context: ./backend`
（那份**从来没有构建成功过**，所以之前没人发现）。

**验证**：用 yaml 解析两份 compose，`os.path.exists(context/requirements.txt)` 均为 True。

**教训（Docker 通用）**：
`COPY` 的源路径永远相对 **build context**，且 **Dockerfile 放在子目录时，
context 必须指向那个子目录**，否则第一层 COPY 就炸。
看到"文件不存在"先查 context，别急着补文件 —— **手写 requirements.txt 会漏依赖**，
后面会变成一堆 ImportError，比现在的错更难查。
