# 2026-11-10 工作记录

## 快讯抓取间隔与压力评估（用户问：间隔多少？减少会加大服务器压力吗？）

### 现状

```
FLASH_POLL_INTERVAL = int(os.environ.get("FLASH_POLL_INTERVAL_SEC", "300"))   # scheduler.py:40
TRACK_INTERVAL      = int(os.environ.get("TRACK_INTERVAL_SEC", "300"))
```
**默认 300s（5 分钟）**，`.env` 里是注释掉的（即用默认）。**无下限校验**（设 5 也会接受）。

`flash_loop` 是 24h 全天轮询（**不判交易时段**），每次 `service.poll_flash_once()`。
实测 `flash_news` 最新到 `2026-11-10 00:50`、1007 行 ⇒ 抓取链路正常。

### 单轮真实成本（实测，非估算）

```
flash_state 总大小 = 3,540 字节（3.5 KB）
  ├ lastId           20 字节
  └ pushedClusters 3,520 字节 / 仅 12 条   ← 有限枚举，不会无限增长
```

`poll_flash_once()` 的固定开销：

| 步骤 | 成本 |
|---|---|
| `fetch_jin10()` | **1 次 HTTP**（金十，timeout=30，返回几十条） |
| `get_new_items()` → `load_state()` | **2 次 DB SELECT** |
| `get_new_items()` → `save_state()` | **2 次 DB UPSERT**（整份写回 3.5 KB） |
| `save_raw_data()` | **无新条目时立即 return**（2026-09-11 已优化） |
| 规则过滤 + 聚类 | 纯 CPU 文本匹配，极轻 |
| **LLM** | **只在新簇 / 升"爆" / 重大更新时触发，与轮询次数无关** |

### 折算表

| 间隔 | 轮询/天 | DB 往返/天 | state 写回/天 |
|---|---|---|---|
| **300s（现状）** | 288 | 1,152 | 1.0 MB |
| 180s | 480 | 1,920 | 1.6 MB |
| 120s | 720 | 2,880 | 2.4 MB |
| 60s | 1,440 | 5,760 | 4.9 MB |
| 30s | 2,880 | 11,520 | 9.7 MB |

### 结论：缩短间隔的**真实**压力很小，但有唯一硬风险

**不构成压力的**：
- **CPU / 内存**：几乎无影响。抓取走 `asyncio.to_thread`（线程池上限 6），300s 间隔下一次 1~3s，占用率约 1%；60s 也才 5%。
- **Supabase egress**：即使 30s 也才 9.7 MB/天。关键原因是 `pushedClusters` 只有 **12 条**（簇是**有限枚举** `rules.EVENT_CLUSTERS`，不是动态聚类）⇒ 不会随时间膨胀。
- **LLM 成本**：**完全不受影响**。LLM 由"新簇 / 升爆 / 重大更新"触发（`service.py:90-99`），轮询次数再多，没新簇就不烧 token。

**唯一的硬风险**：
- **金十接口的限流 / Cookie 封禁**。代码注释（`scheduler.py:38`）原话：
  「再小要留意金十限流/Cookie 风险」。它是**免费接口 + Cookie 鉴权**，
  频率过高可能触发风控 ⇒ **不建议低于 60s**。

**DB 请求数虽涨 5 倍（1152→5760/天），但每次 payload 只有 3.5 KB，不是 egress 问题、
而是连接往返次数问题** —— 若哪天换回按请求计费/连接池紧张才需在意。

### 若要调，建议

1. **交易时段 60~120s、非交易时段保持 300s** —— 快讯的价值集中在盘中/重大事件，
   夜间降频既省请求也避开金十风控。
2. **给 `FLASH_POLL_INTERVAL` 加下限保护**（如 `max(30, ...)`），
   现在设成 `5` 也会照跑，配合"无下限校验"是个隐患（目前还没踩，但没有护栏）。

## ★★ 通知"线上点击无反应"根因（`bec282da`）

`Notification` **只在 secure context 可用**（https:// 或 localhost）。http:// 域名下：

- `'Notification' in window` **仍为 true** ⇒ `supported` 为真、按钮正常显示（UI 被骗过）；
- 但 `Notification.requestPermission()` **直接返回 `'default'` 且不弹授权框**；
- 调用方 `ok=false` + `permission` 仍是 `'default'` ⇒ 既不成功也不 `denied`
  ⇒ 三处 handler 的 `if (!ok && permission === 'denied') alert(...)` **不触发**
  ⇒ **一句提示都没有 = "点击无反应"**。

**本地 `localhost` 属于 secure context ⇒ 本地一切正常。这就是本地/线上差异的唯一来源。**

修复（`useNotifications.requestPermission`）：显式判 `!window.isSecureContext` → `alert` 说明需要 HTTPS；
另补 `result === 'default'`（浏览器既不弹框也不报错，多见于策略拦截/内嵌 WebView）的兜底提示。
⚠️ 三处开关（`Portfolio` / `TradePlans` / `Watchlist`）共用这一个函数，改一处全受益。

## ★ 观察器与实时机制盘点（分析结论，未改代码）

### 防骚扰：首次运行**只建基线、不推送**
